# 階段一：行前規劃

適用：排行程、改行程、選餐廳、訂位、產交付物。
特徵：有時間查到底，使用者不急，但錯了會連鎖到整趟。

前置：先讀 `SKILL.md` 四道閘門、`config/user-profile.md` 與 `state/<行程名>.md`。

---

## 一、開案前必做

```
1. 讀 config/user-profile.md（旅伴表、移動能力、飲食、門檻、地區實例）。
2. 讀 state/<行程名>.md。沒有 → 從範本建一份，先問齊才動手排。
3. 列出硬約束清單（已訂飯店／已付款票券／班機時間／不可調動的預約）。
4. 列出已排除選項（查過不行的，附原因）—— 避免重複推薦。
5. 行李狀態逐日化（見下）。
6. 雨天版（見下）。
7. 宣告「本次套用誰的條件、未套用哪幾類」。
```

**沒有旅伴表就不要排行程。沒有硬約束清單就不要排行程。**

### 1-1 行李狀態逐日化

```
每天標：手上有幾件行李／當日寄物點
寄物點要查到：站名 + 櫃號尺寸 + 費用 + 營業時間 + 客滿備案
```

🔴 **「不可宅配」是硬約束，但 Gate-H 只能做減法（排除候選），
不能做加法（新增必查欄位）** —— 所以這條硬約束在 Gate-H/V/S 裡
沒有任何一道消化得了，必須在這裡變成動作。

> 使用者原話：「我不可能宅配」。
> 失敗情境：回程日排「清水寺 → 午餐 → 搭 JR」，步行實算、無折返、
> 餐廳齊備、檢核表全綠 —— 而清水寺是坡道石階且無置物櫃，
> 使用者得提著 4 人行李爬坡。

### 1-2 雨天版

```
降雨機率高的日子，當天必須有雨天版
做法：日內對調（室外↔室內），不動住宿、不動已訂票券
```

🔴 **跨日對調禁止（撞硬約束），日內對調允許且為必做。**
原規則只記下「整天對調被罵過」，把「需要雨天備案」這個對的意圖一起丟了，
於是在顯眼處留了一個會**抑制正解**的教訓。見 SKILL.md「做對了但手段錯」。

> 實際失誤（10-24）：我建議 10/26 ↔ 10/29 整天對調避雨，
> 完全沒考慮京都飯店已訂死。
> 使用者原話：「你是白痴嗎？你這樣子兩天對調之後那我到底還去不去京都我飯店都訂好了。」

> 實際失誤（10-25）：10/30 班機行程，我假設使用者留在京都，
> 但他早就說要提早回大阪。
> 使用者原話：「10月30的班機你又在耍智障了，我根本就會提早回去大阪啊，有沒有在看行程？」

## 二、動線與方位（E 類 24 次）

### 2-1 排順序前先算方位

兩個以上地點要排順序時，**先算距離矩陣與方位**，確認無折返，才排。

折返定義：**行進方向反轉且多走超過設定檔的 `折返門檻_分`。**

```
步驟：
1. 取每個地點的座標（!3d !4d，不是 @lat,lng）
2. 算兩兩直線距離，標出相對方位（N/S/E/W）
3. 檢查序列：方向是否單調？有反轉就是折返
4. 折返處標紅，重排或改交通方式
5. 時間軸投影（見 2-1a）
6. 日落稽核（見 2-1b）
```

⚠️ 第 2 步的「方位」是地理方位（判折返用），**不是太陽方位**。
別因為「方位算過了」就跳過第 6 步。

### 2-1a 時間軸投影（原規則只檢查空間，不檢查時間）

把估出的停留與移動時間疊成**實際抵達時刻**，然後檢查：

```
用餐時段（依設定檔的「固定用餐時間」）時，人在哪裡？
  → 該處步行可達範圍內有無合規餐廳？
  → 沒有 → 重排，不是讓人餓著

每個景點的抵達時刻 vs 最終入場時刻 / 閉館 / L.O.
  → 晚於最終入場 = 排錯了
```

🔴 **停留時間公式會膨脹**（排隊＋上下樓＋廁所加倍＋休息），
而原規則沒有任何一步回頭檢查「這樣推下去午餐變幾點」。
兩個各自正確的部分（嚴格的營業時間查核 + 會膨脹的停留公式）
組合起來會系統性產生「卡在景點裡吃不到飯」的行程。

孕期用餐不可延後（低血糖風險）→ 這是 1a 級醫療條件，不是舒適度。

### 2-1b 日落稽核

```
查當日當地**真實日落時刻**（不是憑印象）
所有戶外／山道／公園行程的結束時間必須早於
  「日落時刻 − 設定檔的 日落緩衝_分」
違反 → 重排
```

🔴 **用腳本算，不要憑印象也不要查表**：

```bash
python scripts/now.py --tz <當地時區> --at <座標或地標> --date <YYYY-MM-DD>
```

逐日跑一次（排 7 天就跑 7 次）—— 日落每天差 1–2 分，整趟下來差到 10 分以上。
公式算的，任何地點任何日期都能離線算；準確度已對第三方驗過（見 `02-現場即時.md` 1-5）。

⚠️ **緩衝值讀 `config/user-profile.md` 的 H 段，本檔不給數值。**
理由是跌倒風險，所以行動更不便的旅伴要拉長緩衝。

🔴 日落後照明不足，對孕婦／長輩是**跌倒風險**，不只是「看不到景」。
關西 10 月底日落約 17:00，11–1 月更早。

⚠️ **公式算不到海拔、地形遮蔽、陰雨天** —— 這三項都讓實際天黑更早。
緩衝就是在吸收它們，**不要因為公式準就調小**。
山區、谷地、冬季或雨天行程，緩衝要再加。

### 2-1c Gate-O 園內盤點（接 SKILL.md 的 Gate-O）

排進任何園區級景點前，先盤點**內部移動選項**，才准算步行：

```
園內遊園車／接駁巴士／纜車／水上巴士／電扶梯系統／空橋
園內動線：建議入口／出口／內部順序（影響園內實際步行距離）
```

> 真實失誤：大阪城天守閣往南，我算對了 1,642 m / 24 分、
> 認出超過上限、照規則提了替代交通 —— 全部合規。
> 使用者原話：「你竟然叫我搭車去，沒發現有遊園車，這根本不應該」

🔴 **不要把這類失誤歸類成「改走外圍道路重算」。**
那會讓下次把 1,642 m 改成外圍 2,000 m、重算更久、再提計程車 ——
兩個結論都通過全部檢核表，而正解仍然沒進候選集。

> 使用者原話（10-08，行前）：「你掃一下行程，有沒有折返跑的情況，你安排10/25 13:00 去搭遊船感覺就有折返跑」
> 使用者原話（10-08，行前）：「三十三間堂、包車路線你先確認一下方位」
> 使用者原話（08-30）：「錯，Day 2 去宇治 我就是大阪到宇治玩，玩完再去京都啊，幹嘛折返」

🔴 使用者**兩次主動要求**「確認方位」，我都沒做成流程，10-28 大阪城又犯。

### 2-2 步行時間一律實算

```
公式：分鐘 = 距離(m) ÷ speed_m_per_min × detour_factor

參數全部讀 config/user-profile.md 的 B 段，本檔不給數值。
每位旅伴各算一次 → 取最嚴。
🔴 某人的欄位是 ❓未問 → 【不可取別人的值代入】，回報「無法計算」並問
   （處置見 config/profile-schema.md「缺欄位時怎麼辦」）
```

超過該旅伴的 `max_leg_m` 必須主動提替代交通（含 Gate-O 盤點到的園內交通）。

**禁止估算、禁止目測。**

🔴 **公式結果是推算值，不是第三方來源。** 必須並列第三方導航時間，
差距超過設定檔門檻時取較保守者並註明。

> 原規則把第三方導航列進「不得用」，方向錯了：地圖的步行導航
> **天生不會穿越沒有路的公園**，恰恰是唯一能自動避免
> 「對角線穿越 105 公頃公園」那個錯的來源。

### 2-2a 當日總步行量（原規則只管單段）

```
把當天每段加總 → 對照該旅伴的 max_daily_m
超標 → 觸發 Gate-H 的刪減（刪景點或改交通），不是加休息了事
```

🔴 **單段門檻可被無限次重複而不觸發**：10 段 × (max_leg_m − 10 m) 全部合規。
而孕期（尤其孕期手術後）、長輩膝關節的限制是**總負荷**，不是單段。

加入休息後行程在時間軸上「排得進去」，於是看起來合規甚至「有照顧到」——
這是把累積量約束誤編碼成瞬時量約束。

| 實際失誤 | 我寫的 | 實算 |
|---|---|---|
| 天守閣往南 | 「15 分」 | **1,642 m / 24 分**，對角線穿越 105 公頃公園 |
| 整條路線 | 沒算 | **3,641 m / 52 分** |
| 飯店→東梅田 | 「走 3 分」 | **612 m / 9 分**（阪急梅田才 126 m / 2 分） |

### 2-3 景點停留時間不得低估

四個景點塞 130 分鐘，實需 165–195 分鐘。

```
每個景點必須分別估：
  移動到入口  +  排隊／購票  +  實際參觀  +  上下樓／石階  +  廁所
依設定檔另加：每 max_continuous_min 休息 rest_min、廁所頻率高者時間加倍
```

### 2-3a 入場制度盤點（Gate-O 的一欄）

```
需不需事前預約？  線上／電話／只限當地語言表單
分時段券？        哪些時段還有
最終入場時刻      ← 原規則完全沒有這項
閉館時刻 / L.O.
當日券售完時間
```

🔴 **「只能電話或當地語言表單預約」的景點，套用第四節的排除邏輯。**
原規則的訂位硬限制只寫在餐廳節，景點沒被覆蓋 ——
於是會排進一個使用者（講不出當地語言、不能打電話）根本進不去的景點。

> 失敗情境：排「16:30 抵達二条城」，步行實算、無折返、停留 60 分。
> 實際最終入場 16:00、16:45 關門。14 項檢核表全 pass。

### 2-3b 排隊時間事前估算

```
資料來源：地圖的混雜時段直方圖 ＋ 評論中的等待敘述 ＋ 整理券制度
估算超過設定檔門檻者 → 套分流條款（一人先排、一人去坐）
```

🔴 **歷史統計屬可查項，不得用「現場狀態不得假設」免除。**
原規則把「即時叫號不可知」錯誤推廣成「排隊時間不可知」，
於是會把 90 分鐘的排隊填成 0 ——**正確地遵守一條被錯誤套用的規則**。

只有「現在排到幾號」才是即時狀態。

> 使用者原話（08-31）：「延曆寺境內石階？你這樣四個景點9:40-11:50你確定跑的完？」

### 2-4 車站出口

出口編號必須依**使用者實際搭乘的路線**查該線改札，不得抄官網。
**路線改變時出口必須重算。**

> 實際失誤：阿卡將出口抄官網「御堂筋線 7 號出口」，
> 但使用者搭中央線，應走**南改札 11 號出口**。

百貨換樓層、地下街連通道，**沒有官方樓層圖就不猜**。

## 三、餐廳推薦（B 類 7 次、C 類 10 次）

### 3-1 必備三項，缺一不得稱推薦

```
① 設定檔 I 段的「主評分站」分數 —— 必須是該分店店頁，不是搜尋列表
② 設定檔 I 段的「第二來源」分數 + 樣本數
③ 讀過負評內容（至少掃最低星等）
```

🔴 **平台名一律讀設定檔，本檔不寫 tabelog。** tabelog 只有日本有。

**第二來源不足時的降級路徑**（原規則在此沉默，於是會靜默降級）：

```
該地區沒有獨立於地圖平台的第二評分站
  → 明標「單一來源」，不得默默當三項齊備
  → 改用：近期使用者評論內容 ／ 獨立媒體編輯評比 ／ 當地論壇
  → 全都沒有 → 標 HYPOTHESIS，不得稱「推薦」
```

分數必須綁定該分店本身，不得用同品牌其他分店。

**綁定方式**（判準在這裡，選擇器在快取層）：

```
① 證明讀的是該分店店頁，不是搜尋列表
② 取穩定識別碼（ftid + !16s；place_id 拿不到）
③ 換第二條入口重讀，數值一致

機械判準與實際選擇器 → cache/externals.md E-01 / E-03 / E-04
（用前先跑 scripts/check-cache.py 看有沒有過期）
```

🔴 **第 ③ 步不是「交叉驗證」。** 兩條入口都是同一個平台，
它只抓得到「我讀錯分店」，抓不到「平台本身資料是錯的」。
真正的交叉驗證要**不同營運主體**，見 `SKILL.md` Gate-V。

🔴 **不要在本檔貼選擇器。** 貼了就是兩份副本，改版時只會改一份。

> 實際失誤（かつ満）：我給 tabelog 3.62 推薦，實際那是**京橋店**的分數。
> JO-TERRACE 分店 Google 只有 3.3，是全棟最低，有中文負評「油不乾淨、有臭肉味」。
> 使用者原話（10-28）：「你真的很爛，你沒有去找一下其他家嗎？交叉驗證啊。」
> 使用者原話（10-28）：「你不會去看谷歌評分嗎？」

> 實際失誤（永田精肉店）：只讀官方文案「陶板自己調熟度」就推薦，
> **Google 實際 2.2 分（419 則）**。

### 3-2 同名不同店必須區分

分店、本店、駅前店、○○店 —— 一律用 ftid + `!16s` 區分，座標（`!3d!4d`）核對一次。

> 實際失誤：THE CITY BAKERY 同名兩家，B1 的 4.0(1,086) 7:30 開，
> 7F BRASSERIE RUBIN 4.0(464) 是餐廳 11:00 才開。

### 3-3 搜尋範圍宣告（Gate-S 的餐廳版）

```
搜尋範圍：<建築／樓層／半徑>
掃到 N 家
→ Gate-H 過濾（過濾項讀設定檔的旅伴條件）後 M 家
   依哪幾條禁忌排除了幾家：<逐條列>
→ 達設定檔「評分下限」且「樣本數下限」的 K 家
→ 品類去重後 J 家
跳過：<什麼、為什麼>
```

🔴 **過濾項不得在本檔列舉。** 寫死「生食／座敷／電話／站立／吸菸」
會造成換人時「逐項判定不適用 → 全部打勾 → 檢核表正確全綠」，
而該旅伴真正需要的過濾項（無障礙、電梯、座椅靠背、牙口、用藥）一項都不在清單上。

> 使用者原話（10-29）：「怎麼可能下次做這麼少你根本就沒有去查玩啊」
> 使用者原話（10-26）：「少了一個廚具機」

### 3-4 必吃標準與品類去重

- 「必吃」= 該品類在該地區有辨識度，不是「分數還可以」。
- 同一天不得推兩家同品類（兩家拉麵、兩家燒肉）。
- 推薦時附「建議點什麼」，不只給店名。

> 使用者原話（10-29）：「飯糰店建議我怎麼點…其他小吃也都請列出建議我點的品相你最好都要有實際數據支撐」

### 3-5 營業時間必須展開逐日表

搜尋列表的一行摘要**不算**。要在店頁點開逐日營業時間確認。

## 五、交付物（H 類 18 次）

### 5-1 結構照使用者要的來

每日路線**必須和當天時刻表放在一起**，不得分成兩個 tab。

> 使用者原話（10-09，行前）：「網站的每日路線跟行程表應該要放一起吧，你分兩個tab我怎麼看」
> 使用者原話（10-10，行前）：「還是不好，為什麼 每日路線 跟 行程表每天的時刻表 不能整合再一起」
> —— 連改兩次才對。第一次改完沒確認使用者要的是「整合」不是「並列」。

### 5-2 交付形式：預設單一本機檔

```
預設：一份本機 HTML 或 Markdown，路徑寫進狀態檔
不要主動做線上站台 —— 多一份副本就多一個會漏同步的地方
使用者明確要線上版才做
```

🔴 2026 關西行的教訓：做了 Vercel 站台，結果**站台落後本機檔三批修改**，
使用者現場打開發現沒更新。使用者原話：「這邊沒有更新啊」。
最後使用者直接說「網站可以關閉了，不須使用」。

### 5-3 規範與文件本身也算交付物（2026-11-01 教訓）

**不要把規範／規則文件複製成兩份放在不同地方。**

```
🔴 實際發生：規範同時放在 Claude\travel-agent\ 與 skill 的 references\
   改了 skill 忘了另一份 → 那邊還列著已下線的站台、已淘汰的 place_id 規則
   這是 H 類（交付物沒更新，18 次）的同型錯，只是對象從行程表變成規則本身
```

做法：**單一來源 + 指路**。真身放一處，其他地方只放「規範在哪」的連結，
並在過期副本放一份「已失效，別照做」的標示。

### 5-4 多副本時的同步紀律

真的有多份副本（本機 + 線上 / 本機 + Artifact）時：

```
1. 狀態檔「交付物路徑清單」列出全部路徑，一個都不漏
2. 一次改完全部，不准只改一份
3. 線上版改完要驗證：讀渲染後 DOM，確認新內容存在 —— 回 200 不算
4. 需要密碼的站台，先確認登入態成立（DOM 有登出連結／內容區塊），再讀目標頁
5. 禁止用截圖當驗證證據
```

### 5-5 原始碼位置

**不得放 scratchpad（會被清除）。** 放 `C:\Users\User\Claude\<專案名>\`。
