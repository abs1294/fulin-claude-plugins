## 一、座標：取錯欄位差 300 公尺

```javascript
// ✅ 正確：!3d !4d 是地點的實際座標
const m = location.href.match(/!3d(-?[\d.]+)!4d(-?[\d.]+)/);

// ❌ 錯誤：@lat,lng 是地圖視窗的中心點
// 搜尋結果頁的 @ 座標是「搜尋區域中心」，跟任何一家店都無關
```

> 真實失誤：炸魚餅店用了 `34.6689197`（搜尋頁中心）而非 `34.6662299`（實際店址），
> 差 300 m。「離主線 87 m／順路」這個結論整個錯。

取完座標要**反向驗一次**：把座標貼回 Google Maps，目視確認落在該店。

## 二、分店分數會接錯

搜尋列表（tabelog／Google）顯示的分數，可能是**同品牌其他分店**的。

```
必須：開該分店的店頁（機械證明見下），用 ftid + !16s 綁定
不得：用搜尋列表分數、用「○○（本店）」的分數套到分店
```

### 判準在這裡，實作細節在快取層

```
② 規範（本檔）  「必須證明讀到的是該分店店頁，不是搜尋列表」  ← 判準，不會變
④ 快取          具體的選擇器、URL 形狀、regex                ← 會隨改版失效
                → cache/externals.md E-01 ~ E-05（用前先看有沒有過期）
```

🔴 **不要在本檔重複貼選擇器。** 那會製造兩份副本，
而改版時只改一份 —— 正是 H 類（18 次）的同型錯。

### 🔴 Google 對不存在的店名會靜默重導向到近似店

**沒有錯誤訊息，沒有「找不到」提示** —— 它直接給你另一家店的頁面與分數。
只讀分數完全看不出來。

```
2026-11-01 實測：搜「551蓬莱 戎橋本店」（此店名不存在）
→ 靜默重導向到「551蓬莱 本店」，回 4.2 (4,603)
→ 若不比對 aria-label，就會把 4.2 當成「戎橋本店」的分數交出去
→ 與 かつ満 把京橋店分數套到 JO-TERRACE 店同型
```

不相等時：**不要改口說「就是這家」**。但「不相等」有三種，處置不同
（判準全文與實測四案例見 `cache/externals.md` E-01）：

```
aria-label == 我搜的                   → 通過
我搜的【包含】aria-label 全文            → 我多打了區名／地名，不是店不存在
                                          → 比對地址／座標落不落在我要的那一區
無包含關係                              → 這才是靜默重導向，報「該店名不存在」
```

🔴 **只做二分的逐字比對會製造假陽性。** 2026-11-01 dry-run 實測：
搜 `Flour and Stone Woolloomooloo`（雪梨真店，我多打了區名）
→ aria-label 回 `Flour and Stone` → 逐字不等 → 二分判準會報「不存在」
→ 而那家店明明就在。使用者會以為自己記錯店名。

連帶教訓：**使用者（或我自己）給的店名可能是俗稱、區域別稱或記錯**。
例：戎橋筋南端那家 551 的 Google 登錄名是「本店」，沒有「戎橋」三字。
相鄰 20 m 還有不同法人的「蓬莱本館」（4.0／1,009，門牌 6-1 vs 本店 6-3）—— 容易誤讀成同一家。
而「我多打了區名」正是這種俗稱問題的**最常見形狀** —— 三分支判準就是為它設計的。

🔴 **重導向可以跨國。** 實測搜 `Gelato Messina Antarctica Branch`（雪梨品牌的假分店）
→ Google 給了【香港灣仔】的 Messina，4.9(48)，而 feed===null、place 頁、
F7nice 分數三項判準全綠。只有 aria-label 比對擋住。
**判準不只要擋「換了分店」，要擋「換了國家」。**

### 🔴 「雙入口重讀」不等於交叉驗證

取到 ftid 後組第二條 URL 重讀，兩條都是同一個平台。

```
它能抓     我讀錯分店（讀到同品牌別家）
它抓不到   平台本身的資料是錯的      ← 「列表寫 8:00、實際平日 11:00」那次
```

🔴 **不得因為做了雙入口重讀就宣稱「已交叉驗證」。**
真正的第三方定義見 `SKILL.md` 的 Gate-V：**不同營運主體**。

> 真實失誤（かつ満）：我給 tabelog 3.62，那是**京橋店**的分數。
> JO-TERRACE 分店 Google 只有 3.3，是全棟最低，有中文負評「油不乾淨、有臭肉味」。

**同名不同店**（分店／本店／駅前店／館內不同樓層）一律 ftid + `!16s` 區分。

> 真實失誤：THE CITY BAKERY 同名兩家 —— B1 的 4.0(1,086) 7:30 開，
> 7F BRASSERIE RUBIN 4.0(464) 是餐廳 11:00 才開。

## 六、步行時間：公式與禁區

```
公式：分鐘 = 距離(m) ÷ speed_m_per_min × detour_factor
參數讀 config/user-profile.md 的 B 段（本檔不給數值）
每位旅伴各算一次 → 取最嚴
🔴 某人的欄位是 ❓未問 → 【不可取別人的值代入】，回報「無法計算」並問
   （處置見 config/profile-schema.md「缺欄位時怎麼辦」）
單段超過該旅伴的 max_leg_m → 必須主動提替代交通
當日加總超過 max_daily_m → 觸發刪減，不是加休息了事
```

**公式結果是推算值，必須並列第三方導航時間。**

🔴 **大型公園：先查園內交通（Gate-O），再考慮改走外圍。**

## 十一、下線交付站台：主 URL 404 ≠ 沒有活著的部署

```
🔴 curl 主網域回 404，不代表該專案已無部署
   實例（2026-11-01）：kansai-site.vercel.app 回 404，
   但 vercel ls kansai-site 顯示仍有 1 個 Ready 的 production deployment
   （受 Vercel Authentication 保護，直接 curl 回 302）
```

正確做法：

```bash
npx --yes vercel@latest whoami            # 先確認登入態（別假設沒登入）
npx --yes vercel@latest project ls        # 列全部專案，找出所有相關的
npx --yes vercel@latest ls <專案名>        # 逐專案列部署 —— 這才是真相
npx --yes vercel@latest remove <部署URL> --yes   # 移除部署（可逆，專案殼仍在）
npx --yes vercel@latest project rm <專案名>      # 🔴 刪專案（不可逆，須使用者本人授權）
```

驗證要三項都做：`vercel ls` 回 `No deployments found` ＋ 主 URL 404
＋ **每個部署 URL 各自 404**。

🔴 **CLI 不必安裝**：`npx --yes vercel@latest` 免安裝可跑。
寫「CLI 未安裝所以做不到」之前先試一次（環境完備性紀律）。

🔴 **移除部署而非刪專案** —— 前者可逆（重新 deploy 即復原），後者不可逆。
刪專案屬破壞性操作，要先問使用者。

## 十一之二、推測的 URL 格式 vs 真連結（parse-loc.py，2026-11-04）

寫解析器時我推測 Google「分享你的位置資訊」會給 `/place/<lat>,<lng>/`，
照這個推測寫了 regex、跑了 13 個自製 fixture 全綠。使用者貼來真連結：**沒有座標**，
只有 `ftid`。13 個 fixture 驗的全是我自己想像的格式 —— 驗證器對施作器盲區同構。

```
自製 fixture 全綠          證明「regex 寫得跟我想的一樣」
真連結一次                 證明「我想的跟現實不一樣」
```

判準：**解析外部格式的程式，沒拿到至少一個真樣本之前，所有 fixture 都是 HYPOTHESIS**，
文件要標，不可寫「支援 X 格式」。真樣本到手後要做的事：① 跑；② 推翻的推測明寫「已推翻」；
③ 把真格式寫進 cache 帶日期；④ 剩下沒驗的（Apple、空曠處）繼續標 HYPOTHESIS。

附帶二：找座標的 regex 寫 `-?\d{1,2}\.\d{5,}` 配 `121.5453…` 時，會從第二個字元開始配成
`21.5453…` —— 數字看起來像、位置卻錯到印度洋。台灣經度是三位數，`\d{1,2}` 擋不住；
而且 Google 這個端點是【lng,lat】順序。**配座標一律 `\d{1,3}`，配到後用「經度 ≤180、
緯度 ≤90、落在預期國家」三條反查**，不要只看樣子像。

附帶：靜態 HTML 裡唯一的座標 `25.0249216,121.5266816` 是台北預設地圖中心（E-01 記過同一組），
不是目標。**看到一組座標先對「它是不是某個已知的預設值」**，再決定要不要信。

### 🔴 Windows 的 Python 沒有 IANA 時區庫，而 `-I` 讓裝了也讀不到

2026-11-01 實測，兩層坑疊在一起：

```
第一層   ZoneInfo("Asia/Tokyo") → ZoneInfoNotFoundError
         Linux/macOS 有 /usr/share/zoneinfo，Windows 沒有。
         要 pip install --user tzdata（348 KB 純 Python）。

第二層   裝好了，用 python -I 跑還是讀不到。
         -I 是 isolated mode，它【排除 user site-packages】。
         而環境指引要求跑外部資料時用 -I —— 兩個要求直接衝突。
```

**修法**：腳本自己把 user site-packages 補回 `sys.path`，不要靠呼叫者記得拿掉 `-I`
（靠記憶的規則就是會忘的規則）。`scripts/now.py` 的 `_ensure_tzdata()` 是實作範例，
它回傳 `ok` / `ok-via-usersite` / `fail-need-tzdata` 三種狀態給診斷用。
補完路徑要跑 `zoneinfo.reset_tzpath()` 與 `ZoneInfo.clear_cache()` ——
zoneinfo 會快取「找不到」的結果，不清就白補。

**為什麼不能用固定 UTC 偏移代替**：

```
無 DST   Asia/Tokyo +9、Asia/Taipei +8        → 固定偏移完全正確
有 DST   Australia/Sydney +10/+11             → 切換日前後差 1 小時
         Europe/London +0/+1                     日落時刻就錯 1 小時
```

日本行程用固定偏移沒事，但這個 skill 的泛用性目標含澳洲、英國 ——
那裡錯 1 小時比沒算更危險（會以為還有一小時天光）。

### 🔴 單獨驗函式會漏掉「呼叫端改寫過參數」的錯

2026-11-01 dry-run 實例，連猜兩次都錯，第三次改用二分法才定位：

```
症狀   now.py --date 2027-01-15 印出「還有 18 小時 5 分到戶外收工」
       那是拿 2027 的日落配 2026 的現在時分，數字無意義

我加的防護   if sunset.date() == now_local.date():   只有今天才印倒數
結果         防護完全沒生效，照印倒數

猜 1   __pycache__ 舊 bytecode  → 清掉，還是錯
猜 2   跑的不是這支檔案          → 驗 module.__file__、字串存在，都對
二分法 查 now_local 的【所有】賦值處
       → 找到 now.py:392  `now_local = now_local.replace(year=d.year, ...)`
       → --date 時 now_local 的年月日【已被覆寫成指定日期】
       → 所以 sunset.date() == now_local.date() 永遠成立
       → 我的判斷式從設計上就測不出差異
```

**為什麼單獨驗沒抓到**：我另外寫了一段小程式呼叫 `sun_times()` 並自己算
`datetime.now(tz)`，印出 `eq=False`（正確）。那段**沒有經過 392 行的覆寫** ——
驗證碼與施作碼走的不是同一條路，所以驗不出施作碼的錯。

**判準**：在函式裡加「跟現在比」的防護前，先查那個「現在」變數
在呼叫端有沒有被改寫過。`grep -n '<變數名>' <檔>` 看**全部**賦值處，
不要只看宣告那一行。

### 🔴 這個坑是怎麼漏掉的（方法論教訓，比坑本身重要）

```
上一輪我回報「now.py 11 條路徑 exit code 全部正確」
  → 是真的，但【我測的時候沒給 --tz】
  → 走的是「用本機時區」那條分支，繞過了整個 ZoneInfo 路徑
  → 而文件通篇寫 --tz Asia/Tokyo，那是【正式用法】
  → 正式用法從來沒成功過，而我宣稱驗過了
```
