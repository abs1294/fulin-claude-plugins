# 階段二：現場即時

適用：使用者人在當地，訊息含「現在」「我在」「剛到」「等一下」「馬上」。
特徵：**要秒回，但錯了當場就害人**。這階段的失誤密度最高（10-28～10-30 三天
佔了 D 類與 E 類一半以上）。

前置：讀 `00-總則.md`，狀態檔只讀「硬約束」「已排除」「踩過的坑」三節（求快）。

## 一、現場導航鐵則

### 1-1 先確認使用者的物理位置與交通方式

```
回答任何「怎麼走」之前，必須已知三件事：
  ① 使用者現在在哪（哪棟建築、哪層、哪個出口）
  ② 要去哪（店名 + ftid/座標）
  ③ 搭什麼線過來／要搭什麼線過去
```

三件事缺任一 → **先問，不要猜**。問一句比錯一次快。

> 使用者原話（10-29）：「你怎麼會假設？你不是知道我搭什麼路線的車子嗎？」
> 使用者原話（10-26）：「我看不懂我根本就沒有一堆日文你講的講這樣誰知道我要去哪裡搭車」

**為什麼主線是即時分享**：使用者原話「你要自己抓時間跟地點，不要一直問我」。
即時分享他開一次就不用再貼；一次性連結每次要貼；問地標要他打字。
三者精度：即時分享＝手機 GPS；一次性（Google）＝吸附到最近的店；地標＝某站某口。

🔴 **三件事不要再試**（都實測過，寫在這裡省下次的時間）：
```
Claude Code 的工具清單    沒有定位工具（查三次，+geo 回 no match）
Remote Control 訊息       不帶 GPS（FetchInboxMessage 契約無座標欄位；實際訊息也沒有）
桌機 Chrome geolocation   權限提示在瀏覽器外框，我看不到也點不到；且桌機無 GPS 晶片
```

⛔ **不算「有位置來源」的東西**（常見誤判）：

| 看到這個 | 為什麼不算 |

| 系統時區是 Asia/Taipei | 那是**電腦所在地**。人在大阪、電腦在台灣，時區照樣是 Taipei |
| 有地圖／導航工具 | 能「畫出 A 到 B」≠ 能「知道 A 在哪」 |
| 行程表寫著今天在哪 | 那是**計畫**。人會脫稿 |
| 上一則訊息的位置 | 人會動。即時分享的 age 就是為了抓這個 |

##### 瀏覽器 geolocation 實測（2026-11-02，桌機 Chrome）

使用者說「你有 GPS 可以偵測啊，我有給你 GPS 權限啊」—— 於是實跑一次。
**他確實在某處給過權限，但不是給這個執行環境的。** 權限給在哪、程式跑在哪，是兩件事。

```
navigator.permissions.query({name:'geolocation'})   → "prompt"（從未被回應過）
isSecureContext / hasGeolocationAPI                 → true / true（API 在，不是沒有）
getCurrentPosition({enableHighAccuracy:true,
                    timeout:25000, maximumAge:0})   → 25010 ms 後 code 3 TIMEOUT
再 query 一次                                        → 仍是 "prompt"
不 await 再射一次，18 秒後讀 window.__geo            → 仍 status:"pending"
                                                       docVisibility visible、hasFocus true
computer screenshot                                 → 只拍到 viewport，看不到權限泡泡
```

🔴 **TIMEOUT(3) 與 PERMISSION_DENIED(1) 必須分開看，處置完全不同**：

| code | 意思 | 要做什麼 |
|---|---|---|
| 1 PERMISSION_DENIED | 使用者按了封鎖，或政策擋掉 | 別再試，改走問話 |
| 2 POSITION_UNAVAILABLE | 權限有，但定位服務算不出位置 | 可能是 OS 定位關閉 |
| 3 TIMEOUT | **提示彈出來沒人按**，或服務在算但太慢 | 請使用者去按，不是放棄 |

被拒絕會在 1 秒內回 code 1。**跑滿整個 timeout 才回 3 = 沒人回應提示**，
不要把它講成「被拒絕」或「沒有定位能力」。

⛔ **這條路徑不可列入現場即時的自動流程。** 三個理由：

```
① 權限提示在 Chrome 外框上 —— 我的 computer 截圖只拍 viewport，看不到它
② 看不到就無法診斷 —— 提示沒彈出、彈了沒按、被設定擋掉，三者症狀都是 TIMEOUT
③ 就算成功，桌機沒有 GPS 晶片，回的是 Wi-Fi/IP 推算值
   → accuracy 可能數百 m 到數十 km，不足以算 max_leg_m
```

→ 現場即時要位置，**還是走問話那套**（問最近車站或看得到的店招）。
   瀏覽器 geolocation 只在使用者主動要求、且願意自己按提示時才用，
   用了要把 `coords.accuracy` 原樣報給他，不可只報座標。

**本機實測結果（2026-11-01，Claude Code／桌機）**：

```
① 環境變數掃 loc/geo/city/lat/lon/region/country   → 零個地理資訊
② 工具清單搜 location / GPS / coordinates /
   nearby places / current position                 → 零個定位工具
   （回的是 WebSearch、圖片裁切、字體查詢、
     Firefly 畫板、Chrome 瀏覽器操作 —— 都不回座標）
③ 系統時區 Taipei Standard Time                     → 是電腦所在地，不可用
```

→ 本 session **沒有**定位工具。走問話那套。

⛔ **不要把這條推廣成「Claude 沒有定位能力」。**
這是本機執行環境的限制，不是 Claude app 的限制 —— 兩個不同的主張，
證據不能互通。（我犯過這個錯：拿本機環境變數的證據去否定 Claude app 的 GPS。）

**為什麼要分平台**：使用者的主要使用情境是手機的 Claude app，那裡 GPS 是有的。
在有定位的平台上還問「你在哪」，正是使用者要求避免的
（原話：「你要自己抓時間跟地點，不要一直問我」）。

**已查證（Anthropic 官方 support 頁，2026-11-01）**：

```
Claude app 有 location tool
  「Access your location to provide contextual suggestions
    for nearby places and services」
  「Permission required when Claude needs to access your location」
  「supported on all Claude plans」
  🔴 Team／Enterprise 方案不能用：
     「Members of Team or Enterprise plans can't access the location tool at this time」
  會畫地圖，點了跳 Apple Maps／Google Maps 導航
```

⚠️ **HYPOTHESIS（官方沒公布，必須實測才能當事實）**：

```
定位精度是街區級還是城市級？  ← ✅ 已改道（2026-11-05）：改走即時分享，手機 GPS 精度，不再需要驗這條
  官方 support 頁只說「access your location」，沒給精度
  隱私頁只講 IP 推的粗略位置（city/region），對 GPS 精度沒有說明
  → 實測方法：在 Claude app 問「我現在在哪」，
    看回「大阪市」（城市級）還是具體街區
  → 影響：城市級不足以算 800 m 的單段步行上限

Remote Control 時手機 GPS 會不會傳到電腦端 session？
  ✅ 已驗（2026-11-04）：【不會】。兩個方向的證據：
    ① 工具契約：FetchInboxMessage 的回傳欄位只有 body / sender_display /
       slack_permalink，沒有座標欄位 —— 手機有定位也沒地方裝
    ② 本 session 使用者多則訊息實際進來，沒有任何附帶位置資料
  → 解法不是等平台補，是讓使用者貼「分享我的位置」連結，見下節第四個來源
```

🔴 **（已改道）** 上面那段是改道前的紀錄。現在精度由 live-loc.py 的 age 代理：>2 分鐘要講「N 分鐘前」，>10 分鐘當沒有。

##### 沒有定位工具時（Claude Code／桌機）

實測證據與誤判來源表在上一節，不重複。這裡只講「那怎麼辦」。

**派 subagent 或寫函數也抓不到** —— subagent 跟主對話跑在同一台機器，
它能取得的位置是**那台電腦的**位置。使用者在難波，它會回台灣。
（這條要寫出來，因為「那你寫個函數去抓啊」是很自然的下一個念頭。）

位置的合法來源只有四個，**全部來自使用者**：

| 來源 | 什麼時候算有效 | 不可以 |
|---|---|---|
| **他貼的「分享我的位置」連結** | 跑 `scripts/parse-loc.py` 回 exit 0 | exit 4 是【地點】不是【位置】，不可當起點（見下） |
| 這一則訊息裡的地標 | 站名、店名、路口、改札編號 | — |
| 使用者主動傳的照片 | 招牌、站名牌、樓層指示牌 | **不可主動要他拍照**（比打兩個字麻煩） |
| 行程表該時段（狀態檔第 3 節） | **只能當「問話時的預設值」** | **不可當事實用** |

**首選是「即時位置分享」，其次才是一次性連結**（2026-11-04 兩者都實測過）：

```
即時位置分享      使用者開一次（Google Maps → 位置資訊分享 → 1 小時或直到關閉 → 複製連結）
                 之後每次問路我自己拉最新位置，他【什麼都不用貼】
                 python scripts/live-loc.py "<連結>"  → 座標、幾秒前更新、反查地址
                 exit 3 = 分享結束或過期（>10 分鐘沒更新也算），回頭用下面的來源
一次性連結        每次要貼一下；Google 版會吸附到最近的店
                 python scripts/parse-loc.py "<連結>"
```

**多人分頭行動**：每個人從自己手機開分享、把連結傳給使用者、使用者貼給我。
`python scripts/live-loc.py --who 太太 "<連結>" --who 爸 "<連結>"` 一次讀全部，附兩兩直線距離
（算會合點時要再乘繞路係數，直線距離不是步行距離）。連結只能由本人產生，這就是同意。

🔴 即時分享的三條規矩：
```
① 出發前講一次怎麼開，並請他設「直到關閉」—— 選 1 小時的話中午就斷了
② 每次用之前看 age：>2 分鐘要講「你 N 分鐘前在○○」；>10 分鐘當作沒有位置
③ 連結與座標【不可寫進 state/ 或 cache/】—— 連結等於追蹤權限（見 config/隱私.md）
④ age 會在手機靜止時變大（實測：前 10 分鐘每 60 秒更新，之後停在同一點 15 分鐘以上）
   → 「過期」不等於「分享關了」。先問一句「你還在○○嗎」，不要直接說位置失效
```

**一次性連結** —— 手機 GPS 等級、使用者只要兩下（點藍點 → 分享 → 貼），
比打地名還快，而且精度夠算 800 m 單段步行（地標只能定到「某站某口」）。

```
使用者訊息裡有 maps.apple.com / maps.app.goo.gl / google.com/maps 連結
        │
        ▼
python scripts/parse-loc.py "<整則訊息>"
        │
   ┌────┼──────────────┬──────────────┐
 exit 0            exit 4           exit 2/3
 是位置            是【地點】        解析不到
   │                 │                │
   ▼                 ▼                ▼
當步行起點      ⛔ 不可當起點        照「沒有地標」那套問
                回問一句：           （不要叫他重貼，他可能貼了就走了）
                「你在這家門口，
                  還是要去這家？」
```

⚠️ **Google 分享的是「吸附點」不是原始 GPS**（2026-11-04 實測）：連結裡沒座標，只有最近那家店的
識別碼，腳本再去解析成座標。所以回報時要講「你在○○附近」而不是「你在這個座標」——
人在大馬路中間時吸附點可能偏到對面的店，差一條馬路就差一個路口的走法。

🔴 **「分享我的位置」vs「分享這個地點」只差一個點按，但意義相反。**
前者是他站的地方，後者是他看中的店。腳本用 URL 裡有沒有店名／place id 區分，
但判準是推測的（見 `cache/externals.md` E-10），第一次拿到真連結要對一次。

**要主動教他這個動作**（出發前講一次，現場不用重複）：
```
iPhone 地圖    點藍點 → 分享我的位置 → 拷貝 → 貼進對話
Google Maps    點藍點 → 分享你的位置資訊 → 拷貝連結 → 貼進對話
```

⛔ **不准從行程表推定位置然後直接算路線。** 人會脫稿 —— 晚起、多逛一家、臨時改點。
行程表寫 14:00 道頓堀，不代表 14:05 他在道頓堀。
（`scripts/now.py --state <行程名>` 讀得到該時段，但它自己也印這句警告。）

**位置缺漏時的決策（砍掉推測鏈）**：

```
            這一則訊息裡有明確地標嗎？
                          │
            ┌─────────────┴─────────────┐
           有                          沒有
            │                            │
            ▼                            ▼
       直接用                    ⛔ 不准從行程表推
       不做二次推測               ⛔ 不准從上一則訊息推
                                 ⛔ 不准要他拍照
                                         │
                                         ▼
                                  問 —— 但給選項，
                                  讓他一個字回完
```

問法要讓他**回一個字**，不是打地名：

```
❌ 「你現在在哪？」                     他要打字，而且可能打日文站名
❌ 「請提供你的具體位置」               更糟
✅ 「你在難波還是梅田？」                回兩個字
✅ 「我假設你還在道頓堀，對嗎？」        回「對」
   （預設值可以取自行程表 —— 當【猜測讓他確認】可以，當【事實】不行）
```

🔴 **一次只問一輪。** 問完就等，不要連問三題。他人在路上。

### 1-2 只給動線，不給說明

現場要的是「往哪走、走幾步、看到什麼轉彎」。
不要寫歷史背景、不要寫店家故事、不要寫替代方案清單。

> 使用者原話（10-29）：「我不需要解釋跟說明，我只需要動線」

格式：

```
1. 出<改札名>（<線名>的<南/北/東/西>改札）
2. 往 <方向> 走 <N> m（約 <M> 分），會看到 <地標>
3. 右轉進 <通道/建築>
4. 搭電梯到 <樓層>
5. 出電梯 <方向>，<店名> 在 <左/右> 手邊
```

每一步都要有**可目視確認的地標**。沒有地標的步驟不要寫。

### 1-4 步行一律實算，超過上限一律提替代

```
公式與參數讀 config/user-profile.md 的 B 段，本檔不給數值
每位旅伴各算一次 → 取最嚴
🔴 某人的欄位是 ❓未問 → 【不可取別人的值代入】，回報「無法計算」並問
   （處置見 config/profile-schema.md「缺欄位時怎麼辦」）
超過該旅伴的 max_leg_m → 必須主動提替代交通
```

**替代交通要盤點完整，不只是「離開這裡」的交通**：

```
園內遊園車／接駁巴士／纜車／水上巴士   ← 景點內部移動
電扶梯系統／空橋                      ← 垂直與跨棟
計程車／電車／公車                    ← 離開景點
```

🔴 **穿越大型公園：先查園內交通，再考慮改走外圍。**
原規則只寫「改走外圍道路並重算」，會把 1,642 m 改成外圍 2,000 m、
重算更久、再提計程車 —— 兩個結論都合規，而正解（園內車）仍沒進候選。

> 實際失誤：天守閣往南「走 15 分」，實際 1,642 m / 24 分，對角線穿越 105 公頃公園。
> 使用者原話（10-28）：「有孕婦耶，你怎麼會叫他走路？」
> 使用者原話（10-28）：「飯店走到東梅田站很遠耶」—— 我寫「3 分」，實際 612 m / 9 分。

### 1-5 時間資訊要自己查 —— 有工具，跑它

「現在幾點」「這班車幾分」「還有多久關門」「天黑前來不來得及」
—— 自己查，不要問使用者。

> 使用者原話（10-29）：「現在幾點了，你自己不會查嗎？」

🔴 **不要靠「我記得要去查」。跑腳本。**

```bash
python scripts/now.py --tz <當地時區> --at <座標或地標代號>
```

它一次給四件事：當地時間、日出、日落、戶外收工時刻（日落 − 緩衝）。

```
實例（大阪，查於 2026-11-01 17:30 JST）
  現在      2026-11-01 (Sun) 17:30  Asia/Tokyo
  日落      17:04
  戶外收工  16:34   （日落 - 緩衝 30 分）
            🔴 已超過戶外收工時間 56 分 —— 戶外/山道/公園行程要收
```

**日落是公式算的，不是查表** —— 任何座標、任何日期都能離線算，不依賴快取、不會過期。
（使用者 2026-11-01 決定：「帶著走」不該依賴快取。）

**準確度已對第三方驗過**，不是我自己說的：

```
真值來源   api.sunrise-sunset.org（獨立營運主體）＋ aa.usno.navy.mil（美國海軍天文台）
覆蓋       9 個測試點 × 日出日落 = 18 項
           北/南半球、赤道到高緯 64°N、分點與至點、跨 DST
結果       18/18 全部在 2 分內，最大誤差 0.97 分
重跑       python scripts/verify-sun.py       exit 0 = 全過 / 3 = 有超標
```

⚠️ **公式算不到的三件事**（要用到就得另外查）：

```
海拔        高地日落比算出來晚，每 100 m 約晚 1 分
地形遮蔽    山谷／高樓後方的「視覺天黑」更早 —— 公式永遠算不到
天氣        陰雨天的實際光線比日落時刻早暗
```

→ 這三項都讓天黑**更早**或更不確定，所以 `日落緩衝_分` 是在吸收它們。
**不要因為「公式算得準」就把緩衝調小。**

🔴 **緩衝值讀 `config/user-profile.md` 的「日落緩衝_分」**，腳本裡的 30 只是預設值。
帶長輩／幼兒要拉長（45–60）。

## 二、現場狀態不得假設

排隊人數、叫號進度、剩餘座位、售完與否、臨時休業 —— 這些是**外部即時狀態**，
查不到就標 HYPOTHESIS，**不得推測後當事實講**。

| 狀態 | 可查的方式 | 查不到時 |
|---|---|---|
| 剩餘座位 | 開訂位頁看時段 | 「我查到的訂位頁只剩 X 時段，現場候補狀況我看不到」 |
| 排隊進度 | 無（只有使用者看得到） | 直接問使用者現在號碼 |
| 臨時休業 | 店家 IG／X 最新貼文 | 標 HYPOTHESIS |
| 商品有沒有貨 | 無 | 直接說「要現場看」 |

> 實際失誤（10-26）：我對排隊進度做了錯誤假設。
> 使用者原話：「你有沒有腦袋啊？現在才剛叫號」

## 三、現場臨時換店

使用者說「這家不行／太遠／客滿」時：

```
1. 重新宣告搜尋範圍（以使用者**現在位置**為圓心，不是原計畫位置）
2. 過 Gate-H —— 過濾項**讀設定檔的旅伴條件**，不得用寫死清單
3. 三項查證 —— 平台名**讀設定檔 I 段**，不得寫死某國的平台
4. 一次給完符合的全部，附距離與分鐘數
5. 寫回狀態檔「已排除」，附原因
```

🔴 **第 2、3 步特別容易被寫死。** 現場模式求快、只讀這一節，
不會回頭讀 SKILL.md 的禁令 —— 所以在這裡再寫一次：

```
❌ 過 Gate-H（生食／座敷／電話／站立）      ← 某個人某一趟的條件
❌ 三項查證（tabelog／Google／負評）        ← 某個國家的平台
✅ 過 Gate-H（讀設定檔該旅伴的禁忌與能力）
✅ 三項查證（讀設定檔該地區的主評分站與第二來源）
```

後果：帶長輩去沒有 tabelog 的國家時，照寫死版會
**過濾掉他們最想吃的生食、再去找一個不存在的平台** ——
而檢核表會「逐項判定不適用 → 全部打勾 → 正確全綠」。

現場時間壓力下**可以只給少數幾家**，但要說「這是半徑 N m 內全部符合的，
擴大到 M m 還有 K 家要不要」—— **這不是擠牙膏，是範圍宣告**。
區別：擠牙膏是「知道卻不講」，範圍宣告是「講清楚沒查的邊界在哪」。

## 四、當地語言與名稱處理

🔴 **這一節有三條通則，與語言無關。** 原版標題是「日文處理」，
於是換英語國家時整節被跳過 —— 連帶跳過了下面第 3 條那條跟語言無關的通則。

### 4-1 字形不可讀 → 行內解釋

```
站名、線名、改札名、店名 → 行內附當地語解釋
例：南改札（minami，南側出口）／御堂筋線（Midosuji，紅色那條）
禁止做對照表
```

### 4-2 字可讀但語意不明 → 本地慣用語解釋

```
拉丁字母國家的陷阱：字看得懂，意思猜錯
例（澳洲）：BYO（可自帶酒，但要付開瓶費）／bottle shop（賣酒專門店，
            超市多半不賣酒）／servo（加油站）／flat white（咖啡種類）
            Myki（交通卡）／EFTPOS（刷卡機）
```

**發音提示**也屬這類：地名拼得出來但念不出來，問路與叫車時會卡
（例：Prahran 唸 "Pran"、Melbourne 當地唸近 "Mel-bun"）。

### 4-3 不得使用地圖 App 上找不到的名稱（與語言無關）

> 實際失誤：我叫使用者找「新快速」，Google Maps 不顯示這個名稱。
> 使用者原話（10-24）：「你這個低能兒我在Google Maps根本看不到新快速這條JR線」

查核方式：給線名／站名前，先確認它在地圖的當地語／英文界面上顯示為什麼。

⚠️ 這條在任何國家都成立（墨爾本電車官方寫 "Route 96"、
當地人說 "the 96"、火車線說 "Sandy line"）。**別因為標題是某國語言就跳過。**

## 六、現場回覆格式與分級

```
第一行：直接答（往哪走／可以吃／還是別去）
接著：動線步驟 或 數據
最後：只在會改變下一步時才加 caveat
```

### 分級（解「要秒回」與「要第三方背書」的衝突）

```
                      問題進來
                          │
                          ▼
              答錯會不會害到人？
      （醫療風險／花錢／不可逆動作如搭錯車）
                          │
          ┌───────────────┴───────────────┐
         會                              不會
          │                               │
          ▼                               ▼
    必須等                          查設定檔的「即答區」
    先回「我查一下，<N> 秒」              │
    不准先給可能錯的答案        ┌─────────┴─────────┐
          │                 即答區有             即答區沒有
          ▼                     │                   │
    完整 Gate-V 後才答           ▼                   ▼
                            直接答              即答 + 明標「未重查」
                            （已查證過）         要行動前再補查
```

**即答區**在狀態檔最前面，內容是：

```
硬條件摘要（不能吃什麼、不能坐什麼、走多慢）
已排除清單（查過不行的，直接說不行）
已訂位行程（時間／地點／訂位編號）
常用動線（飯店↔車站、車站↔主要景點，已算過的）
```

🔴 **即答區的存在就是為了讓「秒回」不必犧牲「查證」** ——
它裡面的東西是行前查過的，現場只是讀出來。

**不准寫「讓我先查一下」然後不查。** 說了就要查完才回。
