# Changelog

所有版本的變更紀錄。SKILL.md 每次調用都整份進 context，故變更紀錄放這裡不放 SKILL.md。

## 0.6.0 — 2026-09-05

- 新增 **PreToolUse hook 機械閘**（`hooks/guard-terminal-width.js`，matcher 為 Skill）：調用本 skill 時若 `config.json` 的 `terminalWidth` 不是正整數，直接 exit 2 擋下本次調用，並把「印階梯標尺→問使用者→寫回設定檔」的完整指令從 stderr 塞回給模型。**為什麼要機械閘**：規則寫在 SKILL.md 裡靠模型自覺遵守，實測會漏——上一版才把讀設定檔寫成硬性第一步，下一個 session 仍然沒讀檔就直接問使用者，而使用者早就答過了。只認 skill 名為 `what-the-fuck`（含帶 namespace 的寫法），其他 skill 一律放行，裝了本 plugin 但不用這個 skill 的人不受影響；無 stdin 或 stdin 非 JSON 時放行，閘壞掉不卡使用者。已實跑十項紅綠測（擋：null／0／負數／字串型別／設定檔不存在／帶 namespace；放行：另外三個 skill／無 stdin／非 JSON／寬度 170）。
- **修一個機械閘造成的死結**（送審時被 code-reviewer 判 Critical）：hook 是 PreToolUse，擋在 SKILL.md 載入之前——使用者若明確說「不要問了」，SKILL.md 裡「那就停、照 80 排」那條降級規則模型永遠讀不到，因為每次重新調用都被同一個 exit 2 擋住。**閘擋住了它自己的逃生門**，而 v0.5.0（純文字規則）沒有這個洞。修法：config.json 新增 `widthPromptDeclined`，設為 true 時 hook 放行；stderr 也明講這條出路，並註明「必須是使用者明確拒絕過才准設，不准因為問了很煩就自己設」。已實跑七項驗證（null+無旗標擋／null+true 放行／null+false 擋／有寬度放行／字串 "true"、數字 1、"yes" 皆不得放行）。
- 複審再補：SKILL.md 的判斷樹原本只畫「有數字／是 null」兩支，拒答並設了 `widthPromptDeclined` 的使用者會落進「是 null → 強制先問」，與降級規則矛盾。已重畫成三支（有數字／null 且未拒答／null 且已拒答），第三支直接接到「照 80 排、只用一行輕量提醒」。
- **已知取捨（使用者裁決 A，刻意不修）**：`widthPromptDeclined` 該不該設，程式面無法驗證「使用者是否真的拒絕過」——唯一守門是 SKILL.md 那句純文字禁令，也就是說這個新出口的最後一道鎖仍是模型自覺，正是本次要修的病根搬了個位置（Codex 審查指出）。考慮過「每個新 session 自動重置成 false」逼一次性重問，經使用者裁決不採用：**濫設的後果只是圖表變窄（80 寬）不會爆版，代價遠小於讓使用者每開新 session 都被問一次**。
- 複審第三輪再補：判斷樹沒畫「有數字 + 已拒答」這第四種組合。補說明時我第一版寫錯成「declined 一律優先、有數字也走第三支（照 80 排）」——**那是把 hook 的職責誤讀成排版規則**。hook 只決定「擋不擋調用」，兩種情況都放行；「用多寬排版」是 SKILL.md 的事。正確語意：兩個欄位各管各的，`widthPromptDeclined` 管「還要不要再問」、`terminalWidth` 管「排版用多寬」，所以有數字時照數字排，他拒絕的是被問、不是拒絕自己給過的值。
- 複審第四輪：上一輪我只改了 SKILL.md 被點名的那一句，**同一句錯誤說法在另外三處還留著**——config.json 的 `_widthPromptDeclined` 註解（code-reviewer 抓到）、hook 的程式碼註解與 stderr 訊息（兩軌都沒抓到，我自己掃全檔才找出來）。已全部改成「這個旗標只管還要不要再問、不管排版；terminalWidth 有數字就照數字排，只有 null 時才退回 80」，並用判準「有沒有暗示 declined=true 就一律 80」複掃全 plugin 確認無第四處。**教訓：被指出一處就只改那一處，是這個 repo 的全域紀律早就禁止的（被點名一處＝掃全文），我照樣犯了；而且掃全文是我自己做的，兩軌都沒抓到 hook 那兩處。**
- 複審第五輪，Codex 指出一個更根本的問題：**判斷樹只有三支，第四種組合（有數字＋已拒答）我是用圖底下的散文補的**——而這個 skill 第 73 行自己明訂「fallback 鏈與擇一分支要用流程圖不是清單」，等於自我違反：本該畫進圖的路徑被降級成文字。它同時指出圖上沒畫「已拒答之後使用者主動補數字該怎麼接」這條回饋線。已把樹重畫成完整四支並補上回饋線，圖下方那段與圖重複的文字補丁一併刪掉（留著就是同一件事講兩次，違反本 skill 自己的密度規則）。四支行為已用 hook 實跑逐一驗證：有數字+未拒答／有數字+已拒答／null+已拒答 三支 exit 0，只有 null+未拒答 exit 2。**教訓：用文字補丁繞過「該畫圖」的要求，比漏畫更難發現——因為看起來已經講清楚了，只有拿 skill 自己的鐵則回頭檢驗才抓得到。**
- 複審第六輪，Codex 判 BLOCK：四支樹的匯流線接錯了。**兩軌對同一條線給出相反結論**（code-reviewer 說畫對、Codex 說連錯），兩邊都宣稱用程式算過座標，所以我自己按東亞寬度逐字元量測仲裁——Codex 對：163-164 行四支垂直線在 col 14／33／64／83，但 169 行在 col 32 憑空冒出一條線接到「他主動給了數字」，視覺上緊貼第一、二支下方，讀者會以為「已經有數字的人還要繞經『給數字』這個動作」，邏輯不通。第一、二支本來就該是死路。已重畫：一二支明確標「（終點）」不再往下拉線，只留第三支（強制先問→印標尺→答了標尺）與第四支（事後改變心意主動給數字）兩條線匯入「寫回 config.json」。重畫後逐項驗證：col 32 已消失、第四支線 163→177 行完整無斷、箭頭與轉角接點正確、圍欄配對 20 個偶數。**教訓：兩軌結論相反時不能挑一邊信，要自己拿可重現的量測仲裁——這次若信了 code-reviewer 就會把錯的圖推上去。**
- 複審第七輪，Codex 指出一個文字覆蓋率缺口：「使用者事後改變心意」只有第四支（null+已拒答）寫了，**第一支（有數字+未拒答，也就是最常見的長期路徑）從頭到尾沒提「他哪天主動說要改寬度該怎麼接」**。不是「（終點）」兩字會誤導，是這個情境根本沒被寫進規則。已補一句涵蓋四支：「圖上標『（終點）』只是說這一支不需要再問他，不是說寬度從此不能改——他任何時候主動說要改寬度，一律照做並寫回 config.json」。教訓：**圖畫對了不等於規則寫全了**，圖只表達「系統怎麼判」，沒表達「使用者主動要求時怎麼辦」。
- 補一個兩軌都沒回答的問題：使用者主動要求改寬度時，`widthPromptDeclined` 要不要一併改回 false？**實測後判定不用**——hook 對「有數字+declined=true」是放行（exit 0），排版看 `terminalWidth`，而 `declined` 只擋「主動詢問」、已經有數字時本來就不會問；硬改回 false 反而可能讓他之後又被問。已把這個判斷寫進 SKILL.md，避免以後有人在這裡猶豫。
- **修一句實測推翻的事實錯誤**：SKILL.md 與 config.json 都寫著「plugin 更新可能把 terminalWidth 蓋回 null」——**錯的**。2026-09-05 實測本機 cache：`~/.claude/plugins/cache/fulin-plugins/what-the-fuck/` 底下同時存在 `0.1.0/`、`0.4.0/`、`0.5.0/` 三個獨立資料夾，使用者填在 0.5.0 的值（170）完好無損、從未被覆寫，而遠端推的仍是 null。真相是「新版是全新資料夾、config.json 就是發布時的空檔」，**不是舊值被蓋掉**。結果一樣（更新後會重問一次），但原因不同——留著錯誤說法會讓模型以為「值被覆寫了」而去別處撈舊值。兩處已改成正確敘述並附實測依據。這個錯誤是 Codex 在複審時標為 HYPOTHESIS（它無法在自己環境實測 plugin 更新機制）才促使我去實測的。
- 前一條的敘述再加保留語（Codex 複審時挖到的）：它查到舊版目錄帶 `.orphaned_at` 與 `.in_use/<pid>` 兩個管理檔，證實「按版本號分資料夾」是 Claude Code 的正式版本管理機制而非巧合（用 deliver-report 的 11 個歷史版本等交叉驗證）；但也發現孤立版本已標記約 1-2 週卻還沒被清除，**暗示存在未來可能觸發的清理機制**。我實測確認 `.orphaned_at` 標記確實存在（cc-statusline、daily-report、deliver-report 等多個 plugin 皆有）。已加一句「別依賴『舊值永遠撈得回來』，該問就問」——即使未來真有清理機制，操作結論不變，但敘述不該寫死成永久保證。
- 收尾兩處（Codex 第十輪建議，皆採納）：①把「別依賴舊值永遠撈得回來、該問就問」從舉證括號內搬到括號外，與既有的「永遠不要因為應該問過了就跳過讀檔」並列——那是行為規則不是佐證，塞在舉證括號裡會被當次要補充略讀；括號內只留實測細節。②**config.json 的 `_note` 刻意不同步這句保留語**：SKILL.md 是規則正本且每次調用整份進 context，模型執行到「讀 config.json」這步時 SKILL.md 必然已在 context 裡，`_note` 只是操作提示的複誦、不需要全文同步。此處明記，避免日後被誤會成漏改。
- hook 的說明**刻意不寫進 SKILL.md**：被擋時 stderr 已把指令塞給模型，沒被擋時那段就是廢話——SKILL.md 每次調用整份進 context，不放不必要的內容。

## 0.5.0 — 2026-09-05

- **改用與 SKILL.md 同層的 `config.json` 存寬度**（使用者裁決）。前一版寫「問到後記進 memory」有兩個問題：memory 靠模型自覺去查會漏、且綁專案換專案就失效；中途我一度提議放 `~/.claude/`，被否決——**plugin 是要發布給別人的，設定檔必須跟著 plugin 走，不能依賴外部狀態**。定案：`config.json` 隨 plugin 發布、`terminalWidth` 預設 `null`，每位使用者在自己機器上填自己的值；skill 第一步硬性讀檔，讀到 null 就強制問、拿到就寫回。plugin 更新可能把值蓋回 null，那不是錯誤、重問一次即可。**教訓：我一度卡在「會被更新覆蓋」而不敢做，但覆蓋的後果只是「再問一次」，不是災難——把小成本誤判成阻礙，就會繞遠路去做更糟的設計（把個人設定打包進發布物，正是這輪在修的缺陷）。**

## 0.4.0 — 2026-09-05

- **移除硬編的 170**（使用者指出的真缺陷）：170 是「這一位使用者的視窗寬度」，不是通用值——skill 發布給別人用時，窄視窗的人會每張圖都爛版、寬視窗的人右邊浪費一大塊，而原文還明文寫著「不要自己重測」。改為**向使用者問到為止、不設 fallback**（使用者裁決：不要保守值，猜窄了浪費版面、猜寬了整頁爛版，兩者都不能接受）：先看本 session 問過沒 → 再找 memory → 都沒有就印階梯標尺問，答案寫進 memory 供後續 session 用；
- 新增「**框字不是畫圖**」一節（使用者連續指出三次同一個病）。判準：**把框線全部刪掉、只留文字，意思有沒有變？沒變就不是圖，是加了裝飾的清單。** 附反例對照（同一組內容用框字 vs 用真流程圖）與「框線要承載資訊的五種方式」表（線代表流向／線代表分岔／位置代表層級／欄位對齊代表對應／長度代表量），以上皆非就不要加框、直接條列更好讀。同時補判準表三列（**fallback 鏈、if-else 擇一、錯誤處理分支一律用流程圖**）與誤判警告（`①②③` 看起來像表格，但「①不成立才走②」是排他關係＝流程圖）。自檢擴為十六題，新增第 9、10 題就是刪框線測試與「這些項目會同時成立嗎」。**教訓：我用「有沒有畫圖」自檢，但盲區正是「什麼才算圖」——用有盲區的尺去量，量不出盲區本身；當時我還掃過七張圖宣稱「只錯一處」，那個掃描本身就是用同一把壞尺做的。****教訓：把「查證過程的結論」（程式量不到、中文佔兩格、手排必歪）和「這位使用者的環境值」（170）混在同一段寫，就會把個人設定當成通用規則發布出去。**

## 0.2.0 — 2026-09-05

- 首次實戰即失敗：重講版比原版更長，使用者當場指出「越寫越落落長」。真因是原規則只管句子長度不管版面密度，且「寧可寫十個短句」直接鼓勵膨脹。修正：第 2 條改為「同樣的內容要佔更少版面」並列出五種該砍的無資訊贅物（**不設字數或行數上限——使用者明確否決，事實一件都不能少，砍的是廢話不是內容**）；新增第 2-1 條「能畫就別寫」把 ASCII 圖表列為主力手段，附判準表、樣板、以及**圖表左右並排**的要求（終端機很寬，右邊留白是浪費）；「講詳細」段改為「放寬長度但不放寬不准廢話」；自檢擴為八題，前四題是寬度、密度、圖表、並排。
- 補寬度基準 170 與程式排版骨架。真因：連續四次手排爛版（框線折行、橫線接點差 2 格、中文寬度沒算）。查證過程：`tput cols`／`process.stdout.columns`／PowerShell `WindowSize.Width`／P/Invoke `CreateFile("CONOUT$")`+`GetConsoleScreenBufferInfo` 四法皆量不到 TUI 真實寬度（前兩者因 stdout 被 Claude Code 導管線而失效，後兩者讀到的是中間層 cmd.exe 的 console buffer 120），最後以階梯標尺請使用者目視確認寬度。
