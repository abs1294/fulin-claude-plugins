## 一、核心原則

1. **註解寫「為什麼」，不寫「做了什麼」**。程式碼已經說明做了什麼；註解記的是程式碼看不出來的東西：為什麼這樣做、為什麼不用另一種做法、踩過什麼坑、有什麼前提或限制。判準：**刪掉這條註解，讀者從程式碼還能得到一樣的資訊嗎？**能 → 刪。
2. **沒有資訊量的註解寧可不寫**。沒有註解好過假註解——假註解讓讀的人以為有說明，其實什麼都沒講。
3. **向本專案既有的好註解靠齊**（第四節），不自成一套工整格式。工整、逐項、每個成員都有說明，正是最容易被看出不是人寫的樣子。

## 二、禁止事項

| 編號 | 禁止 | 反例 | 正解 |

| N1 | **空殼 doc 註解**：標籤或區塊在，內容是空的 | 空的 `<summary></summary>`、`/** */`、只有 `"""` 沒有字的 docstring | 內部成員：整段刪掉；對外公開、工具要求一定要有的：見第三節，改寫或局部關閉規則，不補空殼 |

## 三、編譯器或 linter 要求一定要寫 doc 註解時

有些專案開了「對外公開的成員沒有 doc 註解就警告或報錯」的設定。**這是罐頭 doc 最大的來源**：為了壓掉警告，補上 `<summary>Handle</summary>`、`/** Constructor. */` 這種空殼——警告沒了，指紋留下了。

**規則：不准補空殼。** 三種做法，依序選：

1. **改寫成有內容的說明**：一句話講這個成員的職責、邊界、前提（例：「更新負責人清單；清單要先全數通過白名單驗證，狀態守門在實體內做，已結案會拋例外」）。對外公開、別人會呼叫的成員優先走這條。
2. **工具本來就不要求的成員**（內部、私有）：空殼直接刪，不會有警告。
3. **真的沒有東西可寫**（純轉發、名稱已完全自解釋）而工具仍要求：**在那個成員或那個檔局部關閉該規則，並寫一句理由**；**不得自行整個專案關掉規則**（例：專案層的 `NoWarn`、整份 lint 設定把規則設成 off）——要整個專案關，先徵得使用者同意，同意後記進下表「局部關閉的寫法」那一欄（寫明範圍與理由），沒記在本表的整專案關閉一律當違規。

## 五、套用方式（漸進，碰到才清）

1. **新程式碼**：一律照本檔寫。
2. **改到的舊檔**：順手清掉該檔裡 N1～N9 的指紋，但不為了清而清——只動你這次改到的檔。
3. **不主動全 repo 掃改**：一次大量改註解，本身就像批次洗註解；也會讓 diff 混進大量無關改動，審查看不清這次真正改了什麼。
4. 要找指紋熱點時用下面的樣式（只列本專案用得到的語言）：

（樣式用 `grep -rnE` 跑，範圍限定本專案程式碼目錄）
