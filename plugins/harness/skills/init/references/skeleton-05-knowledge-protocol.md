# 05 — 知識迭代與反思協議

> SSOT：踩坑紀錄格式／制度檔修改權限／記憶精簡／健檢，只信本檔。修改權限：紅區。
> 目的：讓弱模型能安全地更新這套 harness，而不是讓規則熵增到不可讀。

## 1. 檔案分級制

| 分級 | 規則 | 涵蓋檔案 |
|------|------|----------|
| 🟢 綠區（可自行更新，事後在交付訊息提一句即可） | 新增/更新單一事實，不改結構 | 本專案 auto-memory 全部檔案與 `MEMORY.md` 索引行；知識容器的**新增條目**：workspace 根 `CONTEXT.md`（詞條）、`FLOWS.md`（鏈路）、`tests/Project_Detail/PROJECT.md`（QA 坑）——新增時同步在該檔 Changelog 補一行{{；其他綠區檔照專案現況補}} |
| 🟡 黃區（可更新，但必須在當次回覆中明確聲明「我改了 X，原因 Y」，讓使用者有機會否決） | 改既有內容或新增章節 | `04-delegation-templates.md` 的**新增**模板；知識容器的**既有條目修改或刪除**、檔頭收錄原則以外的結構調整{{；其他黃區檔照專案現況補}} |
| 🔴 紅區（改前必須徵得使用者同意：說明原因＋位置＋建議內容，確認後才動） | 一切修改 | workspace 根 `CLAUDE.md`；harness `README`、`02`、`03`、`05`；`04` 的既有模板內文；`.claude/settings.json`；`.claude/hooks/`（機械閘本體——放寬或拆除等於拆掉他律）；`.claude/agents/`（agent 定義）；知識容器的**檔頭收錄原則**；{{既有治理層檔案（已版控＝共用資源）}}；`~/.claude/` 全域層 |

判斷不了分級時 → 當紅區處理。

**制度檔不得記名引用 memory 條目**：memory 會重整、條目名會變，記名引用必斷鏈。教訓要入制度檔＝直接內聯事故事實（日期＋一句話後果）；需要查 memory 時寫「憑描述搜 memory」不寫條目名。反向不受限（memory 可指向制度檔）。

**改任何文件前先過三條紀律：**

- **in-flight 標記**：跨 session 或長任務**動工的第一步**＝把 memory 對應待辦條目 description 開頭加「🚧 進行中（YYYY-MM-DD）」；完成時移除。防中斷後現場不一致被誤判為棄置半成品。
- **文件最後**：完成判準未全過前，**禁止把 guide／memory／文件寫成完成式**（「已根治」「已完成」）——進行中要嘛不寫、要嘛明標 🚧。文件同步是流程的**最後一步**。
- **制度檔不記實作狀態與可數事實**：制度檔（紅區＋黃區）寫**規範、邊界、命名規律、判斷方法**；**禁止**寫實作進度（「尚未落地」「已實作」）與計數（「共 17 個」「8 個 endpoint」）。這類內容會過時且無人負責更新，過時的制度檔比沒有更糟——需要清單時寫「以程式碼現況為準」＋給查法。實作進度與查證結果歸 memory（附絕對日期）或當次回覆，不入制度檔。

## 2. 踩坑紀錄格式

一坑一檔，寫進本專案的 memory 目錄（路徑見系統提示的 Memory 節）：

```markdown
---
name: <kebab-case-slug>
description: <一行摘要，決定未來會不會被撈到——寫「症狀＋正解」不寫過程>
metadata:
  type: feedback | project | reference
---

<事實本體，≤10 行>
**Why:** <為什麼會踩、根因一句話>
**How to apply:** <下次遇到同信號時的具體動作>
```

寫入前檢查：(1) 是否已有同主題檔 → 更新舊檔不開新檔；(2) 是否 repo/git 已記錄的事 → 不寫；(3) 相對日期改絕對日期。寫完在 `MEMORY.md` 加一行索引。

**反例（通用）**：「今天修了某 bug，過程很曲折，最後解決了」——無症狀、無根因、無動作，佔索引位置還撈不到。

## 3. 精簡與抽象化觸發條件（量化）

命中任一條就在當次 session 尾聲執行精簡（綠區，不必先問）：

1. `MEMORY.md` 索引超過 **20,000 字元** → 合併同主題條目、刪除已失效條目（先驗證失效：檔案／功能已不存在）。**判準是字元不是行**：索引有載入上限，超過的部分是**靜默截斷**（後段條目整個 session 沒載入、不會有任何提示）；中文條目行長差異大，用行數當指標會在「行數還在線內」時就已經超限。查法：`python -c "print(len(open(r'<memory 目錄>/MEMORY.md',encoding='utf-8').read()))"`。
2. 同一主題累積 **≥4 個 memory 檔** → 合併成一個「<主題>總則」檔，原檔刪除，索引更新。**寫入紀律（防事後才合併）**：新記憶先找既有總則檔加一節，掛不上才新開檔——索引膨脹的主因是逐坑新開檔。
3. memory 檔內文超過 **30 行** → 抽象化：把過程敘事壓成「症狀→根因→動作」三段（完成形狀＝三段各 1～5 行、全檔 ≤15 行）。判別法：**刪掉這段，下次遇到同一個坑會不會多繞路？**不會就刪。⚠ 三樣東西再長也不砍：可重現的指令／路徑、精確的錯誤訊息原文（憑印象改寫會搜不到）、「為什麼不能用另一種做法」的反例。
4. 發現某條 memory 與現況矛盾 → 立即更新或刪除，**不留過時條目**（過時記憶比沒記憶更毒）。
5. **「已修／已推翻」類 memory 必帶失效條件**：frontmatter 加 `retire_when: <修復的 commit hash｜推翻它的事實一句話>`，健檢時條件已成立的條目退場。

## 4. Harness 檔案變更紀錄

紅區/黃區檔案被批准修改後，在該檔**檔尾** changelog 節加一行：

```
## Changelog
- <YYYY-MM-DD> <改了什麼一句話>（<經使用者同意｜黃區自主>）
```

只寫現行狀態的變更事實，不寫心路歷程。

## 5. 定期健檢（防制度腐化）

觸發時機：使用者說「harness 健檢」，或任何 session 發現距上次健檢**超過 30 天**（看本檔 changelog 最後日期）時主動提議。

檢查項目：

```
□ workspace 根 CLAUDE.md 是否長胖？（>80 行即異常，找出可抽離的段落提案）
□ CLAUDE.md 路由表與 harness 內引用的路徑是否全部仍存在？（逐條 ls 驗證{{，含既有治理層引用}}）
□ MEMORY.md 是否超過 20,000 字元？（**看字元不看行數**，查法見 §3.1）
□ memory 退場掃描：`grep -l "^retire_when:" <memory>/*.md` 逐檔判條件是否已成立，成立即退場並刪索引行（§3.5）
□ 03 矩陣 B 的本專案驗證指令是否仍與 repo 現況相符？（實查 build 腳本與目錄結構）
□ 04 模板是否被實際使用？（抽查近期派工有無三件套——沒有就代表模板腐化，回報使用者）
□ 隔離驗證是否形同虛設？（抽查驗證回報是否有證據行號，全是無證據 PASS 即腐化）
□ 機械閘還活著嗎？在 `.claude/hooks/` 跑 `node probe-hooks.js`：每支 hook 的 cases 兩個方向都要全數符合預期（該擋的擋、該放的放——只驗「會擋」會漏掉「解析壞掉、全部誤擋」這種失效；機械保證的機械也會鏽）。有 hook 缺 cases 會被列為失敗——新加的 hook 要一併補 cases。本期若改過某支 hook 的填空區常數，先確認對應 cases 同步改了。有裝規則引擎（`guard-risky-command`／`guard-test-preconditions`）時，probe 開頭那行要是「語法樹路徑（Bash 與 PowerShell 解析器都已載入）」；出現「⚠ 語法解析器沒有完整載入」＝解析器沒裝或載入失敗，引擎正退回正則判法——在 `.claude/hooks/` 跑 `npm ci` 補回
□ 熔斷清單與機械閘對得上嗎？CLAUDE.md 熔斷清單（與 03 C2）的每一項，在 `guard-risky-command.js`／`guard-test-preconditions.js` 都找得到對應規則，或寫明為什麼只能停在文字；本期新增的熔斷項有沒有補規則
□ CONTEXT.md 斷鏈與新詞補課（①詞條內引用的詞是否都已定義 ②本期新敲定的詞有沒有進來——對照近期 memory 新增條目抽查）
□ CONTEXT.md 與 memory 分工有無漂移？（詞彙表混入實作事實／memory 混入純詞彙）
□ FLOWS.md 新鏈補課（對照本期 memory 新增的事故條目：涉及跨模組鏈路者，有無進 FLOWS.md——收錄原則見該檔檔頭）
□ tests/Project_Detail/PROJECT.md 反映實況嗎？（對照本期 QA 類 memory 新增條目：新操作坑／測試設計知識有無進來）
□ 03 條款中「本專案不適用」的條款，前提是否已改變？（例：當初無 UI、現在有了——該條要改回適用）
{{若有既有治理層加：□ {{治理層入口檔}}是否改版？（其載入規則／門檻流程變動時，04 的必讀清單規則與流程編排節要重對齊）}}
```

環境層（這幾項失效時不會擋下任何動作，只在 transcript 留一則 hook error 通知或退回較陽春的做法，工作照常進行，很容易被忽略，所以要主動查）：

```
□ hook 接線對得上嗎？讀 {{settings 檔路徑}} 的 `hooks` 區，每條 `command` 指向的 `.js` 檔都要真的存在——`.claude/hooks/` 改過檔名或搬過目錄時 settings 不會跟著改，node 找不到檔案會以非 0 結束，Claude Code 把它當成非阻擋錯誤繼續往下做，那支 hook 從此等於沒裝；每支 hook 檔頭「接線」註解的事件與 matcher 也要和 settings 一致
□ hook 的執行環境：在專案根目錄跑 `node --version` 要成功（hook 全靠 node 執行）
{{若有裝壓縮交接 hook（形狀目錄第 26 列）加：□ 交接信真的有寫出來嗎？看最近幾次壓縮的流水帳（`~/.claude/projects/<本專案>/<session>/compact-snapshots/compact-log.jsonl` 每行的 `handoff.ok`）：連續 false 就看同一行的 `handoff.error`——找不到 claude（在專案根目錄跑 `claude --version` 確認）、逾時（`CHILD_TIMEOUT` 太小或對話太長），或 `disabled`（有人設了 `COMPACT_HANDOFF_OFF=1`）。交接信寫不出來時壓縮照常進行，壓縮後注入的會是標明「交接信未產生」的快照清單，一次看到容易當成偶發，要看流水帳才知道是不是每次都失敗}}
{{若有裝壓縮交接 hook（形狀目錄第 26 列）加：□ 壓縮交接的逾時設定還對得上嗎？settings 裡 PreCompact 那條的 `timeout`（單位秒）換算成毫秒後要大於 `compact-handoff.js` 的 `CHILD_TIMEOUT`（單位毫秒），否則交接信寫到一半整支 hook 被中止；`compact-reinject.js` 的 SessionStart matcher 要是 `compact`、`resume-stale-reminder.js` 的要是 `resume`}}
```

健檢輸出一頁報告，異常項附建議修法；修法本身依 §1 分級執行。

## 6. 升格協議（規則從事故長出來）

本實例帶的是開發流程骨幹，不含任何專案的事故條款。本專案踩到新坑時：

1. 先寫 memory（§2 格式，綠區）。
2. 同類坑**第 2 次**出現、或單次後果嚴重（返工 >1 天／污染交付物）→ 提議升格為 harness 條款（紅區流程：說明原因＋位置＋建議內容，經使用者同意）。
3. 升格時遵守 §1 三條紀律；禁止把別的專案的事故條款整批預載進來——沒付過學費的規則只是 token 稅。
4. **「一定要落地」的條款要配機械閘**：skill／制度檔寫「必須」是自律，AI 會繞；只有 hook 是他律。升格時問一句「這條被跳過時，有沒有東西會擋下來？」——沒有且後果嚴重，就同時提議一支 hook（fail-open：hook 故障時放行但 loud 報錯，不得變成擋路石）。先查 harness plugin 的 hook 形狀目錄（`skills/init/references/hook-catalog.md`）有沒有同形狀的範本或規則引擎可以直接用——多數「執行某類指令前先擋」「跑測試前先驗環境」只要往 `guard-risky-command.js`／`guard-test-preconditions.js` 加一條規則，不必新寫 hook。新 hook 或新規則都要補 `cases/` 兩向案例，`node probe-hooks.js` 全綠才算升格完成。
5. **分流**：本實例 init 時已帶的是**開發流程骨幹**（行為紀律＋可參數化的判準）；綁定特定事故的條款（某個第三方套件的坑、某種環境配置的坑）不在骨架裡——那類條款從本專案 memory 長出來，或日後由 harness plugin 規劃中的 `/harness:review`（尚未提供）對照其他實例提議，經本節流程升格。
