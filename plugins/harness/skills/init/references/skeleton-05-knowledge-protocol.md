# 05 — 知識迭代與反思協議

> SSOT：踩坑紀錄格式／制度檔修改權限／記憶精簡／健檢，只信本檔。修改權限：紅區。
> 目的：讓弱模型能安全地更新這套 harness，而不是讓規則熵增到不可讀。

## 1. 檔案分級制

| 分級 | 規則 | 涵蓋檔案 |
|------|------|----------|
| 🟢 綠區（可自行更新，事後在交付訊息提一句即可） | 新增/更新單一事實，不改結構 | 本專案 auto-memory 全部檔案與 `MEMORY.md` 索引行；知識容器的**新增條目**：workspace 根 `CONTEXT.md`（詞條）、`FLOWS.md`（鏈路）、`tests/Project_Detail/PROJECT.md`（QA 坑）——新增時同步在該檔的變更紀錄補一行（落點見 §4）{{；其他綠區檔照專案現況補}} |
| 🟡 黃區（可更新，但必須在當次回覆中明確聲明「我改了 X，原因 Y」，讓使用者有機會否決） | 改既有內容或新增章節 | `04-delegation-templates.md` 的**新增**模板；`06-handover-letter.md`（建立後）附錄「未完成事項交接區」；知識容器的**既有條目修改或刪除**、檔頭收錄原則以外的結構調整；workspace 根 `CLAUDE.md` §0 專案概要的**業務流程狀態與目前進度**{{；其他黃區檔照專案現況補}} |
| 🔴 紅區（改前必須徵得使用者同意：說明原因＋位置＋建議內容，確認後才動） | 一切修改 | workspace 根 `CLAUDE.md`（§0 的流程狀態與進度屬黃區；§0 外部系統的正式／測試分類屬紅區，只有使用者能改）；harness `README`、`01`（建立後）、`02`、`03`、`05`、`06`（建立後，附錄除外）；`04` 的既有模板內文；`.claude/settings.json`；`.claude/hooks/`（機械閘本體——放寬或拆除等於拆掉他律）；`.claude/agents/`（agent 定義）；知識容器的**檔頭收錄原則**；{{既有治理層檔案（已版控＝共用資源）}}；`~/.claude/` 全域層 |

判斷不了分級時 → 當紅區處理。

**制度檔不得記名引用 memory 條目**：memory 會重整、條目名會變，記名引用必斷鏈。教訓要入制度檔＝直接內聯事故事實（日期＋一句話後果）；需要查 memory 時寫「憑描述搜 memory」不寫條目名。反向不受限（memory 可指向制度檔）。

**改任何文件前先過三條紀律：**

- **in-flight 標記**：跨 session 或長任務**動工的第一步**＝把 memory 對應待辦條目 description 開頭加「🚧 進行中（YYYY-MM-DD）」；完成時移除。防中斷後現場不一致被誤判為棄置半成品。
- **文件最後**：完成判準未全過前，**禁止把 guide／memory／文件寫成完成式**（「已根治」「已完成」）——進行中要嘛不寫、要嘛明標 🚧。文件同步是流程的**最後一步**。
- **制度檔不記實作狀態與可數事實**：制度檔（紅區＋黃區）寫**規範、邊界、命名規律、判斷方法**；**禁止**寫實作進度（「尚未落地」「已實作」）與計數（「共 17 個」「8 個 endpoint」）。這類內容會過時且無人負責更新，過時的制度檔比沒有更糟——需要清單時寫「以程式碼現況為準」＋給查法。實作進度與查證結果歸 memory（附絕對日期）或當次回覆，不入制度檔。**唯一例外**：workspace 根 `CLAUDE.md` §0 專案概要的業務流程狀態、外部系統數與目前進度——它是每次開工的第一份必讀，所以允許，但有人負責更新：每次完成一條業務流程的需求，收尾時照程式碼現況更新 §0 的狀態與日期（黃區，當次講明）；定期健檢時 §0 日期超過 30 天就對程式碼重查一次。

## 1.5 產物存放紀律（制度層不放一次性產物）

`.claude/` 只放 Claude Code 的機制與本工作流的制度層，不放一次性產物。寫新檔前先對這張表決定落點：

| 放什麼 | 位置 |
|---|---|
| commands／skills／hooks／agents／scripts／settings | `.claude/`（Claude Code 機制） |
| harness 制度層與它的變更紀錄 | `.claude/harness/` |
| 知識容器 | workspace 根 `CONTEXT.md`、`FLOWS.md`；`tests/Project_Detail/PROJECT.md` |
| 設計文件、規格、架構決策 | {{本專案的設計文件目錄；Phase 1 沒查到就請使用者指定一個}} |
| 交接文件、測試計畫、QA 報告（還有人在用的） | {{本專案的產物目錄}} |
| 已無人引用的歷史產物 | {{本專案的歸檔目錄，例：<產物目錄>/archive/}} |

**判準**：這份文件**換一個專案還需要嗎**？需要 → 機制或制度層；不需要 → 一次性產物，進產物目錄。
另一個問法：檔名有沒有**日期戳或案號**（`<主題>-YYYYMMDD.md`、`<案號>-<主題>.md`）？有 → 幾乎必然是一次性產物。

**歸檔前先查引用**（沒人引用的才進歸檔目錄，還有人引用的留在產物目錄第一層）：掃全 repo 看還有沒有檔案提到它的檔名，零引用才算沒人用。搬完必須改寫所有引用路徑，並確認舊路徑殘留為 0——**搬了不改引用＝製造說謊的地圖**，比不搬更糟。

{{若有裝 guard-claude-dir-hygiene（形狀目錄第 8 列）加：機械閘：`.claude/hooks/guard-claude-dir-hygiene.js`（PreToolUse，在 `.claude/` 底下非機制目錄新建檔時擋下並提示落點）。它只擋最明顯的形態（路徑特徵），完整判準靠本節。}}

## 2. 踩坑紀錄格式

一坑一檔，寫進本專案的 memory 目錄（路徑見系統提示的 Memory 節）：

```markdown
---
name: <kebab-case-slug>
description: <一行摘要，決定未來會不會被撈到——寫「症狀＋正解」不寫過程>
metadata:
  type: feedback | project | reference
---

<事實本體，≤10 行>
**Why:** <為什麼會踩、根因一句話>
**How to apply:** <下次遇到同信號時的具體動作>
```

寫入前檢查：(1) 是否已有同主題檔 → 更新舊檔不開新檔；(2) 是否 repo/git 已記錄的事 → 不寫；(3) 相對日期改絕對日期。寫完在 `MEMORY.md` 加一行索引。

**索引行標星等**（寫在索引行開頭；`MEMORY.md` 開頭放一行判準說明）：
- ⭐⭐⭐＝使用者明文裁定的規則
- ⭐⭐＝踩到會**靜默失效或誤判**（沒有錯誤訊息、看起來像別的問題）
- ⭐＝一般坑，有明確錯誤訊息可循
- 無星＝冷知識或已結案

星等決定精簡時先動誰（§3）：索引要瘦身或分層下沉時，只動 ⭐ 與無星；⭐⭐ 以上原樣保留——它們不是「最常用」，而是「沒記住就會出事而且查不出來」。

**反例（通用）**：「今天修了某 bug，過程很曲折，最後解決了」——無症狀、無根因、無動作，佔索引位置還撈不到。

## 3. 精簡與抽象化觸發條件（量化）

命中任一條就在當次 session 尾聲執行精簡（綠區，不必先問）：

1. `MEMORY.md` 索引超過 **20,000 字元** → 合併同主題條目、刪除已失效條目（先驗證失效：檔案／功能已不存在）；還超過就把 ⭐ 與無星的條目下沉到主題總則檔（索引只留總則那一行），⭐⭐ 以上不動（§2 星等）。**判準是字元不是行**：索引有載入上限，超過的部分是**靜默截斷**（後段條目整個 session 沒載入、不會有任何提示）；中文條目行長差異大，用行數當指標會在「行數還在線內」時就已經超限。查法：`python -c "print(len(open(r'<memory 目錄>/MEMORY.md',encoding='utf-8').read()))"`。
2. 同一主題累積 **≥4 個 memory 檔** → 合併成一個「<主題>總則」檔，原檔刪除，索引更新。**寫入紀律（防事後才合併）**：新記憶先找既有總則檔加一節，掛不上才新開檔——索引膨脹的主因是逐坑新開檔。
3. memory 檔內文超過 **30 行** → 抽象化：把過程敘事壓成「症狀→根因→動作」三段（完成形狀＝三段各 1～5 行、全檔 ≤15 行）。**總則檔（第 2 條合併出來的）豁免本條的 30 行門檻與全檔上限，改為「新合併進來的節 ≤15 行」**——第 2 條要求同主題合併成總則檔，總則檔必然超過 15 行，不豁免兩條就互斥；合併時逐節壓成三段，已經在總則檔裡的舊節不必回頭重寫。判別法：**刪掉這段，下次遇到同一個坑會不會多繞路？**不會就刪。⚠ 三樣東西再長也不砍：可重現的指令／路徑、精確的錯誤訊息原文（憑印象改寫會搜不到）、「為什麼不能用另一種做法」的反例。
4. 發現某條 memory 與現況矛盾 → 立即更新或刪除，**不留過時條目**（過時記憶比沒記憶更毒）。
5. **「已修／已推翻」類 memory 必帶失效條件**：frontmatter 加 `retire_when: <修復的 commit hash｜推翻它的事實一句話>`，健檢時條件已成立的條目退場。

## 4. 變更紀錄（寫在獨立的紀錄檔，不寫在指令檔裡）

紅區／黃區檔案被批准修改後（以及知識容器新增條目時），記一行變更紀錄。**紀錄不寫在被改的檔裡**，寫在獨立的變更紀錄檔：

| 被改的檔 | 紀錄寫在 | 分節 |
|---|---|---|
| `.claude/harness/` 底下的檔（README、01～06） | `.claude/harness/CHANGELOG.md` | 依檔名分節，例：`## 05-knowledge-protocol.md` |
| `.claude/agents/` 底下的 agent 定義 | `.claude/agents/CHANGELOG.md` | 依檔名分節，例：`## qa-engineer.md` |
| workspace 根的檔（`CLAUDE.md`、`CONTEXT.md`、`FLOWS.md`） | 同目錄的 `<主檔名>.changelog.md`（例：`CONTEXT.changelog.md`） | 不分節 |
| 其他目錄的知識容器（`tests/Project_Detail/PROJECT.md`） | 同目錄的 `CHANGELOG.md` | 依檔名分節，例：`## PROJECT.md` |

格式（一行一筆，新的寫在該節最上面或最下面照檔案原本的慣例，不混用）：

```
- <YYYY-MM-DD> <改了什麼一句話>（<經使用者同意｜黃區自主｜綠區>）
```

（「綠區」只用在知識容器的新增條目；健檢紀錄另有專用寫法，見 §5。）

被改的檔檔尾只留一行指標：`變更紀錄見 <紀錄檔相對路徑>`，不放 changelog 節。

**為什麼拆出去**：制度檔、agent 定義、CLAUDE.md 這類指令檔每次載入都整份進模型 context，檔尾的 changelog 節只會越長越胖、擠掉可用的視窗，而它對當下要做的事沒有用。獨立的紀錄檔只在需要查歷史時才讀。

只寫現行狀態的變更事實，不寫「原本 X 後來改成 Y」的心路歷程。新增一個要記紀錄的檔（例：建立 01、06）時，在對應紀錄檔加一個同名的節。

## 5. 定期健檢（防制度腐化）

觸發時機：使用者說「harness 健檢」，或任何 session 發現距上次健檢**超過 30 天**（看 `.claude/harness/CHANGELOG.md` 的 `## 05-knowledge-protocol.md` 節裡帶【健檢執行】標記、**日期最大**的那一筆——不是節裡最後一筆；改制度的紀錄不帶這個標記、不算；`health-check-reminder.js` 會在開機時自動算）時主動提議。

**用 `/harness:review` 執行，三軌**：
- **軌一 制度**：review 從實際的對話紀錄、subagent 紀錄、知識筆記抽證據（要實際試跑自動檢查時會先問使用者，同意才跑），並派 subagent 把下面清單（含 §5.1 稽核工具表）逐項跑完——每項附實際輸出，清單裡寫了預期結果的項目照描述實跑、對照；對不上時先查證是哪一邊錯——找得到「行為是刻意改的」證據才算清單過時、更新描述，找不到就當故障處理。
- **軌二 `/doctor`**：工具鏈健康（安裝、版本、沒在用的連接器與 skill、慢 hook、常駐 context）。
- **軌三 `/insights`**：跨 session 的使用行為與卡關點；它的建議會逐條對照現有規則，分「已有規則只是沒照做（改做自動檢查）／真的沒有（補規則）／不屬於本專案（指出該補在哪）」。

軌二、軌三是內建指令，模型叫不動：開跑時請使用者在提示列輸入，不准靜默略過；沒跑要在報告寫明。三軌各看一層——軌一抓得到「工具給錯答案卻不報錯」，軌三抓得到「規則寫了卻沒人照做」，單軌都有盲區。

review 會把修正分兩批：可逆的（重建索引、memory 退場、更新已查證過時的清單描述、修明顯的 hook bug…）列成一批，使用者一次核可後當場修並逐項重跑驗證；改規則內容的、不可逆的仍照 §1 分級逐項問。最後問要不要在 `.claude/harness/CHANGELOG.md` 的 `## 05-knowledge-protocol.md` 節補一行健檢紀錄（寫法 `- YYYY-MM-DD 【健檢執行】/harness:review：<一句話結論>`，標記緊接在日期後面；提醒 hook 只認這個標記重新起算。手動跑健檢的也照這個寫法記；改健檢清單、改制度的紀錄不准用這個標記）。沒裝 harness plugin 的環境三軌都手動做。

**【使用者親自看】**：清單項目後面加這個標記，review 會把它放在報告最前面、只給資料不下結論——用在 AI 判斷不了、或使用者想自己盯的項目（例：某個門檻要不要調）。使用者說「健檢時提醒我看 X」時，就把 X 加進清單並標上它。

檢查項目：

```
□ CLAUDE.md §0 專案概要的日期是否超過 30 天？超過就對程式碼重查流程狀態與進度，有差異照黃區更新
□ workspace 根 CLAUDE.md 是否長胖？（§0 專案概要以外 >80 行即異常，找出可抽離的段落提案；§0 不計入、不提議抽離——它的用途就是每次開工先讀）
□ CLAUDE.md 路由表與 harness 內引用的路徑是否全部仍存在？（逐條 ls 驗證{{，含既有治理層引用}}）
□ MEMORY.md 是否超過 20,000 字元？（**看字元不看行數**，查法見 §3.1）
□ memory 退場掃描：`grep -l "^retire_when:" <memory>/*.md` 逐檔判條件是否已成立，成立即退場並刪索引行（§3.5）
```

## 6. 升格協議（規則從事故長出來）

本實例帶的是開發流程骨幹，不含任何專案的事故條款。本專案踩到新坑時：

1. 先寫 memory（§2 格式，綠區）。
2. 同類坑**第 2 次**出現、或單次後果嚴重（返工 >1 天／污染交付物）→ 提議升格為 harness 條款（紅區流程：說明原因＋位置＋建議內容，經使用者同意）。
3. 升格時遵守 §1 三條紀律；禁止把別的專案的事故條款整批預載進來——沒付過學費的規則只是 token 稅。本專案**自己原有規矩**裡的經驗不算「別的專案」：init 的參考模式已經用語意挑過一次、讓使用者選過要不要升格（03 矩陣 D），並另派 subagent 審查有沒有漏帶；之後在舊文件裡再翻到的，照本節一條一條提議升格。
4. **「一定要落地」的條款要配機械閘**：skill／制度檔寫「必須」是自律，AI 會繞；只有 hook 是他律。升格時問一句「這條被跳過時，有沒有東西會擋下來？」——沒有且後果嚴重，就同時提議一支 hook（fail-open：hook 故障時放行但 loud 報錯，不得變成擋路石）。先查 harness plugin 的 hook 形狀目錄（`skills/init/references/hook-catalog.md`）有沒有同形狀的範本或規則引擎可以直接用——多數「執行某類指令前先擋」「跑測試前先驗環境」只要往 `guard-risky-command.js`／`guard-test-preconditions.js` 加一條規則，不必新寫 hook。新 hook 或新規則都要補 `cases/` 兩向案例，`node probe-hooks.js` 全綠才算升格完成。
5. **分流**：本實例 init 時已帶的是**開發流程骨幹**（行為紀律＋可參數化的判準）；綁定特定事故的條款（某個第三方套件的坑、某種環境配置的坑）不在骨架裡——那類條款從本專案 memory 長出來，或由 `/harness:review` 健檢時從該實例的紀錄列進提案，同一件事反覆出錯就提升格，經本節流程升格。
