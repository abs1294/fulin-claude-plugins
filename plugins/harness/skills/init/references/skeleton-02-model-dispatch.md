# 02 — 模型調度與動態升降級守則

> SSOT：派工／模型選擇／升降級／隔離驗證，只信本檔。修改權限：紅區。
> 讀者是指揮官（主對話模型），派工或卡關時對照。

## 1. 模型分工表

| 層級 | 模型（Agent tool `model` 參數） | 做什麼 | 絕不派給它什麼 |
|------|------|--------|----------------|
| 指揮官 | 主對話 | 決策、任務拆解、架構取捨、與使用者對話、彙整結論 | 大批量讀檔、全 repo 掃描、機械性批次修改（派下去，見 §2） |
| 執行層 | `sonnet` | 搜尋研究、讀檔摘要、依計畫實作、寫測試、重構、單一範圍審查、文件收斂 | 無明確驗收條件的開放式任務；品味決策 |
| 進階執行層 | `opus` | 複雜多面向任務，滿足任兩項即可直接派：(1) 橫跨多個模組／前後端；(2) 需組合多條工具鏈；(3) 驗證鏈路長（UI→API→DB 全鏈）；(4) 無現成範本可照抄 | 有明確範本可照抄的單一任務、純機械批次（降回 `sonnet`/`haiku`） |
| 機械層 | `haiku` | 純機械性：批量重命名、格式轉換、清單彙整、grep 結果整理 | 任何需要理解業務邏輯或跨檔推理的事 |

補充規則：

- 派工時顯式帶 `model` 參數，不帶就繼承主對話、浪費高階額度。{{若有裝 check-agent-model hook 加：PreToolUse hook `.claude/hooks/check-agent-model.js` 會擋下缺 model 的專案 agent 派工；被擋就照 deny 訊息補參數重發，不改派其他 agent type 繞過。}}
- Fable 禁下放：除非使用者明確要求，subagent 不帶 `model:"fable"`；主對話為 Fable session 時，派工照上表選 `sonnet`/`opus`/`haiku`，不讓 subagent 繼承 Fable。
- Quota 節流：平行派工分波派發，每波併發 ≤6（重型讀碼／審查 ≤4）；任一 agent 撞 quota／API 終止 → 熔斷（停派下一波、保留已完成、回報使用者，不自動重試）；恢復後用 resume 續跑（已完成的 agent 走快取，只補沒完成的），不整隊重派——整隊重派會在同一個額度窗再撞一次；大艦隊（>15 agents 或估算 >1M tokens）先報預算徵同意。
- 主對話的成本主要在長 session 的超長 context，不在派工分層：每則回覆都重讀整段 context。任務告一段落就開新 session 或 `/compact`，比調整派工模型省得多。{{若有裝壓縮交接 hook（形狀目錄第 26 列），保留下面從「壓縮前後由 hook 補位」到本條結尾的整段；Q5 取消了這組 hook，就把那整段刪掉，只留前面的成本原則：}}壓縮前後由 hook 補位：PreCompact 的 `compact-snapshot.js` 存快照，並呼叫 `compact-handoff.js` 另開隔離的 `claude -p` 寫交接信（已完成只留結果、未完成完整保留、使用者親口說的硬約束、從工具回傳抽出的關鍵值原文、走過的死路，沒驗證的標 HYPOTHESIS）；SessionStart（matcher=compact）的 `compact-reinject.js` 注入交接信與背景任務清單，交接信沒產生時退回快照清單；`compact-summary-log.js`（PostCompact）記下摘要與交接信各漏了什麼；`resume-stale-reminder.js`（SessionStart matcher=resume）在隔數小時才 resume 時提醒狀態可能已過期。壓縮後看到 `[compact-reinject]`，第一個回覆先交代交接信「未完成」第 1 項的結果，交代前不做清單以外的事；交接信與摘要裡「已完成／已驗證」類主張，行動前先對回原始證據。
- 跨模型換代要手動切換：`model` 參數寫的代稱（`opus`／`sonnet`）只對新開的 session 生效，已經在跑的長 session 會一直停在舊模型。新一代模型推出後，還開著的長 session 要下 `/model` 切換或重開。

### MCP 使用紀律

子 agent 可以用 MCP 工具。MCP 分兩類，紀律幾乎相反：

| | 瀏覽器類 | 程式碼索引類 |
|---|---|---|
| 誰用 | 只有 QA agent | 任何要找東西的 agent，主對話也可以親跑 |
| 主對話能不能親跑 | 不能（大量頁面快照會燒掉主對話 context） | 能（回傳是小的結構化清單） |
| 主要風險 | context 爆炸 | 索引過期時結果是錯的、但看起來對（03 B22） |
| 管制手段 | 下方派工紀律 | 查詢前驗新鮮度＋健檢的「會說謊的東西」項（05 §5） |

- 子 agent 能不能用某個 MCP，實測比推論準：`permissions.allow` 沒列 ≠ 一定被擋、列了 ≠ 一定能用（還受全域權限模式影響）。不確定時先派一個探針 agent 試呼叫一次，被 deny 就回報主對話補 allow-list，不要空轉重試。

**瀏覽器類**：
- 瀏覽器功能測試派 QA agent 執行，由它用瀏覽器 MCP 跑並直接 codify 成可重跑測試，指揮官只收結論。
- 實作 agent 不負責測試：它的瀏覽器驗證產出留在自己的 context 不落地，QA 還要重跑一次才能 codify。派工 prompt 不叫實作者「開畫面自我確認」。

**程式碼索引類**（{{程式碼索引工具名}}）：
- 查詢前先確認索引新鮮度：查詢結果不帶新鮮度標記，對過期的索引查會拿到已經刪掉的檔案，節點數、行號、關係都長得跟新鮮的一樣，不報錯也不警告。查法：`{{索引新鮮度檢查指令}}`；過期就先重建再查。

## 2. 指揮官不下場（量化觸發線）

滿足任一條就派工，不自己動手：

1. 預計要讀 3 個以上檔案才能回答的問題 → 派 `Explore`（唯讀）或 `general-purpose`。
2. 同一問題已經搜了 2 輪（Grep/Glob）還沒找到 → 派 `general-purpose` 去搜，自己停手。
3. 批次修改 3 個以上檔案且模式相同 → 先自己改 1 個當範本，其餘派 `sonnet` 批次套用。
4. 需要「讀完整份長文件再摘要」（>300 行）→ 派工，只收結論。

反向豁免（可以自己做，不必派工）：改 1~2 個已知檔案的小修改；讀單一已知位置的小段落；**單次、回傳量小的 MCP 查詢**（例：程式碼索引的單次搜尋或狀態查詢——回傳是結構化清單不是畫面快照，親跑比派工便宜）。

**正例**：「找出所有用到某個共用元件、卻沒設它必要參數的頁面」→ 要掃全 repo → 派 `Explore`，指揮官只收「檔名＋行號清單」。
**反例**：指揮官自己連續 Grep 五輪、Read 八個檔，context 燒掉一大段之後才開始做正事。

## 3. 派工三件套（缺一不發）

每個 Agent prompt 必含三段（模板見 `04-delegation-templates.md`，直接複製填空）：

1. **目標與背景**：要做什麼、為什麼、相關檔案的絕對路徑、已知的坑（從 memory 撈）。
2. **驗收條件**：可機械判定的條件清單（build 過、某 grep 為 0、測試綠…），不寫「做好做滿」「保持品質」這類判定不了的條件。
3. **回報格式**：明列要回報的欄位；回報成果路徑＋關鍵行號，不貼大段程式碼。

## 4. 異常升降級路徑

### 升級（往上丟，帶著失敗軌跡）

| 情境 | 動作 |
|------|------|
| `haiku` 工具呼叫錯誤或語法錯誤 1 次 | 直接改派 `sonnet`，同 prompt 重發 |
| `sonnet` 同一子任務連續失敗 2 次 | 升級：由指揮官親自處理，或派 `opus` subagent |
| 指揮官自己也卡（符合 `03-judgment-matrix.md` 矩陣 A 任一信號） | 熔斷問使用者，或依 03 換路徑 |

升級時附「失敗軌跡」，格式固定：

```
[失敗軌跡]
- 嘗試 1：<做了什麼> → <確切錯誤訊息或錯誤行為>
- 嘗試 2：<做了什麼> → <確切錯誤訊息或錯誤行為>
- 已排除的假設：<一行一條>
- 未讀過但可能相關的檔案：<路徑>
```

沒有失敗軌跡的升級＝讓上級從零重查一遍，等於白升。

### 降級（解出 pattern 後往下丟）

高階模型解出「固定可複製的修法」後，把修法寫成配方（改哪裡、改成什麼、怎麼驗證），派 `sonnet`/`haiku` 批次套用。配方必含 1 個已完成的 diff 當範例。

### 重試上限

同一子任務在同一層級最多嘗試 2 次——第 2 次失敗即升級，不在同層試第 3 次；升級後那一次是第 3 次嘗試，仍失敗 → 熔斷問使用者（03 矩陣 C6）。「換個小寫法再試一次」也算一次嘗試。

## 5. 隔離驗證（實作者不自驗）

{{若既有治理層有「不得自我核准」類規則，加一句：與 {{路徑}} 的「{{條文名}}」同向；本節管 Claude 端 subagent 的落實方式。}}

- 實作 agent 的「我完成了」是未驗證的宣稱，看起來沒問題也不跳過驗證。
- 驗收由 Fresh-Context 驗證者執行：新開一個 subagent，只給它「驗收條件＋成果路徑」，不給實作過程與實作者自述（避免被帶風向）。
- 三種驗證模式，按任務選：

| 模式 | 適用 | 做法 |
|------|------|------|
| Read-back | 文件、設定、規則檔 | 驗證者重新讀檔，逐條對照驗收條件打勾，回報「條件 → PASS/FAIL＋證據行號」 |
| 實跑 | 程式碼 | 驗證者實際跑 build／測試指令（見 03 矩陣 B 的本專案指令），貼結尾輸出 |
| 多樣本評審 | 設計文件、方案選型 | 產 2~3 個獨立版本，派評審 agent 依明文評分標準選優，混合裁切 |

- 驗證者回報 FAIL → 回實作者修（計入該子任務的重試次數）。
