## 矩陣 A：停損換路徑信號（「方向錯了」，立刻停止原地重試）

命中任一條 → 停下當前修法，執行動作欄。「原地重試」定義：不改變假設、只微調程式碼再跑一次。

| # | 信號（量化） | 動作 |
|---|--------------|------|
| A1 | 同一錯誤訊息第 3 次出現，且前兩次用了不同修法 | 停。寫失敗軌跡（格式見 02 §4），重新列出 3 個候選假設，逐一用證據排除，或升級 |
| A2 | 蹺蹺板：修 A 壞 B，修 B 又壞 A | 停。這是共同上游的架構層問題，往上找兩者的共同依賴，不要在 A/B 本身繼續修 |
| A3 | 發現自己在改「不是本任務要動的」框架檔、library 檔、共用工具檔，只為了讓錯誤消失 | 停並還原。通常是自己用法錯；wrapper／框架真有 bug 時，正解是繞過它，不是改它 |
| A4 | 想用這些手段讓測試過：try/catch 吞錯、加 sleep、hardcode 測資、放寬斷言、skip 測試 | 停。這些是掩蓋不是修復，沒有可以請示的例外 |
| A5 | 投入 10 次以上 tool call，而驗收條件的完成數為 0（數的是工具呼叫總數，與 A1 的錯誤次數、02 的重試次數是三個不同的軸） | 停。重讀任務描述，檢查是不是解錯題；向使用者或上級模型重述「我理解的任務」求確認 |
| A6 | 開始懷疑「是不是環境壞了／cache 髒了」而想重啟服務、清 cache、重裝套件 | 先停。這是狀態改變操作：先找到支持該假設的 log 證據（哪一行說明是環境問題），沒證據不動環境 |
| A7 | 用自己稍早訂下的範圍約束（「本次不碰 X」）當理由，略過在 X 裡看到的明顯缺陷 | 停。約束是為了控制風險，不是免除思考：重問「當初訂這條的理由，適用眼前這個缺陷嗎？」。範圍外的缺陷至少明確回報給使用者，不靜默略過 |
| A8 | 想採用暫時性修法：workaround、先讓它能動、註解寫 TODO／暫時／之後再修、只治症狀不治因、在呼叫端補防禦而不修真正壞掉的那一層。兩類不適用本條：①繞過第三方／框架的既知缺陷（A3 的正解），但限於該繞法已是本專案常態——repo 有 ≥2 處既有先例，或 memory／{{詞彙表檔名，預設 GLOSSARY.md；既有專案已有 CONTEXT.md 就沿用}} 已登記該缺陷；首次繞過沒人登記過的缺陷仍走本條（也是 workspace 根 `CLAUDE.md` §3「引入專案沒有的新模式前先徵得同意」的情形）。限定的理由：「繞過第三方」與「在呼叫端補防禦」動作形態相同，只靠意圖分類會變成萬用豁免。②為了讓測試過的掩蓋手段——屬 A4，沒有請示通道 | 停。正確性優先於「能動」；禁止的是靜默採用，不是暫時修法本身。輸出三件事：①正確修法（根因在哪：檔:行；要改什麼）②為何這次不做（成本／風險／根因在不可控的外部系統：{{本專案不可控的外部系統清單，例：第三方 API、上游服務、供應商套件}}）③暫時修法的已知副作用與失效條件。三件齊備才問使用者裁決，缺任一件＝還沒查清楚。使用者裁定可行後才寫，程式碼註解與回報都標明它是暫時的、正確修法是什麼 |
| A9 | **環境級異常、而本任務沒動到那一段**：服務起不來、端點全回授權錯誤、外部呼叫卡逾時、測試信寄到真實收件人、連到不該連的資料庫 | {{有本機覆寫時：停，先不改程式，先查本機覆寫還在不在：`{{救回腳本的檢查指令，例：node .claude/hooks/restore-local-hacks.js}}`（只檢查、不改檔；清單在 {{覆寫清單位置}}）。不見了或內容不完整，救回或補齊後重現一次症狀，再決定要不要往程式找——覆寫被還原時往往過了幾小時才從這些異常浮現，回頭追很貴。每個檔該填的值與漏補的症狀見 `.claude/harness/local-overrides-guide.md`。覆寫全綠而症狀還在時，可能是埠號指到別套服務、跑的是主要工作目錄的服務而不是你改的那份、建置後沒重啟——上面的檢查都抓不到，照 B13 驗服務歸屬與跑的是哪一份程式，並實際打一次端點看拿不拿得到值}}{{有多工作樹時再加：開新工作樹時，清單上的覆寫要從主要工作目錄帶齊，帶完在新工作樹跑一次上面的檢查指令——新工作樹是乾淨的原版，沒有備份可救，漏帶只能靠這一步發現{{有裝 remind-worktree-overrides 時加：；從工作樹起服務時，自動檢查會點名那個工作樹沒帶齊的覆寫（只提醒、不擋）}}}}{{無本機覆寫：本專案不適用：沒有本機覆寫檔{{有裝 check-worktree-ports 時：這句改成「本專案沒有本機覆寫檔」，下面 port 驗證那一句照樣加}}}}{{有裝 check-worktree-ports（工作樹的 port 驗證）時加，不論有沒有本機覆寫：起好服務之後、或覆寫全綠而症狀還在時，先跑 `{{port 驗證指令，例：node .claude/hooks/check-worktree-ports.js --ports <服務>[@<工作樹>]=<port>,...}}`（只讀；只帶 --help 跑會列出可填的服務與工作樹），一次查三件：設定檔指向的 port 跟這次的拓撲一不一致、每個 port 上跑的是不是這次要的工作樹與分支、建置產物是不是比 process 新（建置後沒重啟）；有設健康檢查的服務另外實打一次。標「?」的是判不出、不是通過，那幾項照 B13 手動驗}} |

**A1 正例**：同一個鎖定檔衝突錯誤第 3 次出現 → 停止重試，改走該工具文件記載的已知繞法，並把這個坑寫進 memory。
**A1 反例**：同一個 500 錯誤出現第 5 次，每次只是換一個參數再打一次 API，從沒去看後端 log——這是消耗 context 的祈禱式重試。
**A3 正例**：共用元件的自動量測把版面撐壞 → 不去改元件量測演算法，改用元件提供的固定參數繞過，並把元件疑點記進 memory 待使用者決定。
**A3 反例**：為了讓 build 過，直接改相依套件目錄裡的型別定義檔。

### B23 寫法

- 宣稱「測過沒問題」時說測的是哪一層：「build 過」（①）、「實跑輸出如下」（②）、「我看過畫面，資料是對的」（③）。每層有自己的假陽性，低層看不見高層的失敗，複驗同一層也會一直過。
- ③ 沒做就明說沒做，例：「exit 0、9/9 checks 過（①），但我沒有實際看過那張圖好不好讀（③未做）」。
- 驗證器與施作器不同源：用同一個函式庫寫檔又用它驗檔，驗證器對寫入器的破壞是盲的。跨層驗證要換工具、換判準（例：docx 用 XML parser 讀得過，要用 Word 實開才算③）。

| 模糊商業判斷：某欄位該不該給某類使用者看、流程順序牽動誰的權責 | 需要組織脈絡，模型沒有 | 標 HYPOTHESIS，列出兩種解讀各自的後果，熔斷問使用者（C1） |
| 對外命名：對外 API 名、使用者看得到的文案 | 同上 | 給 2~3 個候選＋各一行理由讓使用者選；內部變數名照專案慣例，不必問 |
| 跨 session 的架構級重構決策 | 單一 session 看不到全部影響面 | 只記錄不動手：寫進 memory 標「待使用者決策」，附目前已知的影響面 |
| 從互相矛盾的規則判斷「哪條才是使用者真正要的」 | 模型會合理化任一條 | 照仲裁順序執行＋回報衝突（C4），不自行修改規則 |

判準能寫成清單的，自主做；寫不成的，做出選項讓人選。

## 品味決策標準流程

先判定是不是品味題，下列徵兆命中任一就是：

1. 沒有可驗證的對錯：兩個做法都能跑、都不違反規範，差別只在看起來或讀起來怎樣。能靠跑測試、查規範、量效能分出高下的是技術題。
2. 理由句寫不出「否則會怎樣」：說得出「不這樣做會壞／會慢／會違規」是技術題；只能說「比較好看／比較順」是品味題。
3. 對外可見：使用者看得到的文案、命名、版面、色彩、間距、圖示、訊息語氣——使用者有話語權，不由執行者代決。
4. 改回來很便宜：純顯示層調整、無資料遷移、無 API 契約變動，做兩個變體給人選比選錯再改便宜。

資安、資料正確性、架構分層、命名規範已有明文者、效能可量測者不是品味題：有正解，照規範做，不包裝成「請你選一個」丟回去。

判定為品味題後：產 2~3 個都能跑的變體（不是口頭描述），實際呈現各變體的可觀察差異（開畫面各截一份狀態，或列代碼差異表），附一張變體 ×（優點／缺點／工作量）表，用 AskUserQuestion 給使用者選並附推薦與一行理由。使用者選定後把決策寫進 memory（type: feedback），下次同類題直接引用。
