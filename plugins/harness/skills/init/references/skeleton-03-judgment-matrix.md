## 矩陣 A：停損換路徑信號（「方向錯了」，立刻停止原地重試）

命中任一條 → 停下當前修法，執行動作欄。「原地重試」定義：不改變假設、只微調程式碼再跑一次。

| # | 信號（量化） | 動作 |
|---|--------------|------|
| A1 | 【計錯誤出現次數】同一錯誤訊息第 **3 次**出現，且前兩次用了不同修法 | 停。寫失敗軌跡（格式見 02 §4），重新列出 3 個候選假設，逐一用證據排除，或升級 |
| A2 | 蹺蹺板：修 A 壞 B，修 B 又壞 A | 停。這是共同上游的架構層問題，往上找兩者的共同依賴，不要在 A/B 本身繼續修 |
| A3 | 發現自己在改「不是本任務要動的」框架檔、library 檔、共用工具檔，只為了讓錯誤消失 | 立刻停＋還原。99% 是自己用法錯，不是框架錯；wrapper／框架有 bug 時的正解是繞過它，不是改它 |
| A4 | 想用這些手段讓測試過：try/catch 吞錯、加 sleep、hardcode 測資、放寬斷言、skip 測試 | 停。這些全是「掩蓋」不是「修復」，沒有合法理由 skip |
| A5 | 【計工具呼叫總數，與 A1 的錯誤次數、02 的重試次數是三個不同的軸】投入 **10 次以上 tool call** 而驗收條件的完成數為 **0** | 停。重讀任務描述，檢查是不是解錯題；向使用者或上級模型重述「我理解的任務」求確認 |
| A6 | 開始懷疑「是不是環境壞了／cache 髒了」而想重啟服務、清 cache、重裝套件 | 先停。這是狀態改變操作：先找到支持該假設的 log 證據（哪一行說明是環境問題），沒證據不准動環境 |
| A7 | 用**自己稍早訂下的範圍約束**（「本次不碰 X」）當理由，略過在 X 裡看到的明顯缺陷 | 停。約束是為了控制風險，不是免除思考。重問一次「當初訂這條的理由，適用眼前這個缺陷嗎？」——通常不適用。範圍外的缺陷至少要**明確回報給使用者**，不可靜默略過 |
| A8 | **想採用暫時性修法**：workaround、先讓它能動、註解寫 TODO／暫時／之後再修、只治症狀不治因、在呼叫端補防禦而不修真正壞掉的那一層。⚠ **兩個不適用本條的類別**：①**繞過第三方／框架的既知缺陷**——A3 已裁定那是正解不是暫時修法；但**入場條件**：該繞法已是本專案常態（repo 有 ≥2 處既有先例、或 memory／{{詞彙表檔名，預設 CONTEXT.md}} 已登記該第三方缺陷）。首次繞過一個沒人登記過的第三方缺陷仍走本條請示——「繞過第三方」與「在呼叫端補防禦」動作形態同構，只靠意圖分類會變成萬用免死金牌；②**為了讓測試過的掩蓋手段**——那是 A4 的絕對禁令、沒有請示通道，不得改走本條降級成「可商量」 | 停。**正確性優先於「能動」**。不是禁止暫時修法，是禁止**靜默**採用：輸出三件事——①**正確修法是什麼**（根因在哪：檔:行；要改什麼）②**為何這次不做**（成本／風險／根因在不可控的外部系統：{{本專案不可控的外部系統清單，例：第三方 API、上游服務、供應商套件}}）③**暫時修法的已知副作用與失效條件**。三件齊備才問使用者裁決，缺任一件＝還沒查清楚。使用者裁定可行後才准寫，且程式碼註解與回報都要標明它是暫時的、正確修法是什麼 |

**A1 正例**：同一個鎖定檔衝突錯誤第 3 次出現 → 停止重試，改走該工具文件記載的已知繞法，並把這個坑寫進 memory。
**A1 反例**：同一個 500 錯誤出現第 5 次，每次只是換一個參數再打一次 API，從沒去看後端 log——這是消耗 context 的祈禱式重試。
**A3 正例**：共用元件的自動量測把版面撐壞 → 不去改元件量測演算法，改用元件提供的固定參數繞過，並把元件疑點記進 memory 待使用者決定。
**A3 反例**：為了讓 build 過，直接改相依套件目錄裡的型別定義檔。

| B19 | **判斷類主張三類——「測試會不會紅」「缺陷修好了沒」「這個問題在不在本次範圍內」——一律先跑再下結論，讀碼推論不算完成**（連續以讀碼推論代替實測，常見結局是全數被實跑推翻；B12 只管「防護是否多餘」的 ablation，本條管其餘三類）。**兩軌審查對同一項判不同嚴重度時同理**：自己實跑驗證，不可取中間值、不可選寬鬆的那軌（「需要更好的工具才能正確處理」≠「可以不正確」） | 貼實跑的指令與輸出（測試結果行／API 回碼／資料筆數）；「我讀過相關程式碼」不構成證據 |
| B20 | **盤點「某欄位／情境有沒有被測過」不得只 grep 呼叫點**：先 grep 定位檔案，**再開檔看該測試是否參數化**（{{本專案測試框架的參數化寫法，例：parametrize／test.each／table-driven}}），有就展開參數清單逐項看涵蓋什麼；判準是「這個欄位有沒有被當**篩選條件送出**」，不是「字串有沒有出現」（欄位名在資料欄位裡出現幾百次是常態）。盤點表格欄位要**先定位欄位定義的行號範圍**再在範圍內取 key，不可掃全檔（會把圖例、狀態標籤的 key 算成欄位）。盤點結論寫進派工 prompt 時加一句「若你 Read 後發現某項其實已有覆蓋，改走 reuse 並說明我哪裡判斷錯」 | 貼展開後的參數清單或欄位定義範圍行號；只貼 grep 計數＝未完成 |
| B21 | **審查時判「假陽性」或翻案，涉及識別字語意的判斷必須同時確認三件事**：①宣告來源（import）②**同作用域是否有同名參數遮蔽**③實際呼叫處——缺一不得定性。翻案本身也是事實主張，要與原始主張同等舉證；取修改前原碼用 `git show <commit hash>:<path>`，**並行 session 環境下不得用 HEAD 相對引用**（HEAD 會在稽核期間被別的 session 推進），每次稽核前重拉 `git log`。典型陷阱：`catch (error) { error('...') }`——只看到 import 存在就判假陽性，漏了 catch 參數遮蔽同名 import，觸發即型別錯誤 | 三件事各貼檔＋行號；翻案附 `git show <hash>:<path>` 的輸出片段 |
| B22 | **「掃描器／覆蓋率工具回報乾淨」不等於「這件事沒問題」——引用任何自動化檢查的零缺口結論前，必須答得出它的盲區是什麼**。判準三問：①這個工具**看得到什麼形狀**的問題、看不到什麼（regex 只認數字？只掃命中行不開全檔？只認某種語法？）②它回報的 0 是「掃過且沒有」還是「根本沒掃到」③這類問題**有沒有第二種判準**能交叉驗。⚠ **新引入的工具尤其危險：節點數／覆蓋率數字會讓結果看起來很成功**——索引工具沒解析某種檔型時只產出骨架節點；依賴框架執行期分派（反射、訊息匯流排、DI）的程式碼，靜態找不到 caller，「死碼」查詢會報出大量假陽性 | 引用零缺口結論時，**同時貼出該工具的盲區說明**（一句話：它看不到什麼）＋**一個反向樣本**（已知該問題存在的案例，證明這個工具抓得到）。只貼「掃描通過／coverage 乾淨／查詢回 0 筆」＝未完成 |
| B23 | **三種宣稱嚴格分離**：①結構檢查（parse 過、lint 過、exit 0）②機器證據（實跑輸出、截圖、量測）③感知審查（人或看得到圖的模型實際看過內容對不對）。**通過其中一種，不准說成通過另一種** | 講到哪層就只貼哪層的證據；跨層宣稱要另附該層證據 |

**完美正例**：「匯出功能完成：build 0 error、畫面實測截 3 個狀態、QA 8/8 TC pass（報告在 `{{測試目錄}}/…`）、diff 僅 4 個目標檔、驗證 agent read-back PASS。」
**典型反例**：「已實作完成，理論上應該可以正常運作」——沒跑過 build、沒看過行為。這句話在本 workspace 等同「未完成」。
**範圍類反例**：「QA 17 個 test 連跑兩次全綠」——但 17 個全是導航斷言，一條資料斷言都沒有，那頁裡面有沒有資料沒有人驗過。同型：「370 passed／0 failed」——全是 mock 的單元測試，真實資料存取路徑一次都沒跑過，實際寫入 0 筆。
**範圍類反例二**：QA 派工只列了正向標的，退件路徑是「本輪唯一沒被任何測試碰過的分支」，使用者一句「跑完你沒驗證退件重送喔」點破。
**對齊類反例**：「新版已對齊舊版」——只掃了分頁標籤和標題，卻漏了分頁預設值、序號位移、後端少回十幾個欄位。目測對齊必漏，必須程式化逐項 diff。

### B23 展開：為什麼要把「我驗過了」拆成三層

```
  ① 結構檢查              ② 機器證據                ③ 感知審查
  parse / lint / exit 0   實跑 / 截圖 / 量測        人真的看過內容
        │                       │                         │
        ▼                       ▼                         ▼
  「格式合法」             「跑起來沒爆」            「東西是對的」

  ⛔ ①過 ≠ ②過        ⛔ ②過 ≠ ③過         ⛔ ①過 ≠ ③過
```

**每一層都有專屬的假陽性，而且低層完全看不見高層的失敗**：

| 真實事故 | 犯的是哪種冒充 |
|---|---|
| docx 用 XML parser 讀得好好的，Word 判「檔案似乎已毀損」 | ①當③（parse 過 ≠ 目標軟體開得了） |
| 六個子系統「全部 200、混合內容 0 筆」，截圖是「連接失敗」 | ①當③（數據合格 ≠ 頁面能用） |
| 兩頁截圖 MD5 完全相同，兩張都是登入提示頁 | ②當③（截到圖了 ≠ 截到那一頁） |
| 某頁截到全白、幾 KB 的圖 | ②當③（有檔案 ≠ 有內容） |
| 只看 grep 命中行就判假陽性，漏了 catch 參數遮蔽同名 import | ①當③（字串在 ≠ 語意對） |

⛔ **最危險的不是沒驗，是「驗了低層卻宣稱高層」**——它讓錯誤穿過所有關卡直到使用者發現，
而且每次複驗都會過（因為複驗的也是同一層）。

**寫法要求**：
- 宣稱「測過沒問題」要說**測的是哪一層**：「build 過」（①）、「實跑輸出如下」（②）、「我看過畫面，資料是對的」（③）
- **③ 沒做就明說沒做**，不准用 ①② 的證據混過去。例：「exit 0、9/9 checks 過（①），但我沒有實際看過那張圖好不好讀（③未做）」
- 驗證器與施作器**不可同源**：用同一個函式庫寫檔又用它驗檔，驗證器對寫入器的破壞完全盲。跨層驗證要換工具、換判準

> 此條改寫自 tt-a1i/archify 的 delivery-contract（MIT）。原版把交付拆成
> `deliver`（確定性檢查）／`visual-check`（瀏覽器證據）／perceptual review（真人審查），
> 並在程式裡強制執行——`visual-check` 的 receipt **永遠回報 `visualReview: "pending"`**，
> 不管截圖拍得多成功，就是不准把自動化截圖算成「有人看過了」。
> **值得學的是這個機制形狀**：不是用規則要求人誠實，而是**讓證據本身拒絕被過度解讀**。

### 問使用者前的三重自查

{{若有裝 check-ask-discipline hook 加一行：> PreToolUse hook `check-ask-discipline.js` 驗「每題必附建議選項」作為自省錨點，判斷靠本節。}}

按 AskUserQuestion 前逐項過，**任一命中＝禁問**：

1. **事實型**？答案能用 15 分鐘內查證得到（讀碼、查 memory、跑指令、B13 三重驗證——port 歸屬、檔案內容、服務狀態全屬此類）→ 自己查。
2. **規則已裁型**？harness／skill／CLAUDE.md／專案慣例已有明文答案（BLOCK→修、審查完成→匯流、內部命名照慣例）→ 照規則做，回報中記一行「已照 X 處理」。
3. **可逆低價型**？選錯一行改回、或不影響可觀察行為 → 自己決，開工表態或回報中列「已代決：X＝Y」供事後否決，不阻塞。{{C2 明確允許自己做的事屬此類，照填}}

過完三關仍是「真決策＋無慣例可循＋選錯需返工」才准問，且**必附建議答案**；多個問題**湊成一次**發（AskUserQuestion 一次至多 4 題），**禁止逐項請示迴圈**。執行中的進度狀態不是問題（「還在跑要不要等」照矩陣 A 走，不問）。使用者已明確授權的範圍 → 直接做。

**同理，查證動作也要湊一次**：當你自己已列得出要查的 N 項（使用者已指明範圍，或你的 plan 已列項），一次查完再回報，禁止「查一項→回報→再查下一項」的擠牙膏。**邊界**：使用者需求在流動、邊看邊追加新查證項時，漸進回報是對的、不受此條約束——此條只治「已知全集卻分批擠」，不治「需求本身在長」。對 **prod 資料變更**尤其適用：DELETE/UPDATE 前一次講清影響全貌與筆數，不可「先刪這五筆」再補說還有。

> 與無條件對齊回合的分界（04 模板五）：對齊回合管**開工前那一次**；執行中冒出的疑問一律過本節三重自查，不是隨時可停下來問的授權。

**本節管的是「請示」這個行為，不限工具**：用回覆文字結尾問「可否繼續／要不要進 QA／需要我接著做嗎」＝**變相請示**，同樣過三關。pipeline 既定的下一步（實作完→QA→review→完成報告）是規則已裁型——**直接做，不問**；問「可否做規則規定要做的事」是最典型的違規。

## 品味決策標準流程（弱模型照抄）

**先判定「這是不是品味題」——徵兆四選一，命中任一就是**（只有後續流程、沒說怎麼認出來時，該走這條的常被當成技術題硬選一個做）：

1. **沒有可驗證的對錯**——兩個做法都能跑、都不違反規範，差別只在「看起來怎樣／讀起來怎樣」。
   反面對照：能靠跑測試、查規範、量效能分出高下的，是技術題不是品味題。
2. **理由句寫不出「否則會怎樣」**——說得出「不這樣做會壞／會慢／會違規」就是技術題；
   只能說「這樣比較好看／比較順」就是品味題。
3. **對外可見**——使用者看得到的文案、命名、版面、色彩、間距、圖示、訊息語氣。
   對外可見＝使用者有話語權，不該由執行者代決。
4. **改回來很便宜**——純顯示層調整、無資料遷移、無 API 契約變動。
   便宜到「做兩個變體給人選」的成本低於「選錯再改」的來回成本。

⚠ **不是品味題的**：資安、資料正確性、架構分層、命名規範已有明文者、
效能可量測者——這些有正解，直接照規範做，不要包裝成「請你選一個」丟回去。

判定為品味題後照下列流程：

1. 承認這是品味題（對照 C5），不假裝有正解。
2. 產 2~3 個**都能跑**的變體（不是口頭描述）。
3. 實際呈現各變體的可觀察差異（開畫面各截一份狀態，或列代碼差異表）。
4. 一張表：變體 ×（優點／缺點／工作量）。
5. AskUserQuestion 給使用者選，附自己的推薦與一行理由。
6. 使用者選定後，把決策寫進 memory（type: feedback），下次同類題直接引用。
