# 04 — 標準化派工 Prompt 模板

> SSOT：派工 prompt 怎麼寫，只信本檔。修改權限：紅區（新增模板屬黃區，見 05）。
> 用法：複製對應模板 → 填掉所有 `<...>` 填空 → 發 Agent tool。**任何 `<...>` 留空就不准發**。
> 派工前先過 `02-model-dispatch.md` §6 的 10 秒自查。

## 共通規則

### 回報鏈鐵則（防「完工但回報斷掉」）

1. **禁止二次轉派**：每個派工 prompt 必寫「本任務由你親自執行，不得再轉派給其他 agent」——回報鏈固定一跳。需要多個 agent 時由主對話自己分別派、分別收。
2. **回報指示放頭尾各一次**：完成後的回報要求寫在 prompt **第一行與最後一行**各一次（抗長 context 遺忘）。
3. **主對話端磁碟驗收（最關鍵的防線）**：收到完成通知一律**直接查磁碟驗收產出**（git diff / grep / mtime），不空等、不催討自述回報——自述只當補充，磁碟才是驗收依據。
4. **「等待型 agent」＝反模式，禁用**：不得派「A 等 B 完成後彙整轉送」的中繼 agent。需要整合多份產出時，由主對話自己收齊再整合。
5. **禁背景 job**：派工 prompt 明令前景執行，subagent 開背景 job 會停下等通知、零產出。

### 其他共通規則

- 路徑一律用**絕對路徑**（subagent 不共享你的對話脈絡，「剛才那個檔」它看不懂）。
- 【邊界】必含搜尋範圍限制：**搜尋一律限定 repo/workspace 目錄，禁止全碟掃描**（殭屍程序不隨 agent 結束，曾有燒 7 小時 CPU 的前例）。
- 已知的坑（memory 條目）要**內聯進 prompt**，不要叫 subagent 自己去翻 memory（它讀不到你的 MEMORY.md 索引）。
- 實作型派工必附**「開工前必讀清單」**：{{填來源：既有治理層的載入規則挑相關檔絕對路徑／各 repo CLAUDE.md／專案規範文件；沒有就刪此段但保留模板欄位}}。subagent 開工第一步是 Read 完清單，且回報必列「已讀清單」——缺這欄或清單不齊，直接退回重報。
- **跨模組鏈路紀律**：任務動到 workspace 根 `FLOWS.md` 已收錄鏈路上的任一層 → 該檔列入【開工前必讀】，且完工報告必答「鏈路其他層是否需同步」（漏同步的層通常靜默吞掉、不報錯）。
- 回報格式鐵則：**成果路徑＋關鍵行號＋結論；禁止噴大段代碼**（>10 行的代碼引用一律改成「見 <路徑>:<行號>」）。
- 驗收條件必須可機械判定。自查法：每一條都能回答「用什麼指令或什麼觀察來判定 PASS/FAIL？」。
- **診斷型任務（查 bug root cause）派工 prompt 必含一句**：「拿到可重現的紅指令前禁提 root cause；先列 3~5 個可證偽假設才准測；修復必走 red→green→verify：先寫紅的回歸測試看它紅 → 修到綠 → 回跑原始紅指令確認症狀消失，缺任一步不算修復完成。」（子 agent 不會自主採用紀律——紀律必須 inline 進 prompt）

```

```

## 模板四：代碼審查型 / Fresh-Context 驗證型（agent type：`{{審查 agent，預設 code-reviewer}}` 或 `general-purpose`；model：`sonnet`）

> 用於 02 §5 隔離驗證與 pipeline 的審查步驟。**只給驗收條件與成果路徑，不給實作者的自述**。
> 審查者不做瀏覽器操作——需要 UI 佐證時，在回報中建議主對話改派 `{{QA agent}}`（靜態審查看不出跑起來才會出的錯，這正是要標註給 QA 的原因）。

```
【目標】驗證以下產出是否達成驗收條件（你是驗證者，預設立場：不相信它完成了，找證據）
【產出路徑】<檔案清單，絕對路徑>
【驗收條件】（逐條判定）

2. <條件二>
【驗證方式】
- 重新 Read 每個產出檔（讀檔尾確認未截斷）
- <需要實跑的指令>
【回報格式】
- 每條驗收條件一行：條件 N → PASS/FAIL — 證據（<路徑>:<行號> 或指令輸出關鍵行）
- 總判定：全部 PASS / 有 FAIL（FAIL 必附「差在哪、建議修法一句話」）

**Pipeline（本專案版本）**：

```
{{Q1 確認後的 pipeline。預設全套：
[對齊回合] → backend-architect 設計 → backend-engineer 實作 ┐
             frontend-engineer 實作（等 API Contract 確認後）┘
           → qa-engineer 測試計畫＋開畫面實測＋codify
           → code-reviewer 審查 → 完成

```

**配套三條（不隨裁切拿掉）**：

1. **無條件對齊回合**：行為類需求開工前**必過一回合、不可跳過**（對話式開工同樣適用）——有決策型解讀分岔（會導向不同 schema／API contract／對外行為，見 03 C1）→ 逐題訪談到清零；無分岔 → **明說「無分岔＋一句理由」讓使用者可否決才開工**，靜默開工＝違規。
2. **QA 先於 review**：行為類（新 API／新畫面／新按鈕／連動／顯示／資料寫入等跑起來才看得到的行為）一律先 QA 實測、再送審查——靜態審查看不出跑起來才會出的錯（行為類 bug 審查全過、上畫面才炸，是這條存在的理由）。
3. **分流例外**：純結構／文案／死碼等「靜態可確定等價」者，可審查過即完成、QA 可評估跳過（判準＝正確性能否只靠讀 code 確定）。{{若 Phase 3 Q6 使用者選擇豁免測試要求，在此加一行：本專案尚無測試基礎，QA 步驟改為「實跑＋貼輸出」，codify 豁免至測試基礎建立為止——這是暫時豁免，不是永久規則}}

**編排順序**：

```
0-a 對齊回合（配套 1）——主對話執行，不得下放
0-b 範圍分析＋開發計畫 → 向使用者確認後才啟動 agents
1~N 依序派工（模板二／四填空；02 §1 顯式帶 model）
    → QA（行為類必做，先於最終審查定案；{{QA agent}} 一手包，派工用模板六）
    → 審查（模板四，{{審查 agent}}）
    → 完成報告
```

**開發計畫格式（0-b 產出，向使用者確認）**：需求摘要一句話／涉及範圍／預計步驟（每步一行：agent — 做什麼）／預計影響的檔案或模組／**對齊判定：無解讀分岔（一句理由）或已對齊清零（N 題）**（強制欄位，缺欄的計畫不得送確認——強制表態是為了讓漏判從「靜默」變「可見」，使用者確認計畫時可直接否決）。

**簽收物不因跳過 architect 而豁免**：行為類任務（含重構、bug 修）即使不派 architect，派實作前仍須產出簽收物並經使用者一行確認——比例原則：大案＝測試情境表＋API Contract；小案＝**影響面清單＋驗證計畫**（動哪些檔、哪些刻意不動＋為什麼、怎麼驗證）。

**計畫確認＝全 pipeline 授權**：0-b 經使用者確認後，派工 → QA → 審查 → 完成報告**一路自動推進**，步驟之間**禁止停下請示**（「可否繼續」「要不要進 QA」——QA 是必要步驟，問「可否做規則規定的事」＝03 三重自查第 2 關違規）。停下的唯一合法理由＝03 矩陣 C 熔斷條件命中、或計畫內明列的中途確認點。

**交接中轉三原則（子 agent 不互通，主對話是唯一匯流排）**：

1. architect 的設計文件（含測試情境表）**原封不動**傳入 engineer prompt；engineer 的檔案清單＋API Contract 確認傳入 QA、審查與前端 prompt。
2. 審查不通過 → 回實作步驟，審查意見以 `## 審查意見（修正）` 區塊附入重派 prompt（計入 02 §4 重試次數）。
3. 完成報告要素：需求摘要／設計文件摘要／檔案清單／QA 報告路徑／審查結果／未盡事項誠實列出。

## 模板六：QA 驗證型（agent type：`{{QA agent}}`；model：`sonnet`，命中 02 §1 進階執行層判準任兩項則 `opus`）

> QA 的測試範圍等於指揮官的想像力——**指揮官漏想的情境，QA 結構上不會補**。本模板的【範圍展開】四格就是治這個（03 B15）。
> 封閉的 TC 清單是最常見的失敗形狀：派工單只列正向標的，使用者實測抓到的缺陷幾乎全落在派工單沒寫的那一格。

```
【本任務由你親自執行，不得再轉派給其他 agent】完成後回報主對話。

【目標】驗證：<功能一句話>
【開工前必讀】（第一步逐檔 Read 完再動工）
- <workspace>/tests/Project_Detail/PROJECT.md（QA 操作坑與測試設計知識）
- {{本專案測試執行說明的絕對路徑（測試目錄 README、執行指令說明）；無則刪此行}}
- <簽收情境表絕對路徑（若有）>
【開工前對齊】無分岔＋<一句理由> ／ 已對齊清零（<N> 題）／ 分流例外：<理由>
【目標環境】<預設 {{本機環境描述}}；切其他環境時寫明網址、後端、身分來源>
【既有測試分流】reuse：<既有 test 檔絕對路徑> ／ 新 TC：<為何既有案例接不住，一句>
【背景】<改了什麼；動到哪些檔；本功能在 pipeline 的位置>
【已知的坑】<與本任務相關的 memory 條目內文，照抄不要省>

【範圍展開】（四格全填；任一格填「無」必附一句理由，空白＝派工不合格）
1. **正向路徑**：<本次改動的 happy path，逐步>
2. **反向／終止分支**：退件／拒絕／取消／軟刪／逾時／重送／權限不足 —— 逐條列出適用哪幾條、怎麼觸發；不適用的逐條說為什麼
3. **狀態序列**：至少一條多步操作（做 A → 做 B → 撤銷 A → 存檔 → 重開），驗最終狀態與各中間態一致；單步操作測不出的鎖死型缺陷只有這格抓得到
4. **受影響的共用元件**：本次觸及的共用元件清單（{{本專案共用元件的所在目錄，例：src/components/common/}}）＋各自其他使用點是否需連帶回歸；改共用元件必列，不得只驗本頁

【測試資料來源】（必填，三選一；選 b/c 必附一句理由）
a. **走真實業務流程長出來**（首選）：從該模組的實際入口操作產生資料。
   理由：走真流程長出來的資料，本身就在驗那條流程還通不通——直接塞進資料庫的資料驗不到入口卡控、欄位預設值、狀態機初值。
b. **自種自清**（寫入後取回自己建的 Id ＋ teardown 自刪）：真流程成本過高、或該資料在真流程中屬於上游系統推送時用。**禁寫死 Id**。
c. **依賴既有資料**：僅限「字典／設定類」主檔，且**期望值必須查資料庫推導、不得寫死**（資料重建後字典 Id 會變）。
   **業務資料列一律不得走 c**。

⛔ **絕對禁止**（六條{{；有稽核工具時寫：機械閘＝<工具路徑>}}）：
   1. 硬編業務資料列的**數字 Id**（`ORDER_ID = 430` 這種）
   2. 硬編**業務代碼**字面值（客戶代碼、租戶代碼、單號這種）→ 從當前生效的身分設定或查詢推導
   3. **直接 INSERT／UPDATE 業務主體表**造被測狀態 → 走產品入口（a）；真的只能自種就走 b，並在註解寫明「為何 a 不可行」。（`DELETE` 自清不在此限）
   4. 硬編**使用者身分**當輸入（帳號、部門代碼這種）→ 從當前生效的登入身分 decode；要「另一個人」用查詢挑一個不是登入者的；要「不存在的人」用刻意命名的常數（`NONEXISTENT_*`）
   5. 依賴要人工先跑的外部種子腳本、teardown 去「還原別人的資料」（只能刪自己造的）
   6. **以顯示文字當定位條件**（用按鈕字、標題字找元素）→ 切換語系或改文案後整批 timeout，症狀像功能壞掉。
      改錨在不隨語系變的東西：①產品既有的 id／name／元件 class／路由 path ②i18n key 取當前語系譯文 ③位置順序 ④測試端執行時打標記。
      ⚠ 存在性檢查（`.count() > 0` 這類）**是定位器不是斷言**，一樣要改。

   **總判準**：把登入身分換成另一個使用者、把租戶／客戶身分換成另一家，這支測試還會綠嗎？不會 → 就是寫死了。
   連「宣告一個常數讓大家引用」都不夠——常數仍然是寫死。單一事實來源是**當前生效的那個身分設定**，它變、測試跟著變。

【欄位級驗證】（寫入型端點必填）
- 本次涉及的寫入欄位共 <N> 個，逐欄做 readback 斷言：填入 → 暫存 → 重開 → 讀回 → 比對
- bool／int 一律用**非預設值**（避免「讀錯來源也看似對」的假陽性）；集合類驗多筆＋順序＋筆數
- 不驗的欄位**逐個列出＋理由**，不得只寫「其餘略」

【邊界】只准動 <測試資料夾清單>；搜尋一律限定 repo/workspace 目錄，禁止全碟掃描；本任務由你親自執行，不得再轉派其他 agent；前景執行，禁背景 job
