# 架構保養例行

**使用者明說才啟動，不得自主發起、不得在談別的事時順手啟動。** 掃描加報告約一個中型任務的用量；嫌貴就拉長間隔（建議每兩週，或每做完一個大模組一次）。

程式寫得快，亂也長得快——定期掃，**每次最多修一個**。清單不是目的，修掉一個才是。

## 流程

1. **讀排除清單**：本 skill 目錄的 `exclusions.md`（`.claude/skills/structure-upkeep/exclusions.md`；**不存在＝空清單**，第一次收尾時建立）。使用者否決過、而且給了理由的候選記在裡面，**不得再提**。
2. **找熱點**：派 `Explore` 掃最近兩週的 git log（{{repo 清單}}），找反覆被改的檔與模組——最近常動的地方，整理起來最划算。搜尋限定在 repo 目錄內，禁止全碟掃描。
3. **列候選**：只看下面幾類、讀檔就判得出來的問題：
   - {{本專案規範抓得到的類型，每類附依據（規範檔＋條目）。通用預設四類：同一層裡重複的邏輯形狀（第 3 次出現）；同一個分支判斷散在好幾個地方；名稱跟實際行為對不上；一個檔因為好幾種不相干的理由被改}}
   - 不准質疑：{{使用者或規範明定要保留的結構，例：規定一定要有的轉換層、包裝層}}
   **每一條候選都要開檔實讀驗證過才能進報告**——不准只憑行數、修改次數、檔名或 Explore 的摘要下結論（行數多不等於職責混雜、檔案多不等於散落、檔名看起來像測試用不等於沒人用）。Explore 只負責圈熱點，判定一律自己讀；讀完還不確定的放「待查」區，不准寫成候選。驗證成本不能轉嫁給使用者。
4. **出報告**：3～5 個候選，每個附「檔案／問題／改法一句話／預期好處」，一頁以內。
5. **使用者挑最多一個**（或全部略過）→ 照一般開發流程修（`04-delegation-templates.md` 模板五：設計 → 實作 → 測試 → 審查），不因為是「保養」就降低標準。
6. **收尾**：被否決而且有理由的 → 寫進 `exclusions.md`（檔案不存在就這時建立），一條一行：`- YYYY-MM-DD [模組] 候選一句話 —— 否決理由`；沒挑也沒否決的**不留待辦**（下次重掃自然會再浮出來）。

## 護欄

- 使用者明說才啟動，不得自主發起、不得在談別的事時順手啟動（約一個中型任務的用量）。
- 每次最多修一個；報告不超過一頁；候選不超過 5 個。
- 排除清單是本 skill 自己的狀態，住在本 skill 目錄，不放 memory（memory 會被精簡、改名，這裡會找不到）。

變更紀錄見同目錄 `CHANGELOG.md`
