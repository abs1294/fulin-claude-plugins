# init 規則的理由與事故經過

> SKILL.md 與 `phases/` 各檔裡，規則旁只留一句理由；為什麼會有這條規則的完整經過收在這裡。
> 執行 init 時**不必讀本檔**——照規則做就好。要改規則、或懷疑某條規則多餘時，先讀它在這裡的經過。
> 每條標出原所在檔與段落（0.15.2 時都在 SKILL.md，0.16.0 拆分後的位置寫在後面）。

## 核心原則

### 核心原則-1：先懂這個專案在做什麼，再裝流程

- 原出處：SKILL.md「核心原則」第 6 點（0.16.0 起仍在 SKILL.md 同一點）。
- 實際紀錄：某專案盤點把設定檔裡的預設網址判成「正式 ERP」，建議五項動作全部要先問使用者，使用者一句「這些都是測試環境」全部推翻；同一次安裝的專案詞彙表裝完只有示範條目，因為整個過程沒問過任何一個專案詞；必讀文件還推薦了一份自己也判定已過時的 README。
- 所以 Phase 1 第 13 項推專案輪廓、Phase 2 先攤專案概要草稿、Phase 3 先問專案理解三題（U1～U3）。

## Phase 0

### Phase 0-1：版本落後就停下

- 原出處：SKILL.md「Phase 0 — 前置檢查」開頭「最先做：比對正在用的 harness 是不是遠端 repo 上的最新版」的 exit 2 那一點（0.16.0 起在 `phases/phase-0-precheck.md` 同一段）。
- 實際發生過：裝到一半才冒出新版，舊版少了最後畫流程圖那一步，使用者裝完才發現，整輪重裝。

### Phase 0-2：多 repo 工作區不是非 git 專案

- 原出處：SKILL.md Phase 0 表格 0-1 那一列「不過時」欄（0.16.0 起在 `phases/phase-0-precheck.md` 表格 0-1 列）。
- 實際回饋：多 repo 工作區被當成非 git 專案，使用者要自己指出「最終的目的都還是要推到 git 上」。

### Phase 0-3：Codex 沒裝時問，不是停下

- 原出處：SKILL.md Phase 0 表格 0-3 那一列「不過時」欄（0.16.0 起在 `phases/phase-0-precheck.md` 表格 0-3 列）。
- 實際回饋：原本寫成「沒裝就停下」，使用者要自己說「Codex 這步先跳過」才能繼續，並指出「git-commit 會問要不要裝，Codex 為什麼不問」。

### Phase 0-4：git-commit 沒裝要在一開始講清楚

- 原出處：SKILL.md Phase 0 表格 0-5 那一列「不過時」欄（0.16.0 起在 `phases/phase-0-precheck.md` 表格 0-5 列）。
- 實際回饋：使用者在訪談中途才被告知需要它，還得自己問「裝和不裝差在哪」、裝完再問「然後裝好了嗎」。

## Phase 1

### Phase 1-1：測試目錄要打開看

- 原出處：SKILL.md Phase 1 盤點表第 5 項「測試基礎」的「記下什麼」欄（0.16.0 起在 `phases/phase-1-inventory.md` 同一列）。
- 曾實測某 repo 自述有測試目錄，實際不存在。

## Phase 6

### Phase 6-1：為什麼收尾要畫流程圖

- 原出處：SKILL.md「Phase 6 — 流程圖」開頭「為什麼有這一步」（0.16.0 起在 `phases/phase-6-flow.md` 同一段）。
- 實際回饋：「裝完之後沒有告訴我裝了些什麼」。

### Phase 6-2：要畫的清單由實際變動推，不寫死

- 原出處：SKILL.md Phase 6 三條硬規則第 1 條（0.16.0 起在 `phases/phase-6-flow.md` 同一條）。
- 實際回饋：「不應該寫死，要看有新增或更改的檔案」「不是說所有的檔案嗎」。

### Phase 6-3：每個節點都要有線

- 原出處：SKILL.md Phase 6 三條硬規則第 2 條（0.16.0 起在 `phases/phase-6-flow.md` 同一條）。
- 實際回饋：「知識筆記裡面讀跟寫的流程也都沒有畫出來」。

### Phase 6-4：拆成三張圖

- 原出處：SKILL.md Phase 6 三條硬規則第 3 條（0.16.0 起在 `phases/phase-6-flow.md` 同一條）。
- 實測：全部檔案加上全部關係塞進一張圖，實測 29 處線交叉、線穿過別的節點，讀不出來。

### Phase 6-5：同一支 agent 只畫一個節點

- 原出處：SKILL.md Phase 6「2. 先列清單，再寫三張圖的 JSON」表格「圖一」那一列（0.16.0 起在 `phases/phase-6-flow.md` 同一列）。
- 實際回饋：畫了兩個同名節點，被看成有後端架構師。

### Phase 6-6：流程圖的字要第一次用的人看得懂

- 原出處：SKILL.md Phase 6「5. 交付前易讀性自檢」開頭（0.16.0 起在 `phases/phase-6-flow.md` 同一段）。
- 實際回饋：流程圖寫「派工缺欄位」，第一次用的人根本不知道是什麼意思。

### Phase 6-7：收尾回報要列各角色交給哪個模型

- 原出處：SKILL.md「收尾回報」第 4 段「你已經有的」第 4 點（0.16.0 起在 `phases/phase-6-flow.md` 同一點）。
- 實際回饋：裝完使用者要自己問「工作交給哪個模型？怎麼判斷的」，看到表才發現寫規格的角色被套成 sonnet。

### Phase 6-8：踩坑經驗不寫「0 條」

- 原出處：SKILL.md「收尾回報」第 5 段「你還沒有的」第 1 點（0.16.0 起在 `phases/phase-6-flow.md` 同一點）。
- 實際回饋：使用者看到「踩坑知識 0 條」以為是缺陷，要自己推回「那是要讓它從專案的規矩長出來吧」。
