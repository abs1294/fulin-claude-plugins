# 測試計畫設計原則

**設計前先讀被測物本身**，測試案例從程式碼推出來，不從派工單的描述猜——派工單寫的是預期，程式碼寫的才是實際有哪些分支、欄位與檢核：

1. 開發任務描述：本次功能範圍
2. 介面定義：API Contract／路由與參數（{{本專案的 API 進入點位置}}）
3. 畫面程式碼：路由、欄位、按鈕、前端檢核邏輯（{{本專案的頁面目錄；無前端刪此項}}）
4. 資料流：狀態管理與 API 模組（{{本專案的對應目錄；無則刪此項}}）

- 每個測試案例逐步描述操作，粒度細到「照計畫執行即可，無需臨場判斷」（計畫同時是 codify 的藍本）；每個步驟附預期結果，執行時逐步比對判定 Pass/Fail
- 涵蓋派工單【範圍展開】四格；派工單缺格就回報主對話補，不要自己默默只測正向
- 建立測試資料時，每個可填欄位都填入合理且真實的值（留空的日期、數字欄位常在後續換算時爆出例外，而那正是使用者會踩到的路徑）
- 動到日期／時間相關欄位時，走真實 UI 輸入驗證，不只用手寫 API payload——手寫 payload 通常剛好避開時區換算；驗證要四點一致：UI 輸入值 → 送出的 payload → 資料庫實值 → 重新整理後的顯示值

# 回報格式

回報照派工單【回報格式】，另外：

- 測試報告檔案路徑
- 有簽收情境表的任務，對照簽收表逐列回報（每列標 綠／fail＋原因／blocked＋原因；列數由簽收表定，不得少報）；無簽收表就對照自擬測試計畫逐列，同樣三態
- 新的操作坑或測試設計知識：寫進 `tests/Project_Detail/PROJECT.md`（同步在同目錄 `CHANGELOG.md` 的 `## PROJECT.md` 節補一行），回報中列出寫了什麼
