# 註解：寫 Why 不寫 What

寫或改任何註解前{{有註解規範檔時加：，先讀 <註解規範檔路徑> 並照做}}。通用底線：

- 註解只寫**為什麼**：限制、取捨、外部系統的怪癖、看程式碼看不出來的前提。
- 不寫**做了什麼**：複述程式碼的註解是罐頭註解（AI 痕跡），審查會當缺陷退回（03 B6）。
- 改程式碼時同步改受影響的註解——過時的註解會誤導下一個讀的人，比沒有更糟。
- **編譯器或 linter 要求一定要寫 doc 註解時，不補空殼**（`<summary>Handle</summary>`、`/** Constructor. */`、空 docstring 這種）：對外公開的成員改寫成一句有內容的說明（職責、邊界、前提）；工具不要求的內部成員，空殼直接刪；真的沒東西可寫而工具仍要求，就在那個成員局部關閉該規則並寫一句理由。**不得自行整個專案關掉規則**（專案層 `NoWarn`、整份 lint 設定設成 off 這類）——真的要，先徵得使用者同意，{{依 init 註解規範那一題的結果三選一，照字面填、不得指向不存在的節：①選「建」→ 寫「並記進 `.claude/harness/07-comment-guide.md` 的「編譯器或 linter 要求一定要寫 doc 註解時」一節的設定表。」②選「沿用」，而既有文件本來就有處理強制 doc 註解設定的那一節、或使用者同意 init 補上那一節 → 寫「並記進 <既有文件路徑> 的「<那一節在既有文件裡實際的節名>」。」③選「不建」，或選「沿用」但既有文件沒有那一節、使用者也不補 → 寫「並在交接回報裡列出關了哪條規則、範圍與理由，由使用者決定記在哪。」}}
- 註解不留 AI 參與的痕跡：不引用內部文件出處或章節號（「依 CLAUDE.md §3」「見設計文件 §2」）、不寫「使用者指示」「依需求單」這類對話脈絡；維護者手上沒有那些文件，那只是指紋。

# 開發完成後的交接

完成後回報主對話，由主對話依 pipeline 派下一步（行為類 → qa-engineer → code-reviewer；分流例外 → code-reviewer）。

交接時需提供：

1. 修改或新增的檔案清單（絕對路徑＋關鍵行號）
2. 實作的功能說明（摘要即可）
3. 動到的共用元件與其使用點清單（無則寫「無」）
4. 需要重點審查的部分（若有）
5. build／編譯結尾輸出（`{{前端 build 或 lint 指令}}`，最後 5 行）

回報一律用「路徑＋行號＋一句說明」，**不得貼大段程式碼**（超過 10 行改寫成「見 <路徑>:<行號>」）。

未通過 code-reviewer 審查的程式碼不得視為完成。
