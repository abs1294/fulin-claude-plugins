# 實例化改編原則（adaptation guide）

骨架填空之外的判斷都在這裡。來源：fulin 主力業務專案的完整版 harness（01~06＋十餘支 guard hooks＋知識容器），與兩個實例化實戰（fulin-claude-plugins 手動版、首個標準實例）的教訓。

## 1. 原則：開發流程骨幹全帶，事故型條款留在各實例

舊原則是「不預載事故條款、不帶 guard hooks」，結果 init 只產出幾份填空文件、零可執行物——**把「怎麼確保規則真的生效」整個交給模型自覺，而骨架收錄的每一條事故都在說自覺不夠**。skill 或制度檔寫「必須」是自律，AI 會繞；只有 hook 是他律。

新原則：**開發流程骨幹全帶，事故型條款留在各實例**（從實例的 memory 長出，由 `/harness:review` 健檢時從該實例的紀錄列進提案，同一件事反覆出錯就提升格）。實測來源專案判斷矩陣 43 條判準：22 條純通用、18 條參數化後可通用，只有 3 條綁死來源專案的工作法——但這 3 條挖空後的形狀都還成立，已全數帶過來：本機覆寫在 0.9.0 帶成 03 A9；多站鏡像與環境檔歸屬在 0.10.0 帶成 03 B24（同構檔必掃另一側）與 B25（自己起服務就配自己的環境檔）。不帶的只剩各條綁專案的細節。

### 1.1 帶／不帶的判準

| 內容類型 | 處置 | 例 |
|----------|------|----|
| **純行為紀律** | 骨架原文照搬，不因專案改動 | 停損信號、熔斷條件、三重自查、回報鏈鐵則、隔離驗證、指揮官不下場、紅→綠→驗證 |
| **可參數化的判準** | 帶，把專案事實挖成 `{{}}` 由 init 填 | build 指令、測試目錄、QA agent 名、本機覆寫檔清單、稽核工具指令 |
| **開發流程骨架** | 帶，依盤點結果自動裁切＋使用者刪改 | agent pipeline、配套三條、五支通用 agent、知識容器、機械閘範本 |
| **綁死特定工作法的條款** | **綁專案的細節不帶；挖空後形狀還成立的，形狀帶** | 多站鏡像：形狀已帶成 03 B24（同構檔必掃另一側、差異三類分級、存量豁免），不帶的是「哪些目錄同構、同構率多少」這類來源專案的實測。環境檔歸屬：形狀已帶成 03 B25（自己起服務就配自己的環境檔），不帶的是來源專案那份最小環境清單與對應的環境對齊閘。仍整條不帶的：綁特定服務拓撲的多 worktree 稽核裡的埠號對照與連通性實測。⚠ 本機覆寫（hack）管理**不在此列**：它挖空後的形狀（逐檔備份、擋銷毀、開場點名、救回、分支條件、必要字串）是通用的，已參數化成 `hook-catalog.md` 第 16–18 列的 C 類 hook，Phase 1 偵測到本機覆寫就裝；「從新工作樹起服務時漏帶覆寫」挖掉工作樹路徑與起服務指令後形狀也成立，參數化成第 19 列的 C 類 hook（起服務指令樣式放填空區），「覆寫全帶齊、鏈路照樣不通」那一層以 03 的 A9 文件條款帶過去 |
| **事故型條款**（某第三方套件的坑、某次事故的細則） | 不進骨架；由目標專案 memory 長出，或由 `/harness:review` 健檢時從該實例的紀錄列進提案，同一件事反覆出錯就提升格 | 某元件的量寬 bug 繞法、某閘道把錯誤碼壓平 |
| 診斷書（01）、交接信（06） | 內容不進骨架——那是各專案自己的病歷與遺囑；骨架只帶「何時建、照什麼結構建」 | `skeleton-05` §7 |

**判斷測試**：
1. 這條換一個語言／產業還成立嗎？成立＝通用，照搬。
2. 不成立，但把專案事實挖空後剩下的「形狀」還成立嗎？成立＝參數化後帶。
3. 挖空後就沒東西了（整條都在講某個專案的特定工作方式）＝不帶。

### 1.2 誠實條款

init 產出的是**骨架＋長出資產的路徑**，不是「一套成熟的 harness」。成熟 harness 的組成除了制度檔，還有數十到上百條踩坑記憶、數百支回歸測試、每個模組的覆蓋登記——init 只能給第一項的骨架，其餘要目標專案自己跑出來。收尾回報必須講清楚這件事（SKILL.md Phase 5）。

## 2. 既有治理層的讓位規則

**先分清楚是哪一種既有設定**，兩種的對待方式相反：

| 既有的東西 | 對待方式 | 理由 |
|---|---|---|
| Claude Code 自己的設定：`CLAUDE.md`、`.claude/`（agents、hooks、commands、skills、settings），含之前裝過的 harness | **參考來源，不讓位**：整份備份後當盤點證據，逐項沿用／併入／取代，經使用者核對（SKILL.md Phase 0-2、Phase 1 第 12 項、Phase 2 第 5 項） | 使用者在已有設定的專案跑 init，代表他覺得原本的流程有問題；讓位等於把他想換掉的東西原樣留著。但裡面的專案事實與知識條目不會因為換流程而失效，一律留下 |
| 多工具共用的治理層：AGENTS.md、.agents/、.cursor/、copilot-instructions | **讓位**（下列規則）；只給某一個 AI 工具讀的規則檔另有第二種選擇，見 §2.2 | 不只 Claude 在用，改掉會影響別的工具與別的人 |

目標 repo 已有 AGENTS.md／.agents/ 這類治理層（常見於多工具協作 repo）時：

- 開發流程（sizing、gate、review checkpoint、stack 限制）正本＝它；harness 實例**只管 Claude Code 特有層**：subagent 模型派工、停損熔斷、隔離驗證、memory 協議。
- 路由中心（CLAUDE.md）明寫分工與衝突仲裁順序；04 的【開工前必讀】改接該治理層的檔案；**模板五改走（A）讓位版**（不建 pipeline 編排）。
- 目標專案已有自己的 agents → 不建同名通用 agent，02 對照表、check-agent-model 的名單、`check-review-discipline.js` 的 `REQUIRED_MARKERS` key 與 `DOC_SECTION_RULES` 的 agents 改填既有名稱（沒改 key 的角色不受派工檢查）。預設模型照 §2.1 對應，不一律套 sonnet。
- 該治理層檔案列入實例 05 的紅區（通常已入版控＝共用資源）。
- 引用它的內容時**先驗證**（實查目錄與檔案，勿信其自述——實戰抓過治理層自己的文件漂移：宣稱有測試目錄實際沒有）。

### 2.1 沿用原有 agent 時的預設模型

原有 agent 的名字與 harness 骨架不同，但職責對得上某一級——照職責給預設模型，不看名字：

| 原 agent 的職責 | 對應骨架哪一級 | 預設模型 |
|---|---|---|
| 寫規格或做設計：需求規格、UX／產品規格、系統架構、API 契約、資料模型 | `backend-architect` | `opus` |
| 照規格實作（前端、後端、手機、元件庫） | `*-engineer` | `sonnet`（02 的進階判準任兩項成立改 `opus`） |
| 測試 | `qa-engineer` | 不低於它要驗的那支實作用的模型 |
| 審查 | `code-reviewer` | `sonnet` |
| 純機械（批次改名、格式轉換、整理清單） | — | `haiku` |

原 agent 檔的 frontmatter 自己寫了 `model` 的，照原檔，不改。理由：寫規格的角色出錯，後面每一棒都照著錯的規格做，錯的代價最大；實際發生過沿用原有的規格 agent 時被套成 sonnet，使用者看到模型對照表才要求改成 opus。

### 2.2 只給某一個 AI 工具讀的規則檔：讓位，或精煉成自有正本

`.github/copilot-instructions.md`、`.github/instructions/*.instructions.md`、`.cursor/rules/`、`.windsurfrules` 這類檔，寫給**另一個** AI 工具讀，常由別人維護（客戶、別的團隊）。它們跟 AGENTS.md 不同：不是多工具共用的開發流程，而是那個工具的提示詞。init 在 Q7（動手前必讀）對每一份給兩種選擇：

| 選擇 | 做法 | 適合 |
|---|---|---|
| **讓位**（預設） | 原檔照讀，列進必讀；不另寫一份 | 內容跟 repo 現況對得上、篇幅小、Claude 直接讀不會讀錯 |
| **精煉成自有正本＋已知矛盾表** | 原檔不動、Claude 不再直接讀它；把其中適用的規則精煉成 `.claude/harness/review-rules.md`（骨架 `skeleton-refined-rules.md`），每條註明出自原檔哪一節；原檔跟 repo 現況或其他規範衝突的地方，列進同一份檔的「已知矛盾表」並寫明本專案照哪一邊 | 原檔篇幅大、夾雜那個工具專屬的寫法（`applyTo` 這類標頭、給它的語氣指示）、或已經跟現況對不上——Claude 直接讀會照著過時的規則審 |

精煉的代價是兩份要同步：原檔改版時，自有正本不會跟著變。所以選精煉時，05 健檢清單加一列「原檔改版了沒（比對精煉時記下的原檔版本：commit 或修改日期）」；審查員（code-reviewer）的規則來源與「改到哪類檔就照哪份規則審」表改指向自有正本，不再列原檔。

## 3. 外向邊界判定

- `git remote -v` 指向客戶／外部伺服器 → 實例 CLAUDE.md 必寫「push 前徵得同意」；實例落點預設 workspace 根（不進 repo）。
- workspace 內有憑證／VPN／機密目錄 → 絕對邊界寫明「不得出現在 commit、文件、對外輸出」。
- Phase 1 外部副作用路徑掃描的命中（寄信、外部 API、毀滅性 SQL、部署、金流、實機、資料管線）→ 經 Q2 確認後進 03 C2 與 CLAUDE.md 絕對邊界。
- commit 不加 AI 署名屬全域規則，實例只需提醒適用範圍，不重複條文（SSOT）。

## 4. 去專案化檢核

### 4.1 污染詞表（黑名單）

詞表正本＝`../pollution-wordlist.txt`（機器可讀，一行一個 regex 片段；Phase 5 靜態驗收與 `hooks/wordlist-sweep.js` 共用同一份）。用法：

```
# 實例驗收（Phase 5）：命中逐筆判斷，changelog 出處標註除外
grep -rniE "$(grep -v '^#' <plugin>/skills/init/pollution-wordlist.txt | grep -v '^$' | paste -sd'|')" <實例檔案們>
```

**維持黑名單的理由與它的兩個限制**（改詞表前先讀）：

- 黑名單是使用者裁決保留的做法——白名單（只准出現某些詞）對自由文字不可行。
- **限制一：它只擋已知**。新回收一批條款時，新的來源專案詞不會自動進表；表裡沒有的詞，驗收一律「0 命中」＝假的乾淨（03 B22 同一個病）。
- **限制二：詞表本身就是來源專案的技術棧指紋**。它列的是「某個專案的業務名詞、系統代號、port、專屬腳本」——換一個來源專案回收條款，表就得跟著長。目標專案若自己的技術棧正好含表中某詞，實例驗收時要逐筆判斷「目標專案查證過的事實」還是「骨架漏進來的來源事實」，不要一律刪。
- 所以要有一道機制在適當時機提醒更新詞表 → §4.2。

**0.3.0 從詞表移除的詞**（因為現在是骨架刻意帶的通用名，不再是污染）：`qa-engineer`、`frontend-engineer`、`backend-engineer`（通用 agent 名）、`CONTEXT.md`、`FLOWS.md`（知識容器）、`playwright`（qa-webwright plugin 的正式依賴）。`COVERAGE.md` 仍在表內（只比對檔名，不比對「coverage」這個通用詞）——骨架帶的是覆蓋登記的**形狀**（`skeleton-05` §5.1，檔名用 `{{覆蓋登記檔}}` 填空），不帶來源專案的檔名，所以它仍是來源專案的專屬名。

### 4.2 詞表維護觸發

**時機**：動到骨架檔（`references/` 底下任何檔、`hooks/templates/`、詞表本身）要 commit 時。

**形狀**（仿知識沉澱閘）：plugin 自帶 PreToolUse hook `hooks/wordlist-sweep.js`——staged 含骨架檔時，要求 git-commit 的 args 帶 `詞表=<答案>` 表態，並把已知詞在 staged 內容中的命中列出來。答「無」零成本，漏答才擋；只驗有沒有表態，不判內容對錯。其他 repo、其他改動一律放行（所以一般專案裝了 harness plugin 不會被擋）。

**為什麼選「紀律＋hook」而不是只寫紀律＋健檢清單項**：

1. **觸發點與健檢週期錯位**：健檢 30 天跑一次，但骨架一旦發布，污染就已經進了別人的實例——等健檢抓到時已經擴散。
2. **會漏想新詞的正是改骨架的那個 session**：它剛從某個實例搬條款過來，腦中那些詞是「日常用語」而不是「專案特徵」，最不可能自發地想到要補表。自律在最需要的時候最不可靠。
3. **成本低**：只在 git-commit 且 staged 含骨架路徑時觸發，一般使用不會碰到；表態制不需要判斷語意，不會誤擋。
4. **機械部分與表態部分分工**：已知詞命中由 hook 直接列出（這部分機械可判）；新詞只能靠人判斷，所以用表態逼出「有沒有想過這題」並留在 transcript 讓使用者可否決。

沒裝 git-commit plugin 的維護環境，這支 hook 不會觸發——改用純紀律：發布前手動跑 §4.1 的掃描指令，並回答同一題。

### 4.3 引擎側發布前掃描

骨架改版發布前，對 `references/`（含 `agents/`、`containers/`）與 `hooks/templates/` 全掃一次詞表，另掃日期戳：

```
grep -rnE '20[0-9]{2}-[0-9]{2}-[0-9]{2}' <上述目錄>    # 條款區應為 0；事故一律只講機制不寫日期
grep -c '^| [ABC][0-9]' references/skeleton-03-judgment-matrix.md   # 03 條款數（0.10.0＝43：A 9／B 25／C 9），不得因改版意外掉條
grep -rn --include='*.md' '^## Changelog' references/              # 0 筆：骨架檔不放 changelog 節（規格見 skeleton-05 §4）
```

## 5. 骨架維護（引擎側）

- 骨架檔屬本 plugin，改動走 monorepo 慣例（bump 版本＋publish）。
- **回收條款的門檻**：某實例的升格條款要進骨架，必須「≥2 個專案獨立踩過同類坑」或「與專案無關的純行為紀律」或「參數化後形狀仍成立」（§1.1 判斷測試）；單一專案的事故留在該實例，由該實例的 `/harness:review` 健檢管；`/harness:review` 只看單一實例，跨專案比對「是不是 ≥2 個專案都踩過」目前由維護者人工做。
- 回收時照 §1.1 挖空專案事實、**事故只講機制不寫日期**（「靜態審查看不出跑起來才會出的錯」，不寫「某月那次」），並過 §4.2。
- 骨架改版**不回寫既有實例**——實例自治，要同步由各專案自己依其 05 紅區流程決定。plugin 更新覆蓋的只有骨架、範本與本指南，永不觸碰任何專案的 `.claude/harness/`、`.claude/agents/`、`.claude/hooks/`。
- **骨架檔不放 changelog 節**：骨架本身的變更記在 plugin 的 `CHANGELOG.md`；實例的變更紀錄落點由 `skeleton-05` §4 規定（harness 目錄記 `.claude/harness/CHANGELOG.md`、agent 記 `.claude/agents/CHANGELOG.md`、根目錄檔記 `<主檔名>.changelog.md`、`tests/Project_Detail/` 記同目錄 `CHANGELOG.md`），init 時「建立」那一行由 `skeleton-harness-CHANGELOG.md`、`agents/skeleton-agents-CHANGELOG.md`、`skeleton-CLAUDE.changelog.md`、`containers/` 底下的紀錄骨架寫入。
- hook 範本複製到實例後同樣自治：plugin 更新不會自動同步，實例要同步就對照 `hooks/templates/` 手動合併。

## 6. 已知的實例差異（現況登記）
