> **收錄原則**：只收「踩過坑」或「橫跨 ≥2 個{{模組單位，例：repo／服務／模組}}」的鏈路，**每條掛事故收據**——這不是全量架構文件，是防「跨層漏同步」的地雷圖。層級路徑寫進來前要實地查證，修改前仍以程式碼現況為準。
>
> **維護紀律**（正本＝`.claude/harness/04-delegation-templates.md` 共通規則）：
> - 動到本檔已收錄鏈路上任一層的任務，**開工前必讀本檔**。
> - 完工報告**必答「鏈路其他層是否需同步」**（答「不需要」也要附一句理由）。
> - 新事故涉及新鏈路時，隨 memory 一起補進來（同步在 `FLOWS.changelog.md` 補一行）。
>
> 為什麼要有這份：跨層漏同步的失敗形狀幾乎都是**靜默吞掉、不報錯**——加了一個欄位，四層只同步了三層，中間那層把它丟了，畫面上就是「沒顯示」，看起來像前端的錯。

### 鏈路條目格式

```
## 鏈 N：<一句話講這條鏈在做什麼>

<層與層的流向，一行箭頭圖>

| 層 | 檔案 | 關鍵點 |
|---|---|---|
| <層名> | <路徑> | <這一層容易漏什麼／規律是什麼> |

命名規律：<這條鏈每一層的檔名或路徑怎麼命名（例：各模組的轉發層都叫 `<模組>Gateway`），讓讀者照規律找到其他模組的同一層，不必每條都列>

**⚠️ 動這條鏈的紀律**：<動哪裡要同步哪裡>
事故收據：<一句話講發生過什麼、後果是什麼——不寫日期，寫機制>

**⚠️ <另一個陷阱，一句話標題>**（同一條鏈可以有好幾段 ⚠️，一段講一個陷阱）
<症狀與判斷方法；照直覺做會得到什麼錯誤結論>

**要改的地方**（某類改動要同時動好幾處時，列成表；缺一處就壞的才列）：

| 要改的地方 | 位置 |
|---|---|
| <例：呼叫端的網址字串> | <路徑或命名規律> |
| <例：接收端的路由> | <路徑或命名規律> |
```

#### 外部契約鏈（我方與外部系統之間的格式約定）

鏈的一端是外部系統、而且踩過「我方照自己慣例送、對方其實不吃」的坑時，加一張對照表：

```
**⚠️ 這條鏈跟外部系統的約定**（<查證方式與日期，例：對方測試站實際回應>）

| 面向 | 對方實際 | 我方慣例 | 送錯的下場 |
|---|---|---|---|
| <路徑／參數名／回傳欄位名／日期格式／錯誤碼> | <對方真的吃或回的寫法> | <我方其他地方的寫法> | <回 404／400／靜默給空值、不拋例外> |

契約文件的可信度：<契約文件路徑>＋<它跟實際回應對得上還是對不上；對不上時寫「以對方實際回應為準，不可照文件實作」>
```

- 「送錯的下場」最要寫的是**靜默**的那種（不報錯、只是值變空或被吞成預設值）——會報錯的錯，下一個人自己會發現。
- 契約文件跟實際回應不一致時，寫明以哪個為準；沒寫的話下一個人會照文件改回錯的寫法。

## （示範）鏈 1：前端顯示後端新增欄位

```
資料庫欄位 → 資料存取層映射 → API 回應 DTO → 前端 API 模組 → 畫面元件
```

| 層 | 檔案 | 關鍵點 |
|---|---|---|
| 資料存取層映射 | `<後端資料存取層路徑>` | 手寫映射時新欄位不會自動帶出 |
| API 回應 DTO | `<DTO 路徑>` | 序列化只輸出 DTO 上有的欄位，漏加＝前端永遠拿不到 |
| 前端 API 模組 | `<前端 API 模組路徑>` | 若有欄位轉換（命名風格轉換），確認新欄位有經過 |
| 畫面元件 | `<元件路徑>` | 顯示欄位清單通常是另一個設定陣列 |

命名規律：（示範）每個模組的 DTO 都在 `<後端>/<模組>/dto/` 底下、前端 API 模組都叫 `<模組>Api`——照這個規律可以找到其他模組的同一層。

**⚠️ 動這條鏈的紀律**：加欄位給畫面看＝**四層全同步**，漏任何一層都是靜默吞、不報錯。
事故收據：（示範）新增欄位只同步了三層，DTO 漏加，畫面顯示空白，被當成前端問題查了一輪。
