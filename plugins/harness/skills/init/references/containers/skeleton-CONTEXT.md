> **本檔只放語言，嚴禁實作細節**。收錄鐵則三條：
> 1. **IS not DOES**——條目只答「這個詞是什麼」，不答怎麼查、怎麼流動、存在哪。
> 2. **本專案特有**——通用程式概念（timeout、cache、分頁）不收，那些歸 memory。
> 3. **每條 ≤2 句**——寫不進兩句代表還沒想清楚，或者混進了實作細節。
>
> 分工：事件與坑歸 memory、跨模組鏈路歸 `FLOWS.md`、架構拓撲歸 `CLAUDE.md`——與本檔重疊即違規。

### 何時寫（四個當場觸發時機）

**當場寫，不要批次。** 一個詞在對話中被釐清的那一刻就補進來——留到 commit 前才補，那一整輪已經在用未定義的詞做判斷了。{{若有裝 guard-sediment-sweep hook 加：commit 前沉澱四問（`.claude/hooks/guard-sediment-sweep.js`）管的是「最後有沒有落檔」，本節管的是「當場有沒有攔下來」；兩者是接力，不可互相取代。}}

| 觸發 | 動作 |
|------|------|
| 使用者用的詞與本表定義衝突 | 當場點出：「本表把 X 定義成 A，但你講的像 B，是哪個？」 |
| 使用者用了模糊或一詞多義的詞 | 提精確替代：「你說的『帳號』是指登入帳號還是客戶帳戶？那是兩回事」 |
| 在討論兩個概念的關係 | 用具體情境壓力測試，逼出邊界（「那退件重送算同一筆還是新的一筆？」） |
| 使用者說某東西怎麼運作 | 去看程式碼同不同意，矛盾就當場攤出來 |

最後一條最常救回時間：不只記錄使用者說的，還拿程式碼對帳——「你的碼是整張訂單取消，但你剛說可以部分取消，哪個對？」詞義沒對齊時，常見的誤判是把「顯示狀態」當成「實際狀態」，然後把預期行為當成缺陷去修。

⚠ 例外一條：**業務上「該不該」的問題不要靠讀碼下判斷**——碼只能答「現在怎麼做」，答不了「本來該怎麼做」。碼與使用者說法矛盾時攤出來問，不要自己選一邊。

### 詞條格式

```
**<詞>（<子域：這個詞只在哪個模組／業務範圍有這個意思；全專案通用就省略括號>）**
<它是什麼，≤2 句。只講 IS，不講 DOES。>
_避免_：<容易混淆的近義詞或另一個子域的同名詞>——混了會誤判成什麼（例：把預期行為當成缺陷、改錯層、撈到別人的資料）
```

- **子域標籤**：同一個字在不同模組指不同東西時（「狀態」在訂單與在審核流程是兩回事），每個意思各一條，用括號標子域區分；標籤用本專案自己的模組或業務名，第一次出現的子域名也要有自己的詞條或在 `CLAUDE.md` 專案概要找得到。
- **`_避免_` 寫後果，不只寫近義詞**：只列「不要叫它 X」，讀者不知道叫錯會怎樣，下次還是會混；寫出「混了會誤判成什麼」，讀者才知道這條值得停下來查。
