## Phase 3 — 訪談（專案理解 3 題＋流程設定 10 題，參考模式加問第 0 題與 Q8，有本機覆寫候選時加問 Q9；**一次一題**）

順序：Q0（參考模式）→ U1 環境 → U2 進度 → U3 專案詞 →〔Q4 單人／團隊＋Q10 用語表匯入＋Q11 註解規範，合成一則訊息〕→ Q1 → Q2 → Q8（參考模式）→ Q3、Q5～Q7 → Q12 選裝 skill → Q9（有本機覆寫候選）。Q11 在 0.15.2 以前排在 Q7 後（它問的是要不要多一份動手前必讀的註解規範，緊接在必讀文件那一題後面最好懂）；0.16.0 起併進 U3 後面那一則合併訊息，因為它的推薦只看 Phase 1 第 6 項盤點到的註解三件，不看 Q7 的答案。Q12 排在 Q11 後：選裝的工作流地圖要列出這次建的每支 skill，前面的題目都定了才列得完整；它也要知道 Q5 有沒有保留本機覆寫保護（決定要不要一併產生本機覆寫說明）。Q9 排在 Q5 後：本機覆寫保護三件組在 Q5 被取消時就不問。Q8 排在 Q2 後、Q5 前：它選出來的條款要跟 Q2 的危險動作一起推導 Q5 的自動檢查。Q10 緊接 U3：剛確認完詞條，使用者對這份表多大、多常用最有感。**先問專案、再問流程**：U1 的答案決定 Q2 有哪些危險動作，U2 的答案決定 Q7 推薦哪些文件，流程設定要建立在確認過的專案事實上。

**一次一題，不要湊成一次 AskUserQuestion**——每題的答案會改變後面題目的選項（Q1 裁掉 frontend-engineer，Q5 的 hook 名單就跟著變）。

**唯一的例外：Q4、Q10、Q11 合成同一則訊息問**（講法見 `questions/how-to-ask.md`「合併一則」）。這三題可以一起問，是因為彼此的答案不影響另外兩題的選項與推薦：Q4（單人或團隊）決定落點、settings 檔與改規則要問誰；Q10（用語表要不要每次自動載入）只看詞彙表大小與「當場發現講法對不上」的機制；Q11（要不要建註解規範）只看 Phase 1 第 6 項盤點到的註解三件。三題也都不改變後面任何一題的選項（Q1 的角色、Q2 的危險動作、Q5 的自動檢查清單都跟它們無關）。其餘題目維持一次一題，不准再自行合併。合併訊息裡三題各自附推薦與理由，使用者只答其中一兩題時，沒答的那幾題單獨再問一次。

**每答一題就寫進答案檔**（SKILL.md 硬規則 4）：`node <本 plugin>/skills/init/scripts/init-flow.js answer <目標> <題號> --json '<JSON>'`（JSON 含引號、在 PowerShell 不好跳脫時，先寫進暫存檔再用 `--file <暫存檔>`），JSON 形狀 `{"asked":"<問了什麼，一句話>","answer":<使用者的答案>,"data":{…}}`。腳本負責補日期、合併進 `init-answers.json`、驗格式；無人值守時代決的加 `"delegated":true`；條件不成立而跳過的題寫 `{"skipped":{"reason":"<原因>"}}`（收尾回報那句「那一題沒問」照這個原因寫）。合併訊息的三題各寫一筆。`data` 是給 `init-verify.js` 機械驗收用的，下列幾題一定要填：

| 題 | `data` 必填欄位 |
|---|---|
| U3 | `confirmedTerms`（這次確認新增的詞，字串陣列；無人值守是空陣列）、`removedTerms`（U3 裁決刪除的原條目）、`originalCount`（參考模式沿用的原有真詞條數；一般模式 0） |
| Q1 | `agents`（最後定案要建的 agent 檔名，不含 `.md`） |
| Q4 | `team`（布林：團隊＝true）；答完後腳本把 `landing` 改成落點（團隊＝repo 根、單人＝workspace 根；多 repo 工作區的團隊模式用 `"landing":"<repo 路徑>"` 指定） |
| Q10 | `import`（布林：匯入＝true） |
| Q11 | `choice`（`build`／`reuse`／`none`） |

重裝（參考模式、備份裡有上一次的 `init-answers.json`）：每一題的推薦選項先用上一次的答案，對使用者講明「上次你選了 <答案>」；使用者改了就照新的寫。每題都附**推薦選項與一行理由**（未附推薦會被 check-ask-discipline 閘擋下，也是三重自查有做的證據）。條件問的題目條件不成立就跳過，並在收尾回報記「<題目主題>那一題沒問：<原因>」（例：「沒有畫面時怎樣算做完那一題沒問：專案有網頁畫面」），不寫內部代號。

### Q1 的預設 pipeline（原版照搬）

```
[對齊回合] → backend-architect 設計 → backend-engineer 實作 ┐
             frontend-engineer 實作（等 API Contract 確認後）┘
           → qa-engineer 測試計畫＋開畫面實測＋codify
           → code-reviewer 審查 → 完成
```

**配套三條（裁切不拿掉，Q1 一併展示）**：

1. **無條件對齊回合**：行為類需求開工前必過一回合、不可跳過——有決策型解讀分岔就逐題訪談到清零；無分岔就明說「無分岔＋一句理由」讓使用者可否決才開工，靜默開工＝違規。
2. **QA 先於 review**：行為類一律先 QA 實測、再送審查——靜態審查看不出跑起來才會出的錯。
3. **分流例外**：純結構／文案／死碼等「靜態可確定等價」者，可審查過即完成、QA 可評估跳過（判準＝正確性能否只靠讀 code 確定）。

### Q5 的 hook 清單怎麼來：照形狀目錄推導，不是從菜單挑

正本＝`references/hook-catalog.md`（來源專案的 hook 與 plugin 自帶閘，加上之後新增的各列，實際列數以它的目錄表為準；逐支拆成「通用形狀＋觸發條件＋專案參數」，分 A 必裝／B 盤點觸發／C 工作法觸發／D 由 plugin 提供／E 長出來才裝五類）。**沒有數量上限**——裝幾支由這個專案的事實決定。

推導（事實判定，不問使用者）：

1. 形狀目錄逐列判觸發條件，用 Phase 1 十三項與 U1、Q1–Q4 的答案（參考模式：原有 hook 照「原有設定的預設處置」逐支判定取代或沿用，沿用的也列進 Q5 清單，標「原本就有」）。
