# 04 — 標準化派工 Prompt 模板

> SSOT：派工 prompt 怎麼寫，只信本檔。修改權限：紅區（新增模板屬黃區，見 05）。
> 用法：複製對應模板 → 填掉所有 `<...>` 填空 → 發 Agent tool。**任何 `<...>` 留空就不准發**。
> 派工前先過 `02-model-dispatch.md` §6 的 10 秒自查。

## 共通規則

### 回報鏈鐵則（防「完工但回報斷掉」）

1. **禁止二次轉派**：每個派工 prompt 必寫「本任務由你親自執行，不得再轉派給其他 agent」——回報鏈固定一跳。需要多個 agent 時由主對話自己分別派、分別收。
2. **回報指示放頭尾各一次**：完成後的回報要求寫在 prompt **第一行與最後一行**各一次（抗長 context 遺忘）。
3. **主對話端磁碟驗收（最關鍵的防線）**：收到完成通知一律**直接查磁碟驗收產出**（git diff / grep / mtime），不空等、不催討自述回報——自述只當補充，磁碟才是驗收依據。
4. **「等待型 agent」＝反模式，禁用**：不得派「A 等 B 完成後彙整轉送」的中繼 agent。需要整合多份產出時，由主對話自己收齊再整合。
5. **禁背景 job**：派工 prompt 明令前景執行，subagent 開背景 job 會停下等通知、零產出。

### 其他共通規則

- 路徑一律用**絕對路徑**（subagent 不共享你的對話脈絡，「剛才那個檔」它看不懂）。
- 【邊界】必含搜尋範圍限制：**搜尋一律限定 repo/workspace 目錄，禁止全碟掃描**（殭屍程序不隨 agent 結束，曾有燒 7 小時 CPU 的前例）。
- 已知的坑（memory 條目）要**內聯進 prompt**，不要叫 subagent 自己去翻 memory（它讀不到你的 MEMORY.md 索引）。
- 實作型派工必附**「開工前必讀清單」**：{{填來源：既有治理層的載入規則挑相關檔絕對路徑／各 repo CLAUDE.md／專案規範文件；沒有就刪此段但保留模板欄位}}。subagent 開工第一步是 Read 完清單，且回報必列「已讀清單」——缺這欄或清單不齊，直接退回重報。
- 回報格式鐵則：**成果路徑＋關鍵行號＋結論；禁止噴大段代碼**（>10 行的代碼引用一律改成「見 <路徑>:<行號>」）。
- 驗收條件必須可機械判定。自查法：每一條都能回答「用什麼指令或什麼觀察來判定 PASS/FAIL？」。
- **診斷型任務（查 bug root cause）派工 prompt 必含一句**：「拿到可重現的紅指令前禁提 root cause；先列 3~5 個可證偽假設才准測；修復必走 red→green→verify：先寫紅的回歸測試看它紅 → 修到綠 → 回跑原始紅指令確認症狀消失，缺任一步不算修復完成。」（子 agent 不會自主採用紀律——紀律必須 inline 進 prompt）

## 模板一：搜尋研究型（agent type：`Explore`（唯讀）或 `general-purpose`；model：`sonnet`）

```
【目標】回答這個問題：<一句話問題>
【背景】<為什麼要查；已知線索；相關目錄的絕對路徑>
【已排除】<已經查過、確定不是的方向——避免它重查>
【搜尋範圍】<目錄/檔案類型；禁止全碟掃描>
【驗收條件】
- 回答覆蓋 <N> 個面向：<列出面向>
- 每個結論都附檔案路徑＋行號佐證，無佐證的推測要標「推測」
【回報格式】
- 結論（≤5 行）
- 證據清單：<路徑>:<行號> — <一行說明>（每條一行）
- 沒找到的部分明說「沒找到」，不要編
```

## 模板二：功能實作型（agent type：{{專案實作 agent 或 `general-purpose`}}；model：`sonnet`，命中 02 §1 進階判準則 `opus`）

```
【目標】實作：<功能一句話>
【計畫／設計文件】<絕對路徑；沒有計畫就先回頭做計畫，不要無計畫就派>
【開工前必讀】（第一步：逐檔 Read 完以下清單再動工，一個不准跳）
- <{{必讀清單來源，同共通規則}}的絕對路徑，與本任務相關的全列>
【背景】<要動的模組；相關既有程式碼的絕對路徑（參考 pattern 用）>
【已知的坑】（照抄，不要省；從 memory 撈，沒有就寫「無」）
- <memory 條目內文>
【邊界】只准動 <目錄/檔案清單>；禁止動 <清單>；禁止重構不相關代碼；本任務由你親自執行，不得轉派；前景執行，禁背景 job
【驗收條件】
- build 0 error（指令見 03 矩陣 B 本專案驗證指令）
- <功能行為條款，逐條可觀察>
【回報格式】
- 已讀清單：逐檔列出實際 Read 過的必讀檔案（與【開工前必讀】逐一對應，缺一檔=整份回報退回）
- 動了哪些檔：<路徑>（新增/修改）每檔一行＋一句做了什麼
- 關鍵決策（若有偏離計畫，說明原因）
- build 結尾輸出（最後 5 行）
- 自認未完成或不確定的點（誠實列出，不列=聲明全部完成）
```

## 模板三：代碼重構型（model：`sonnet`；批次套用配方時 `haiku` 可）

```
【目標】重構：<一句話；例：把 X pattern 全部改成 Y pattern>
【配方】（由指揮官或高階模型先解出，含一個已完成的範例）
- 改什麼：<精確描述>
- 改成什麼：<精確描述>
- 範例 diff：<已改好的那個檔的路徑>，照它的樣子改
【對象清單】<明確檔案清單（先用模板一查出來），不要叫它自己找>
【邊界】行為不可變：只改結構不改邏輯；禁止順手修別的
【驗收條件】
- build 0 error
- grep "<舊 pattern>" 在對象範圍 = 0 matches（replace 後必須實際跑 grep 驗證，不可只宣稱）
- grep "<新 pattern>" 命中數 = 對象清單數
【回報格式】
- 每檔一行：<路徑> — 改了 <N> 處
- grep 驗證的實際輸出（兩個 grep 的命中數）
- 跳過的檔案與原因（若有）
```

## 模板四：Fresh-Context 驗證型（agent type：`general-purpose`；model：`sonnet`）

> 用於 02 §5 隔離驗證。**只給驗收條件與成果路徑，不給實作者的自述**。

```
【目標】驗證以下產出是否達成驗收條件（你是驗證者，預設立場：不相信它完成了，找證據）
【產出路徑】<檔案清單，絕對路徑>
【驗收條件】（逐條判定）
1. <條件一>
2. <條件二>
【驗證方式】
- 重新 Read 每個產出檔（讀檔尾確認未截斷）
- <需要實跑的指令>
【回報格式】
- 每條驗收條件一行：條件 N → PASS/FAIL — 證據（<路徑>:<行號> 或指令輸出關鍵行）
- 總判定：全部 PASS / 有 FAIL（FAIL 必附「差在哪、建議修法一句話」）
- 額外發現的問題（不在驗收條件內但明顯有害；標 🔴/🟡/🟢）
```

## 派工後的指揮官義務

1. 收到回報先掃「驗收條件對應」——subagent 沒逐條回應就退回重報，不要自己腦補。實作型回報同時核對「已讀清單」是否涵蓋【開工前必讀】全部檔案，缺就退回。
2. 回報 FAIL → 計入重試次數（02 §4 上限），修正 prompt 再派或升級。
3. 有價值的新坑 → 依 `05-knowledge-protocol.md` 寫 memory。
