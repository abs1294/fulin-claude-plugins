## 矩陣 A：停損換路徑信號（「方向錯了」，立刻停止原地重試）

命中任一條 → 停下當前修法，執行動作欄。「原地重試」定義：不改變假設、只微調程式碼再跑一次。

| # | 信號（量化） | 動作 |
|---|--------------|------|
| A1 | 【計錯誤出現次數】同一錯誤訊息第 **3 次**出現，且前兩次用了不同修法 | 停。寫失敗軌跡（格式見 02 §4），重新列出 3 個候選假設，逐一用證據排除，或升級 |
| A2 | 蹺蹺板：修 A 壞 B，修 B 又壞 A | 停。這是共同上游的架構層問題，往上找兩者的共同依賴，不要在 A/B 本身繼續修 |
| A3 | 發現自己在改「不是本任務要動的」框架檔、library 檔、共用工具檔，只為了讓錯誤消失 | 立刻停＋還原。99% 是自己用法錯，不是框架錯；wrapper／框架有 bug 時的正解是繞過它，不是改它 |
| A4 | 想用這些手段讓測試過：try/catch 吞錯、加 sleep、hardcode 測資、放寬斷言、skip 測試 | 停。這些全是「掩蓋」不是「修復」，沒有合法理由 skip |
| A5 | 【計工具呼叫總數】投入 **10 次以上 tool call** 而驗收條件的完成數為 **0** | 停。重讀任務描述，檢查是不是解錯題；向使用者或上級模型重述「我理解的任務」求確認 |
| A6 | 開始懷疑「是不是環境壞了／cache 髒了」而想重啟服務、清 cache、重裝套件 | 先停。這是狀態改變操作：先找到支持該假設的 log 證據（哪一行說明是環境問題），沒證據不准動環境 |
| A7 | 用**自己稍早訂下的範圍約束**（「本次不碰 X」）當理由，略過在 X 裡看到的明顯缺陷 | 停。約束是為了控制風險，不是免除思考。範圍外的缺陷至少要**明確回報給使用者**，不可靜默略過 |

**A1 反例（通用）**：同一個 500 錯誤出現第 5 次，每次只是換一個參數再打一次 API，從沒去看後端 log——這是消耗 context 的祈禱式重試。
**A3 反例（通用）**：為了讓 build 過，直接改 node_modules 或第三方套件解包後的內容。

## 矩陣 C：熔斷條件（停止自主作業，向使用者提問）

命中任一條 → 停止動手，整理好選項再問。熔斷不是失敗，**在錯誤方向上多燒 50k tokens 才是失敗**。

| C2 | 動作不可逆或外向：{{填本專案清單：push 到外部 remote、刪除資料、改 DB schema、動共用治理層檔案、改全域設定…}} | 要動什麼、為什麼、回滾方式 |

### 問使用者前的三重自查

按 AskUserQuestion 前逐項過，**任一命中＝禁問**：

1. **事實型**？答案能用 15 分鐘內查證得到（讀碼、查 memory、跑指令）→ 自己查。
2. **規則已裁型**？harness／CLAUDE.md／專案慣例已有明文答案 → 照規則做，回報中記一行「已照 X 處理」。
3. **可逆低價型**？選錯一行改回、或不影響可觀察行為 → 自己決，回報中列「已代決：X＝Y」供事後否決，不阻塞。

過完三關仍是「真決策＋無慣例可循＋選錯需返工」才准問，且**必附建議答案**；多個問題**湊成一次**發，**禁止逐項請示迴圈**。**本節管的是「請示」這個行為，不限工具**：用回覆文字結尾問「可否繼續／需要我接著做嗎」＝變相請示，同樣過三關；流程既定的下一步直接做，不問。

**查證動作也要湊一次**：自己已列得出要查的 N 項時，一次查完再回報，禁止「查一項→回報→再查下一項」的擠牙膏。對 prod 資料變更尤其適用：變更前一次講清影響全貌與筆數。

## 品味決策標準流程

1. 承認這是品味題（對照 C5），不假裝有正解。
2. 產 2~3 個**都能跑**的變體（不是口頭描述）。
3. 實際呈現各變體的可觀察差異（畫面或代碼差異表）。
4. 一張表：變體 ×（優點／缺點／工作量）。
5. AskUserQuestion 給使用者選，附自己的推薦與一行理由。
6. 使用者選定後，把決策寫進 memory（type: feedback），下次同類題直接引用。
