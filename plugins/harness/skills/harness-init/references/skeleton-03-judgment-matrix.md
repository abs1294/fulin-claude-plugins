## 矩陣 A：停損換路徑信號（「方向錯了」，立刻停止原地重試）

命中任一條 → 停下當前修法，執行動作欄。「原地重試」定義：不改變假設、只微調程式碼再跑一次。

| # | 信號（量化） | 動作 |
|---|--------------|------|
| A1 | 【計錯誤出現次數】同一錯誤訊息第 **3 次**出現，且前兩次用了不同修法 | 停。寫失敗軌跡（格式見 02 §4），重新列出 3 個候選假設，逐一用證據排除，或升級 |
| A2 | 蹺蹺板：修 A 壞 B，修 B 又壞 A | 停。這是共同上游的架構層問題，往上找兩者的共同依賴，不要在 A/B 本身繼續修 |
| A3 | 發現自己在改「不是本任務要動的」框架檔、library 檔、共用工具檔，只為了讓錯誤消失 | 立刻停＋還原。99% 是自己用法錯，不是框架錯；wrapper／框架有 bug 時的正解是繞過它，不是改它 |
| A4 | 想用這些手段讓測試過：try/catch 吞錯、加 sleep、hardcode 測資、放寬斷言、skip 測試 | 停。這些全是「掩蓋」不是「修復」，沒有合法理由 skip |
| A5 | 【計工具呼叫總數】投入 **10 次以上 tool call** 而驗收條件的完成數為 **0** | 停。重讀任務描述，檢查是不是解錯題；向使用者或上級模型重述「我理解的任務」求確認 |
| A6 | 開始懷疑「是不是環境壞了／cache 髒了」而想重啟服務、清 cache、重裝套件 | 先停。這是狀態改變操作：先找到支持該假設的 log 證據（哪一行說明是環境問題），沒證據不准動環境 |
| A7 | 用**自己稍早訂下的範圍約束**（「本次不碰 X」）當理由，略過在 X 裡看到的明顯缺陷 | 停。約束是為了控制風險，不是免除思考。範圍外的缺陷至少要**明確回報給使用者**，不可靜默略過 |

**A1 反例（通用）**：同一個 500 錯誤出現第 5 次，每次只是換一個參數再打一次 API，從沒去看後端 log——這是消耗 context 的祈禱式重試。
**A3 反例（通用）**：為了讓 build 過，直接改 node_modules 或第三方套件解包後的內容。

## 矩陣 B：任務完成判準（DoD——全部打勾才准說「完成」）

「完成」是二元的：以下適用項全過才算。部分完成就說「部分完成＋缺什麼」。

本專案的驗證指令（正本＝repo 現況，過時以 repo 為準）：{{填 Phase 1 查證的事實：build 指令、啟動指令、前端指令、測試指令。寫「查法」優於寫「陳述」——例：「測試＝以 repo 現況為準（先查 X 目錄是否存在與 Y 設定）」。禁止照抄文件宣稱，必須實查過}}。

| # | 判準（可機械驗證） | 驗證方式 |
|---|--------------------|----------|
| B1 | build／編譯 0 error | 貼 build 結尾輸出 |
| B2 | {{若有前端／UI：dev server 無編譯錯誤、console 無新增紅字；無則刪}} | 開頁面看 console |
| B3 | **實際把系統跑起來**，看到行為與資料正確呈現（寫碼不看行為＝未完成） | 實跑輸出或畫面驗證紀錄 |
| B4 | `git diff` 只含本任務目標檔案；無誤傷、無夾帶 | 看 diff 檔案清單 |
| B5 | 產出檔案落地：**重新 Read 讀回**，確認存在且未截斷（宣稱寫了 ≠ 寫成功） | Read 回檔尾 |
| B6 | 隔離驗證通過（02 §5）——實作者自己說完成不算數{{若有既有治理層加：；其要求的 review checkpoint 若適用也要過}} | 驗證者的 PASS 回報 |
| B7 | **「對齊／照搬／遷移／同步」類任務**：對兩邊的可觀察契約做**窮舉逐項對照**（UI 呈現、API 回傳欄位、DB 行為），列出所有差異點；差異要嘛消除、要嘛明確標為刻意保留。**肉眼掃幾個點說「對齊了」＝未完成** | 貼兩邊逐項對照表（程式化抓取，非目測） |
| B8 | **bug 修復必走 red→green→verify**：先寫會紅的測試錨定 bug → 看它紅 → 修到綠 → 回跑原始症狀確認消失，測試留在回歸網。「修完再補測試」＝未完成——測試沒先紅過，無法證明它鎖得住這隻 bug。無正確 seam 可寫紅測試＝發現本身，回報之 | 貼紅→綠兩次執行輸出 |

| B9 | **三種宣稱嚴格分離**：①結構檢查（parse 過、lint 過、exit 0）②機器證據（實跑輸出、截圖、量測）③感知審查（人或看得到圖的模型實際看過內容對不對）。**通過其中一種，不准說成通過另一種** | 講到哪層就只貼哪層的證據；跨層宣稱要另附該層證據 |

**典型反例（通用）**：「已實作完成，理論上應該可以正常運作」——沒跑過 build、沒看過行為。這句話在本 workspace 等同「未完成」。

### B9 展開：為什麼要把「我驗過了」拆成三層

```
  ① 結構檢查              ② 機器證據                ③ 感知審查
  parse / lint / exit 0   實跑 / 截圖 / 量測        人真的看過內容
        │                       │                         │
        ▼                       ▼                         ▼
  「格式合法」             「跑起來沒爆」            「東西是對的」

  ⛔ ①過 ≠ ②過        ⛔ ②過 ≠ ③過         ⛔ ①過 ≠ ③過
```

**每一層都有專屬的假陽性，而且低層完全看不見高層的失敗**：

| 真實事故 | 犯的是哪種冒充 |
|---|---|
| docx 用 XML parser 讀得好好的，Word 判「檔案似乎已毀損」 | ①當③（parse 過 ≠ 目標軟體開得了） |
| 六個子系統「全部 200、混合內容 0 筆」，截圖是「连接失败」 | ①當③（數據合格 ≠ 頁面能用） |
| 收藏頁與好友頁截圖 MD5 完全相同，兩張都是登入提示頁 | ②當③（截到圖了 ≠ 截到那一頁） |
| 找回密碼頁截到全白 5.8 KB 的圖 | ②當③（有檔案 ≠ 有內容） |
| 只看 grep 命中行就判假陽性，漏了 catch 參數遮蔽同名 import | ①當③（字串在 ≠ 語意對） |

⛔ **最危險的不是沒驗，是「驗了低層卻宣稱高層」**——它讓錯誤穿過所有關卡直到使用者發現，
而且每次複驗都會過（因為複驗的也是同一層）。

**寫法要求**：
- 宣稱「測過沒問題」要說**測的是哪一層**：「build 過」（①）、「實跑輸出如下」（②）、「我看過畫面，資料是對的」（③）
- **③ 沒做就明說沒做**，不准用 ①② 的證據混過去。例：「deliver exit 0、9/9 checks 過（①），
  但我沒有實際看過那張圖好不好讀（③未做）」
- 驗證器與施作器**不可同源**：用同一個函式庫寫檔又用它驗檔，驗證器對寫入器的破壞完全盲
  （docx 事故的結構性成因）。跨層驗證要換工具、換判準

> 此條改寫自 tt-a1i/archify 的 delivery-contract（MIT）。原版把交付拆成
> `deliver`（確定性檢查）／`visual-check`（瀏覽器證據）／perceptual review（真人審查），
> 並在程式裡強制執行——`visual-check` 的 receipt **永遠回報 `visualReview: "pending"`**，
> 不管截圖拍得多成功，就是不准把自動化截圖算成「有人看過了」。
> **值得學的是這個機制形狀**：不是用規則要求人誠實，而是**讓證據本身拒絕被過度解讀**。

## 矩陣 C：熔斷條件（停止自主作業，向使用者提問）

命中任一條 → 停止動手，整理好選項再問。熔斷不是失敗，**在錯誤方向上多燒 50k tokens 才是失敗**。

| C2 | 動作不可逆或外向：{{填本專案清單：push 到外部 remote、刪除資料、改 DB schema、動共用治理層檔案、改全域設定…}} | 要動什麼、為什麼、回滾方式 |

### 問使用者前的三重自查

按 AskUserQuestion 前逐項過，**任一命中＝禁問**：

1. **事實型**？答案能用 15 分鐘內查證得到（讀碼、查 memory、跑指令）→ 自己查。
2. **規則已裁型**？harness／CLAUDE.md／專案慣例已有明文答案 → 照規則做，回報中記一行「已照 X 處理」。
3. **可逆低價型**？選錯一行改回、或不影響可觀察行為 → 自己決，回報中列「已代決：X＝Y」供事後否決，不阻塞。

過完三關仍是「真決策＋無慣例可循＋選錯需返工」才准問，且**必附建議答案**；多個問題**湊成一次**發，**禁止逐項請示迴圈**。**本節管的是「請示」這個行為，不限工具**：用回覆文字結尾問「可否繼續／需要我接著做嗎」＝變相請示，同樣過三關；流程既定的下一步直接做，不問。

**查證動作也要湊一次**：自己已列得出要查的 N 項時，一次查完再回報，禁止「查一項→回報→再查下一項」的擠牙膏。對 prod 資料變更尤其適用：變更前一次講清影響全貌與筆數。

## 品味決策標準流程

1. 承認這是品味題（對照 C5），不假裝有正解。
2. 產 2~3 個**都能跑**的變體（不是口頭描述）。
3. 實際呈現各變體的可觀察差異（畫面或代碼差異表）。
4. 一張表：變體 ×（優點／缺點／工作量）。
5. AskUserQuestion 給使用者選，附自己的推薦與一行理由。
6. 使用者選定後，把決策寫進 memory（type: feedback），下次同類題直接引用。
