# 從「TC 預期結果」到「critical point」＋ assert（方法論）

核心對映：QA Agent 設計的每條測試案例預期結果 → 一個**可被其結構化證據獨立驗證**的（證據強度依 CP 類型，見下方證據規範）
critical point → 可重跑 runner（pytest 等）裡**（至少）一行 `assert`**（雙向／多面卡控可對多行 assert，見 CP5 範例）。

最後這一步（落成 assert）是讓測試「寫一次、以後直接 `pytest` 跑、
無 agent、不花 token、可進 CI」的關鍵——沒有 assert，就只能每次靠人/agent 看畫面判定。

> **載體中立**：runner 用專案既有的（pytest-playwright / Playwright Test / 任何帶 assert+exit code 者）。
> 證據一律是**結構化**的（API 業務碼 / DOM/a11y 讀回值 / 來源 readback），不靠讀截圖；截圖至多留檔備查。

## 對映規則

| 測試計畫 | critical point | runner 測試碼 |
|----------|----------------|----------------|
| TC 的一個「預期結果」 | 一個 critical point（CP） | （至少）一行 `assert`（打在結構化證據上；雙向卡控等可多行） |
| 步驟的【證據】說明 | 該 CP 的證據來源（API 碼 / DOM 值 / readback） | 取該證據 + 對應斷言 |
| 需檢查項目 | 額外 CP | 額外 assert（無 console error、業務碼 0000 等） |

每個 CP 必須**獨立可驗證**：依 CP 類型，光看其結構化證據（讀取型一個即可；寫入型需業務碼＋readback；
雙向卡控需兩個方向斷言，見下方證據規範與 CP5/CP7 範例）就能判定 pass/fail，不依賴「我記得剛剛點了什麼」。

## 好 / 壞 critical point

✅ **好**（具體、打在結構化證據上）：
```
- [ ] CP2: 用唯一鍵(DocNo)定位那一列，**再 scope 到狀態欄那一格**讀其文字、精確比對（不讀整列，避免「待處理」出現在備註/按鈕等別欄而誤綠）
      → row = page.locator("tr:has-text('DOC-20260626-001')")；assert row.locator("td.status-col").inner_text().strip() == "待處理"（狀態欄定位子依專案實際 DOM）
- [ ] CP5: 必填「聯絡信箱」卡控**雙向**都要驗（只驗一邊＝把「按鈕壞掉永遠 disabled」誤判成設計對）
      → 留空時 assert page.get_by_role("button", name="送出").is_disabled()
      → 填妥後 assert not page.get_by_role("button", name="送出").is_disabled()
- [ ] CP7: 送出成功（業務碼，非只看 HTTP 200）+ DB 讀回 token 相符
      → assert resp.json()["code"] == "0000"；再查 DB 該筆關鍵欄位 == 寫入的 unique token
```

❌ **壞**（模糊、無法斷言）：
```
- [ ] 表單運作正常        ← 斷言什麼？
- [ ] 資料有存進去        ← 從哪看出來？
- [ ] 沒有 bug
```

## 斷言規範

- **每個 CP 對應至少一行 `assert`**，斷言失敗時印出清楚訊息（哪個 CP、預期 vs 實際）。
- **斷言打在結構化證據上**：API 業務碼（如 `code == "0000"`，**非只看 HTTP 200**——業務失敗常 200+碼≠0000）、
  DOM/a11y 讀回值、來源（DB / 重查）readback。寫入型操作必「寫 unique token → 讀回那一筆比對」。
- 斷言要打在**穩定、語意化的條件**上（role、狀態、業務碼、產品既有的 id/name），不要打在脆弱的 xpath index。
  ⚠ **顯示文字不算穩定**——多語系專案切語系就全失效，見下方硬規則 ③。
- 最終資料（單號 / 狀態 / 關鍵值）印進測試 log 或 stdout，供報告引用。
- 全部 assert 通過 → exit 0；任一失敗 → 非 0，CI 即可據此擋。

## 五條硬規則：讓測試不依賴環境既有資料

判準一句話：**把業務資料清空、只留 schema 與字典，這支測試仍該能跑通**。做不到就是測試債。

五條都有實測代價，不是理論偏好（①～④ 據 2026-09 一次「空庫全庫基線」實作沉澱，通過率 29%→60%；
⑤ 於 2026-09-09 補入——先前這條只存在於某個專案的本地文件，導致同一套紀律兩處分歧、
照 skill 這份做的人會漏掉它，而它漏掉的代價是**整輪測試作廢**）。

> 條號只增不改：既有文件與工具訊息會引用「硬規則③」這種編號，重排會讓那些引用全部指錯。

### ① 前提資料自己生，而且走產品入口

- 測試需要的前提資料由 **fixture 走產品的 API／UI** 造出，不寫死既有 Id／代碼（`_ORDER_HEADER_ID = 88` 這種）。
- 直接用 SQL 寫業務資料**原則上禁止**。唯一例外是專案明列的**封閉例外清單**，且要先過
  `test-asset-hygiene.md` §6 的「判產品有沒有入口」四條判準——「我覺得產品沒有入口」不算數，
  那四條就是用來推翻這個直覺的。援引例外時在註解寫明屬於哪一類、產品端證據與查證日期。
- **理由**：直接 INSERT 造出的資料形狀，產品自己永遠不會產生——拿它當前提測出來的綠燈，不證明產品能用。
  實例：某 `add` 端點的 items 少帶一個布林欄位就分發不出下游任務，這個契約**只有走 API 才踩得到**。
- 清理只刪自己造的（造時取 `SCOPE_IDENTITY` 或帶唯一前綴），**不要 UPDATE 回原值**——那會改壞別人的資料。
- **身分類的值一律從「當前生效的設定」反查，不寫死也不宣告成常數**：登入者 alias／部門／email
  從當前 token decode；租戶／客戶／公司代碼從當前身分設定取；要「另一個人／另一家」就查資料源
  挑一筆（規則固定以確保可重現），要「不存在的」就用 `NONEXISTENT_*` 命名的刻意值。
  **宣告一個常數讓大家引用不算修好**——常數仍是寫死，換身分還是要人工同步、還是會漏。
  自我檢查：**把 token 換成另一個使用者、把租戶換成另一個，這支測試還會綠嗎？**
  實測代價：某專案全庫掃出 198 處寫死的員工 alias（單一帳號就佔 81 處），
  換一顆 test token 得改 198 個地方，漏掉的會以「權限不足／查無此人／部門對不上」
  這種**看起來像產品缺陷**的形式紅出來。

### ② 期望值查來源推導，且不得與被測邏輯同源

- 禁止 `assert count == 238` 這種字面數字。期望值要現查資料來源算出來。
- **關鍵**：推導期望值的查詢**不得抄被測程式那一句**。抄了的話後端邏輯錯時測試一起錯、突變測試存活，等於沒測。
  期望值要從**情境的業務定義**獨立寫出。
- 斷言比對「來源算出的值 ↔ API 回傳 ↔ 畫面顯示」三方一致。
- **理由**：寫死的數字連「你接錯資料庫了」都測不出來——實例：換庫後該是 99，測試卻仍回 238 而全綠。

### ③ 定位錨語系無關

依序優先：

1. **產品既有的錨**：`id` / `name` / 元件庫 class（如 `.n-*`）/ 路由 path / 元素結構
2. **由 i18n key 取當前語系譯文**（key 不隨語系變，譯文才變）；資源檔要指明是哪個站的，**不做 fallback**
   ——猜錯 repo 會靜默拿到別份譯文，症狀長得像「功能壞掉」而不是「你指錯了」
3. **位置／順序**：「下拉第一項是全選項」「表格第 N 欄是狀態」這種結構事實不隨語系變。
   比 ①② 更穩的場合：選項文字本來就會變（下拉內容由資料決定），或該值只是用來「清狀態」
   而非驗內容——這時比對位置遠比比對文字可靠。
4. **測試端執行時 `setAttribute` 打標記**：用結構找到元素後自己打標記再定位，產品碼一個字都不動

⚠ **選項值不要從資料庫推**：畫面下拉顯示的文字與 DB 欄位值**不保證同一組**。
實測踩過：從 `Roles.Name` 撈到的角色名根本不在畫面下拉的 10 個選項裡，
`filter(has_text=…)` 永遠找不到、timeout 30 秒，而猜「是不是沒過濾 active／沒排除過期／
該挑人多的部門」全錯——最後靠探針把下拉選項印出來才看到真相。
**要用畫面上的值，就從畫面取**（列出選項再挑），別從資料源猜它會長什麼樣。

⛔ **不得為了好測而在產品碼裡加 `data-qa` / `data-testid` 之類的測試專用屬性**，除非該專案本來就有這慣例
（先 grep 確認，命中 0 就是沒有）。
定位器應該用**使用者看得到的語意**找元素（role、label、可及名稱；文字類經 i18n key 取當前語系譯文），
而不是替產品加一個只有測試看得到的掛鉤——後者讓測試繞過了使用者實際辨認元素的方式，
該元素「對使用者不可辨認」（沒 label、role 錯）這類缺陷就永遠測不到。

⚠ **`assert xxx.get_by_text("送出").count() > 0` 是定位器，不是斷言**——它一樣用文字找元素，切語系一樣失效。
別因為那行有 `assert` 就以為它豁免。

⚠ **遷移時不可弱化比對強度**（2026-09-07 實測，一次改壞整包 15 支）：

    改前  page.wait_for_selector("h1:text-is('訂單資料')")        ← text-is 是精確比對
    改後  page.get_by_role("heading", name=i18n_t("..."))         ← 預設模糊比對
          → 頁面同時有 <h1>訂單資料</h1> 與 <h1>已填寫訂單資料</h1>
          → strict mode violation，整包紅

改成 `get_by_role` / `get_by_text` 時，原本若是精確比對就要補 `exact=True`。
**遷移的目標是「換掉寫死的文字」，不是「順便換一種定位方式」**——
比對強度、層級限定（`level=1`）、容器 scope 都要原樣保留。

### ④ 沒資料時不准跳過，要自己生

skip 依「該由誰負責讓它跑起來」分流（原三分流，2026-09-24 補 D 類成四分流；A～C 語意不變）：

| 類別 | 判準 | 處置 |
|---|---|---|
| **A 資料不存在** | skip 理由是「查無／種子缺／回傳空」 | **改 fixture 自造**，造不出來才 fail |
| **B 環境不可用** | 外部服務／登入態／本機 mock 真的沒有 | 保留，但改 `skipif` ＋**具名條件**（要能被統計） |
| **C 頁面結構變更** | 「找不到某欄位標籤」 | **改 fail**——那是回歸訊號 |
| **D 共用狀態被佔住／前置沒做成功** | 「前一輪殘留鎖住了」「前置步驟失敗所以跳過」 | **改 fail**；teardown 要把共用狀態還原，不依賴前一輪殘留 |

**理由**：skip 讓「沒有測到」長得跟「測過而且沒問題」一模一樣。資料一空 A 類會全面觸發，
通過率看起來還行、保護力歸零。

**執行期 skip 只允許 B 類**：A、D 類出現在執行期 skip 就讓整輪判失敗（它們是測試自己該負責的事）；
C 類應直接寫成 fail。B 類還有一條附加限制——**該外部系統在本機已有 mock 時，不得拿「需要真實外部系統」當 skip 理由**；
真要 skip，理由必須具體寫出「缺哪個 mock／哪個觸發條件造不出來」，
「會動到資料」「無法乾淨還原」不是理由（測試庫本來就可破壞，見 `test-discipline.md` §1）。

**判準是「決定的時機」，不是「有沒有寫 skip」**：收集期就決定的 `@pytest.mark.skipif(<具名條件>)`
（開跑前就知道不適用：作業系統不符、該外部系統在此環境根本不存在）是**誠實的宣告**，要保留，
不計入 A/D 閘；會被 A/D 閘攔下的是**執行到一半才發現「沒資料／被佔住／前置壞了」而呼叫 skip** 的那種。

⚠ 這條與既有的「假綠燈紀律」（禁止把 FAIL 的 CP 改成 skip）方向一致：**那條管新寫的，這條管存量的**。

### ⑤ 驗環境看 `response.url`，不信環境變數

**症狀**：瀏覽器操作的是 A 庫、SQL 斷言讀的是 B 庫，而測試「有跑、有斷言、看起來正常」。
值級比對（畫面 ↔ payload ↔ DB 三方一致）在這種情況下**全部不可信**——
前面四條做得再好，打錯後端就整輪作廢。

**成因**：前端 dev server 的 API base URL 在**啟動當下**就寫死指向某個後端；
測試端的環境變數只影響「測試自己發的 HTTP 請求」，**管不到瀏覽器裡的頁面**。
兩者指到不同後端時，環境變數看起來設對了、實際完全沒生效。

**開跑前的實測**（不是讀設定檔，是看實際流量）：

```python
resp = api.wait_for(page, "<某個進頁必打的端點>", timeout=15000)
print("實際後端 =", resp["url"])     # ← 這個才算數
```

搭配一個「兩邊必不同」的可觀察值交叉驗證（某表筆數、某筆的欄位值）。
只看「頁面有東西 / 回 200 / 寫入成功」不足以分辨打到哪一邊。

**同型陷阱**（都會讓「環境變數設對了」變成假象）：
- 後端起在非預設 port：`ASPNETCORE_URLS` 環境變數會被 launchSettings 的 `applicationUrl` 蓋過，
  要用命令列 `--urls`。症狀是 log 出現 `Failed to bind to address …: address already in use`
  而位址根本不是你指定的那個。
- 身分類環境變數若由**服務啟動時讀取**，測試端改 `os.environ` 對它無效；
  兩個 process 各要帶一份，只帶一邊會造成「後端身分 A、測試以為 B」而整包紅。
- 多堆疊並存時，port 可能被別分支的 binary 佔著——換堆疊或改埠後先驗一次 `response.url`，不要靠記憶。

### 紅燈歸屬：先分流，不要改測試去遷就環境

判到紅燈先問「這個後端／這個環境有沒有這個功能」——拿該測試打的端點去 grep 對應分支的原始碼，
**命中 0 就是環境缺功能，不是測試債**。改測試去遷就落後的環境會把真缺陷掩蓋掉。

## 證據規範（self-verify 時嚴格把關）

- 每個 CP 至少對應一個結構化證據，**依 CP 類型決定證據強度**：
  - **讀取 / 查詢型**：API 業務碼 **或** DOM/a11y 讀回值 **或** 來源 readback，任一即可。
  - **寫入 / 送出型**：業務碼（如 `code=="0000"`）**且**必附「寫 unique token → 讀回那一筆比對」（DB 重查 / 重新 GET / UI 渲染含該 token）——業務碼單證據不足（呼應斷言規範的寫入型讀回鐵則與 CP7 範例）。
  - **守門 / 卡控型**（本無寫入）：斷言特定狀態 / 錯誤碼（如按鈕 disabled、特定業務錯誤碼）即可，不需 readback。
    ⚠ **「disabled」單邊不算證據**：disabled 也可能是「永遠 disabled 的 bug」（判斷條件恆假、依賴的狀態恆為空）。
    必須同時驗到反向場景**真的變 enabled**（「沒變更→disabled」＋「有變更→enabled」、「空→disabled」＋「填妥→enabled」），
    兩邊都驗到才算 PASS（即 CP5 雙向寫法）。驗框架的衍生狀態（computed）時，可順手讀元件內部狀態，
    確認「應變 true 的場景」該旗標真的變 true。
- 確認證據**明確無歧義**：業務碼正確、值完全相符、列表確實反映該條件（用 unique 鍵定位那一筆再讀欄位，
  不是只驗「有列 / 非空」）。
- 對「狀態在 modal / drawer / dropdown 關閉後被藏起來」的情況：操作前先讀到值，或重開後再讀。
- 對「UI 看不到」的 CP（如資料真的寫進某來源）：查來源（DB / 重新 GET）印出結果作證，並對應一行 assert。
- 模糊、被遮擋、只套用一半的狀態 → 一律當 FAIL，不放水。

## 截圖（留檔備查，非判定依據）

- 判定一律靠上述結構化證據；**截圖不作為 pass/fail 依據**（讀圖花 token，且看圖會漏掉渲染層以外的 bug）。
- 若要留檔備查（例：佐證 RWD 破版這類純視覺問題），命名清楚、一個情境一張即可，不要每步狂截。
- runner 的瀏覽器 / viewport / 等待策略一律**沿用該 runner 的慣例**（pytest-playwright 用 chromium + locator；
  外部站備用探索才用 webwright 的 Firefox contract，見 `knowledge/pitfalls.md` G 段）。

## 斷言隔離度：只讓「被測條件」決定結果（2026-09-24 補入）

守門類斷言（「擋下了嗎」「捲到目標區塊了嗎」）最容易假綠：**其他條件本來就會讓它成立**時，
不論被測的那條規則有沒有生效，斷言都綠。

- **驗某區塊的驗證有沒有生效：其餘欄位要全部填到合法，只留目標區塊不填。**
  其餘欄位也空著就送，會有兩個後果：錯誤提示混進別的欄位（實測一次送出跳 20 則錯誤、只有 4 則屬於目標區塊）；
  若表單取「第一個錯誤欄位」決定捲動或聚焦，第一個不是目標時就驗不到目標的行為。
  更糟的是「擋下了嗎」一定成立——**假綠，而且看起來很像真的**。
- **期望值不可與「錯誤實作」恆等**（硬規則 ② 同源判準的延伸）：驗「點某列 → 請求帶那一列的 id」**一定要點非第一筆**。
  點第一筆時，期望值 `items[0].id` 與「元件恆傳第一筆」的錯誤實作恆等，斷言永遠成立
  （實測：把「傳所點那筆的 id」突變成「恆傳第一筆的 id」，5 支測試全數通過、突變存活；改點第二筆才轉紅）。
  - 取樣改 `items[1]`；資料不足兩筆時優先自造第二筆（硬規則 ④ A 類），造不出來才判失敗——
    **不要退回點第一筆換綠燈**，分辨不了就別假裝驗過。
  - 錯誤訊息同時印「期望 id」與「第一筆 id」，紅燈時一眼看出是否退化成恆傳第一筆。
  - 同型陷阱：用「取第一筆」（`TOP 1`／`ORDER BY Id DESC`）取樣驗「有沒有挑對列」，
    期望值與被測邏輯若共用同一條「取第一筆」規則，一樣是恆等斷言。
- **自我檢查**：寫完守門斷言後問「把被測那條規則整段拿掉，這個斷言還會綠嗎？」會綠就是隔離度不足。
  能做就實際做一次突變（改壞被測規則 → 必須紅），比讀碼判斷可靠。
