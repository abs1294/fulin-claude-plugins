# 測試資產衛生（方法論）

codify 之後的測試會活很久。本檔管「**測試資產怎麼維護才不會腐化成假綠燈**」：登記、skip／xfail 的使用紀律、
直接寫 DB 的例外界線、helper 替產品補值的風險、前置與素材的寫法。

> 與其他檔的分工：斷言寫法在 `critical-points.md`；執行紀律在 `test-discipline.md`；症狀→原因→對策的踩坑條目在 `knowledge/pitfalls.md`。
> 本檔提到的工具行為（檔名、指令、閘門判定）**一律以 plugin 工具實作為準**，這裡只寫紀律與理由。節號只增不改。

## 1. 三層登記：情境正本、執行事實、生成索引

| 層 | 載體 | 誰寫 | 回答什麼 |
|---|---|---|---|
| 情境正本 | `<模組資料夾>/COVERAGE.md` | 人（codify 時手寫） | 這個模組**應該測哪些情境**、各由哪支測試覆蓋、覆蓋到什麼程度（含 ❌未覆蓋） |
| 執行事實 | `.runs/results.sqlite` | 執行時自動記錄 | 每支測試**最近一次實際跑出什麼結果**（哪一批、何時） |
| 生成索引 | `CATALOG.md` | 工具生成 | 跨模組總覽；**手改會被覆蓋，禁止手改** |

**為什麼分三層**：情境知識（該測什麼）只有人寫得出來；執行結果只有機器記得準；總覽若也手寫，
一定會跟前兩者漂移。讓每一層只有一個寫入者，漂移才有辦法被機械抓到。

**drift 檢查（登記後必跑、要全為 0）**：

- **孤兒**：有測試、沒登記——測試存在但沒人知道它守的是哪個情境，刪了也沒人發現。
- **幽靈**：登記了、測試不存在——文件宣稱有覆蓋，實際沒有，是最危險的一種（讀文件的人會以為安全）。
- **佔位**：情境欄仍是 `待補` 之類的佔位字——起草後必須**當場**改寫成白話情境，不留到以後
  （實例：一次健檢抓到全庫 120 列佔位債，回頭補的成本遠高於當場寫）。

情境欄寫「**使用者實際會做的事**」，不是 API 名或函式名。覆蓋欄要能表達：完整（正向＋讀回）／部分（只測守門或缺讀回，附缺口）／
xfail＋原因／skip＋原因／❌未覆蓋。改名、刪測試時同步改登記——這也是 drift 檢查要抓的。
漂移的另一個常見來源是**寫檔假成功**（並行取消時 replace 沒真的寫進去卻回報成功），drift 檢查能直接抓到，不要改用人工 grep 代替。

## 2. skip 四分類：執行期只允許 B 類

分類定義與處置正本在 `critical-points.md` 硬規則 ④（A 資料不存在／B 環境或外部鏈路不可用／C 頁面結構變更／D 共用狀態被佔住或前置沒做成功）。
這裡只記紀律與理由：

- **執行期 skip 只允許 B 類**，且要具名條件、能被統計；外部系統已有 mock 時不得以它為由。
- **A、D 類出現即整輪判失敗**：它們是「測試自己該負責讓它跑起來」的事——A 該自造資料，D 該在 teardown 還原共用狀態。
  允許它們 skip，等於允許測試把自己的債轉嫁成「沒測到」，而「沒測到」在報告上長得跟「沒問題」一樣。
- **C 類直接寫成 fail**：找不到預期的頁面結構就是回歸訊號。
- **收集期的 `skipif(<具名條件>)` 要保留**：開跑前就知道不適用（作業系統、該外部系統在此環境不存在）是誠實的宣告，
  不計入 A/D 閘。**判準是「決定的時機」，不是「有沒有寫 skip」**。
- 「取不到值就 skip」的寫法要特別小心：取值寫錯（欄位名大小寫、鍵名錯）也會取不到，
  於是被靜默 skip 成假綠燈（見 `knowledge/pitfalls.md` L 段）。

## 3. xfail：鎖定已知產品缺陷，以及它的反向紀律

**用途**：發現真的產品缺陷、但當下不修（等使用者裁決或排程）時，用 `xfail(strict=True)` 把「缺陷存在」這件事鎖進回歸網，
並在測試說明與情境正本註明缺陷內容、根因位置、轉綠條件。

- **一定要 `strict=True`**：缺陷修好後測試會意外通過 → strict 讓它變成 **XPASS(strict) 失敗**，逼人回來處理。
  不加 strict，修好了也沒人知道，那支測試就永遠停在「預期失敗」而不再守任何東西。
- **XPASS 要轉正**：看到 XPASS(strict) → 確認是真修好（不是測試壞掉變恆綠）→ 拆掉 xfail 標記、改成正常斷言跑兩輪皆綠 →
  同步改情境正本的覆蓋欄（從「xfail 鎖定」改為「已修復轉為常規回歸」）。拆標記後忘了改文件，就會產生「文件說還鎖著、測試早已轉綠」的幽靈描述。
  XPASS(strict) 本身也是有價值的證據：它證明測試在修復前後行為確實反轉，不是「讀碼覺得修好了」。
- **不得用 xfail 掩蓋新缺陷**：xfail 只能用於**已經定位、已登記**的產品缺陷。
  新寫或既有測試紅了，不可以為了讓整輪變綠而補一個 xfail——那等於把回歸訊號靜音。
  也不可以用 xfail 標「測試自己寫不出來 / 不穩定」的情況（那是測試債，該修測試）。
  改寫測試時同理：規格變了而改寫斷言，要寫成新的正確斷言並真實通過，不是改成 xfail 了事。

## 4. 故意保留的紅燈

有些紅燈是**刻意留著的**：它鎖定一個已知、尚未裁決修不修的缺陷，或守著一個「綠轉紅就代表回歸」的關鍵行為。

- **已鎖定的缺陷不准「修綠」**：接手的人在批次修紅燈時，看到被登記為鎖定項的測試，不得為了全綠而改斷言或刪掉。
  登記處（情境正本與生成索引的缺陷匯總）要清楚標示「維持現狀、勿修綠」。
- **關鍵行為的閘門測試：綠 → 紅一律視為回歸，未歸因前不得上線**。
  對「曾經靜悄悄出過大事」的區域（症狀安靜、不擋流程、上線很久才被發現），
  把該區全部行為鎖成一組必跑測試，列為上線前必驗閘門。
- 紅燈的歸屬要先分流再處理（見 `critical-points.md`「紅燈歸屬」）：環境缺功能、測試債、產品缺陷，處置完全不同。

## 5. 用缺陷現場當定位錨

缺陷的外顯症狀有時能直接當定位錨，例如 i18n key 缺失時畫面原樣印出 key 字串，
測試就用那串 key 當 placeholder 去定位元素，並在**檔頭**寫明：「刻意鎖住缺陷現場，修好後這裡會變成真譯文，屆時要連同情境正本一併更新」。

- 缺陷修好的當下測試必轉紅——**這是設計要的效果，不是測試壞了**；把定位錨改回正常寫法（i18n key 取譯文）後重跑轉綠。
- 價值：缺陷若只寫在報告裡，修好了沒人知道要回頭改測試；寫進定位錨，修復的瞬間測試就會出聲，
  不會默默漂移成「還是綠的，只是測錯東西」。
- **檔頭說明是必要條件**：沒有它就只是一個寫死的髒定位錨，接手的人看到紅燈會先懷疑自己。
  用之前先問：這個現場修好後，有沒有人會看到我留的說明？
- 同型適用：任何「暫時的錯誤輸出」——未翻譯的 key、fallback 文案、除錯用的預設值。

## 6. 直接寫 DB 造狀態：例外的判準框架

用 SQL 直接寫業務主體表來造被測狀態，**原則上違規**——SQL 拼出來的組合可能是產品永遠不會產生的形狀，
拿它當前提測出來的綠燈不證明產品能用（`critical-points.md` 硬規則 ①）。例外要同時滿足：

1. **產品確實沒有入口**：在**當前分支 / 工作目錄**的原始碼 grep 過那個處理器，確認產品發不出這種狀態，
   而不是「記得以前沒有」或「派工單說沒有」。
2. **例外類別是封閉清單**：專案要有一份明列的例外類別（例如：無 UI 入口的外部系統回調狀態），**不隨手擴充**；
   新增類別要經使用者裁定。
3. **登記理由**：在該段程式碼的註解寫明屬於哪一類例外、產品端證據（哪個處理器、哪一行寫死了什麼）、查證日期。
4. **有機械稽核**：用掃描工具把直接寫業務表的位置列出來，與例外清單比對；
   用 baseline 制時，**baseline 不可在判準收緊前重產**——那會把存量違規一次蓋章成合法，應先重構降水位、每清一批再重產。

**「產品做不到」是分支相依的事實，不是專案常數。** 實例：某個「產品發不出國外邀請」的例外在主線成立，
但在某功能分支已經補上入口；派工單照抄過期前提，QA 於是用 SQL 造了資料，白白繞過一個能驗到入口卡控的路徑。
過期的表現是「測試還是綠的，只是繞遠路」——不會有任何訊號。**援引任何例外前，在當前分支再查一次。**
同理適用於任何以「目前產品沒有這個功能」為理由的測試捷徑。

### 判「產品有沒有入口」的四條判準（援引例外前逐條過）

1. **「前提資料不存在」不等於「沒有入口」**：要問的是「那個前提，測試自己造得出來嗎？」。
   最常見的誤判發生在鏈式前提——看到最上游缺一筆資料，就把整條鏈判成例外；
   其實先用產品入口把上游那筆造出來，下游的入口就通了。
2. **例外清單不擴充**：「產品現在產不出這個形狀」不構成例外理由。先想怎麼讓產品產出來——
   補受控的注入點（見 `test-plan-design.md` §9）、改斷言、改測法，或判定這支測試根本不該存在。
3. **追寫入端，不靠畫面推論**：畫面上的限制不等於 API 的限制。判「產品產不出這個值」必須讀到
   **寫入端真正的阻擋邏輯**（請求模型的驗證標註、命令層的欄位檢查、處理器裡的驗證呼叫）。
   下拉選單不再提供某個選項，API 可能照單全收；那時「產品產不出」這句話是錯的。
4. **別讓舊種子的實作細節定義需求**（最根本的一條）：看到測試種了某個特定值，先問它是**需求**
   （規格、業務規則、缺陷重現條件），還是**舊種子隨手填的**。判斷法：把它換成產品自然產生的值，
   這支測試要驗的規則還成立嗎？成立 → 那個值不是需求，改成「走產品入口拿到什麼就照那個值斷言」。

### 宣稱「這是真例外」時要貼的四步證據

判「產品沒有入口」最危險的地方是**推理鏈看起來完整**：確實讀了處理器、確實找到守門條件、守門也確實會擋，
只差沒問「擋我的這個前提是誰造成的」。單看被擋的那一刻是真的被擋，所以自我複查結構上抓不到，
必須靠一個外加動作。宣稱例外時逐步貼出：

1. **擋你的守門在哪**（檔案:行號）
2. **它為何不滿足**（缺哪個前提、哪個值不對）
3. **這個前提測試自己造得出來嗎、順序能不能換**——寫出試過什麼方法造前提或調換操作順序，**附實跑輸出**，不得用推論填補
4. 只有第 3 步答「不行」，才是真例外

**缺第 3 步＝該例外不成立，回去走產品入口。** 實際紀錄：一輪內六個「產品產不出來」的判斷全被推翻——
把某歷程誤判成只由外部回呼寫入（唯一寫入點其實是內部某個端點）、把某狀態欄誤判成只由回呼寫入
（建單當下就賦值、另有非回呼的寫入點）、「helper 造不出這個佈局」（對 helper 成立、對產品 API 不成立）、
「產品會去重所以造不出重複列」（讀到的去重在被測路徑本身、不在資料產生路徑）、
「產品產不出舊格式」（下拉不再提供但寫入端零驗證）、「掃描器漏收」（實為分桶問題）。

### 不算例外的理由

以下說法**一律不構成**直接寫 DB 的理由：跨站操作麻煩、跑一輪很慢、要湊多種並存的版本、成本太高、
要精確控制資料形狀、歷史相容性。這些都是「走產品入口比較辛苦」，不是「產品沒有入口」——
**這些情況一律走真實業務流程長出來，不論成本。**

### 兩個「看起來修好了、其實沒有」的資料來源寫法

- **借一筆現成的，光跑過不算修好**：把「借一筆既有資料」改成「借不到就走產品入口造」之後，
  DB 裡只要還有可借的列，測試就會走借用那條路——綠燈證明不了它會自己造。
  驗收時要**把可借的來源拿掉再跑一次**（清空該類資料、或換一個空庫），確認造的那條路真的通。
- **既有 id 寫死進回歸測試＝空庫下靜默消失**：寫死一筆「實測有資料」的既有 id，空庫時那筆不存在，
  測試若寫成「查不到就 skip」，**不會紅、只會不見**。要對真實既有資料跑鏈路（探查），
  把鏈路抽成帶參數（如 id）的 helper：回歸測試傳自己造的那筆，探查時才傳既有 id——
  兩者共用同一套驗證邏輯，既有 id 不進回歸測試目錄。

### 失敗注入的邊界

受控注入點（`test-plan-design.md` §9）解決的是「**外部系統回失敗**」這種沒有合法輸入能觸發的分支，
**不是用來造前置狀態**。拿注入點去產生產品正常流程產不出的資料形狀，跟直接寫 DB 是同一件事。

### 環境開通也走產品入口

不只造被測狀態：替測試帳號開通權限、角色、選單這類「讓測試跑得起來」的環境準備，同樣要走產品的
管理頁或送審流程，**不得直寫權限、角色對照表**。直寫出來的授權形狀可能是產品流程永遠不會產生的，
而且會讓「授權流程本身壞掉」這個回歸永遠測不到。產品若是全域單軌的權限版本鏈，走流程時留意
會連帶核准別人的草稿（見 `knowledge/pitfalls.md` 的權限綁定條目）。

## 7. helper 替產品補欄位（G 類）：覆核與 `G-REVIEWED` 註記

**G 類**＝測試 helper 在參數省略時，**自動補齊會落 DB 的產品欄位**（例如從當前登入身分反查一個負責人填進去）。
這類寫法看起來完全合規（走真實入口、不寫死、從當前身分反查），但若產品端有某條路徑**不填**該欄位，
helper 補了就等於改了產品的輸入——**那條路徑的缺陷永遠撞不到，兩邊測試都綠**。

實例：某 helper 建案時自動補負責人，而產品的「同步建案」路徑寫死負責人為空；
於是同步建出來的案件無法結案（守門擋回），使用者隨手一點就撞到，
但建案側測試沒斷言負責人、結案側測試的案件全走會補值的 helper——「同步建案 → 結案」這條沒有任何測試走過。

**判「safe」的五種性質，穩定度差很多：**

| 穩定度 | 性質 | 重掃時 |
|---|---|---|
| **結構性** | ① 欄位被序列化忽略標註丟棄（payload 值不會進後端，由後端自行灌值）<br>② 該值是刪除語句的 WHERE 條件（不落 DB）<br>③ 型別本身強制必填（產品不可能不填） | 可跳過 |
| **行為性** | ④ 產品處理器主動拒絕空值（throw）＋必填驗證標註 | 守門被拿掉就要重驗 |
| **條件性** | ⑤ 產品**確實有**不填的路徑，但由**另一支測試**守住 | **每次都要複查**——那支被刪 / 改 / skip，本處當場變真違規且沒有任何訊號 |

- **最快的查法**：先看後端命令物件的該屬性有沒有序列化忽略標註，有就直接結案（身分類欄位常由後端從 token 灌入）。
  不要從 helper 往下追，那個順序會先入為主。
- **判準陷阱**：同一個變數常餵進**多個** payload 欄位，只查一個會判錯（一個真落 DB、一個被丟棄）。**逐個去處都要查。**
- **真違規的修法優先序：先補測試，再改 helper。** 即使 helper 開放「該欄位可傳空」，沒人去用還是撞不到缺陷——
  真正補洞的是「有一支測試走那條不填欄位的產品路徑、再驗後續行為」。

**覆核完確認是假議題的，在該行上方留註記**：

```python
# G-REVIEWED: safe — <產品端證據：處理器檔名與行號、標註、型別約束>（YYYY-MM-DD）
#   （可多行，續行照樣是註解）
if owner is None:
    owner = identity.current_user()
```

格式：`# G-REVIEWED: <safe|real> — <產品端證據>（日期）`。**理由要寫產品端證據**，不是「我看過了」。
條件性（⑤）的註記必須寫出守住它的那支測試名，重掃時才查得到。

**為什麼放程式碼註解而不是資料庫**：改那行程式碼的人**一定看得到**；放在資料庫要另外查，人不會查。
而且註記自帶失效偵測——有人把欄位換掉、註記還留著就是明顯的說謊，code review 看得出來。

## 8. 前置不得編碼「當前的錯誤行為」

最毒的測試缺陷不是漏測，是**前置步驟編碼了當前的錯誤行為**——產品修對之後，這些測試會集體轉紅，
看起來像回歸，實際上是測試在守著缺陷。

實例：版本號原本從「最後一筆單據的版號 + 1」推算，不分該筆是核准還是退件，於是退件也推進版本、造成斷號。
修成「只認已核准那筆」後，6 支既有測試同時轉紅——前置都是「造一筆退件單，然後假設下一版就是版號 + 1」。

```python
# 前置編碼了舊行為：造退件單就假設版本會推進
seed_doc(ver=21, status=REJECTED)
assert working_version() == 22          # ← 守著缺陷

# 正確：用核准單定錨版本，退件只表達「當前是退件狀態」
seed_doc(ver=21, status=APPROVED)
seed_doc(ver=22, status=REJECTED)
assert working_version() == 22          # 退件不推進
```

- **判準：前置裡出現的數字，是「業務規則要求的」還是「當前程式算出來的」？** 後者就是把實作細節焊進測試。
- 查詢型 helper 只用「依 Id 倒序取最後一筆」而不帶業務條件（例如只取已核准），是同一個病的變體——它跟著實作一起錯。
- **改 helper 比改個別測試重要**：helper 錯會讓所有引用它的測試同時盲。

## 9. 掃原始碼的測試：綁死字面寫法，必須用突變證明守得住

有些守門只能靠掃原始碼做（函式寫在元件內部、未匯出，單元測試 import 不到）。這類測試有兩個固定弱點：

- **逐行掃描抓不到跨行寫法**：格式化工具把一個呼叫拆成多行後，每一行單獨看都不匹配，測試全綠而問題仍在。
  修法：先剝掉註解與字串，再對整份原始碼做多行比對。
- **掃字面數字，值一收斂成常數就全落空**：掃 `case 5:` 的測試，在程式碼改成 `case STATUS.RETURNED:` 之後全紅——
  **測試在擋一個正確的重構**。修法：改掃常數名，並**另加一組斷言驗常數值對回後端列舉**；
  少了後者，「名稱對、值被改錯」這條鏈沒人守。

**共通鐵則：這類測試綠燈不代表守得住，必須用突變測試證明它抓得到目標缺陷**——
逐一把目標行為改壞（改回傳值、改常數值、加一個跨行寫法的探針），每次都應轉紅；全部還原後應轉綠。
突變完務必確認工作目錄還原乾淨（用版控 diff 對照），別把探針檔或改壞的值留下。
