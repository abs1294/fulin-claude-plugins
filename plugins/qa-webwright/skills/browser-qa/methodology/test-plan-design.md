# 測試計畫設計（方法論）

QA Agent 在 Phase 1 產出測試計畫的通用規範。**不假設任何特定 UI 框架、元件庫或後端**——
所有技術棧專屬的雷與領域知識都在 `knowledge/`，不在這裡。

## 0. 設計前置：盤點既有測試資產（先於覆蓋矩陣）

動筆寫 TC **之前**，先盤點目標專案 runner 內**既有的測試自動化資產**——page object / helper / fixtures /
相似的既有 TC。兩種情況：

- **（A）已有既有資產** → 能復用就優先復用，新 TC 與既有資產的風格、命名對齊。
  - **怎麼盤（手段）**：枚舉 runner 既有測試——`pytest --collect-only`（或讀 tests/ 目錄與描述性測試函式名）+ 讀 xfail / skip marker。
    這能盤出「**已寫的**測試」供復用對齊，但**回答不了「該做卻沒人寫的情境」**（見 §0.5）——枚舉只能列出存在的測試，不存在的測試在 collect-only 輸出裡是隱形的。「要沿用還是新建」的完整答案需搭配 §0.5 的情境覆蓋索引。
- **（B）greenfield（專案尚無 runner / 測試資產）** → 建立第一個：
  - **不要自己 mkdir / 自己判斷落點**：一律先跑 `qa-flow.sh bootstrap`（見 `SKILL.md` Phase 2），
    它鎖 `CLAUDE_PROJECT_DIR`、發 `ASSET: none` + `ACTION-REQUIRED: ask-user-install` 訊號、確保 catalog.md 存在。
  - **落地目錄與命名（由腳本鎖死）**：測試放在**你起 session 的那個資料夾**底下的 `tests/e2e/`（檔名 `test_<feature>.py`），
    **禁止自行鑽進子專案目錄**——這條規範由 `qa-flow.sh` 用 `CLAUDE_PROJECT_DIR` 機械執行，AI 想鑽也鑽不進去
    （歷史踩雷：執行者看到子目錄有既有 JS 專案就鑽進去出 JS）。
    > **要讓 e2e 進某個專案 repo 版控，正確作法是「在那個專案資料夾裡起 session」**，而非從上層資料夾鑽進去——e2e 的測試棧/語言不一定等於該專案語言，落點由「session 起在哪」決定、不由 skill 寫死絕對結構。
  - **runner 固定優先 pytest**：使用者同意後 `qa-flow.sh scaffold <feature> pytest` 建骨架，安裝指令
    （`pip install pytest-playwright && playwright install chromium`）由腳本印出、**使用者自行執行（腳本不代裝）**；
    僅使用者明確不同意裝 Python 才退而 `scaffold <feature> playwright-js`。
  - 專案專屬值（port / login / BASE_URL）仍委派目標專案 `CLAUDE.md`，不寫進方法論。

> 與 §1「讀範圍內程式碼」不同：§1 讀的是**被測功能的產品原始碼**（API/前端/store）；本節盤的是**既有的測試碼**。
> 漏了這步，QA Agent 會在不知道既有資產存在的情況下從零設計，產出與既有回歸資產重疊或風格不一致的計畫，
> 弱化 codify 閉環的一致性。

## 0.5 持久化情境覆蓋索引（**必做**，跨功能、含未覆蓋、邊 codify 邊登記）

§0 的 runner 枚舉只能回答「**已寫了哪些測試**」，回答不了「**該做卻沒人寫的情境**（❌未覆蓋）」——
而後者正是 R3「這情境要沿用還是新建」的答案來源。`pytest --collect-only` 是對「已存在測試」的枚舉，
一個「使用者會做、但還沒人寫測試」的情境在它的輸出裡**結構性隱形**（無法枚舉不存在的東西）。

> **兩個不重疊的 SSOT，不是漂移**：runner 是「**已寫測試**」的單一真相來源；情境覆蓋索引是「**應測情境＋各自覆蓋狀態（含 ❌）**」的單一真相來源。
> 兩者語意不重疊——索引補的是 runner 結構上沒有的「差集語意（哪些情境還沒被覆蓋）」。漂移屬「維護紀律」問題，不是「不該有索引」的理由。

因此：**從第一條測試起就維護一份跨功能、持久化的情境覆蓋索引**，邊 codify 邊累積（呼應 codify 閉環）。
**這份索引固定落在 `tests/e2e/catalog.md`（與它索引的 test 檔 / report 同層、一份總表、跨功能累積），由 `qa-flow.sh catalog <情境> <函式> <狀態> <模組>` 機械回填**（以測試函式為主鍵 update/append，不靠 AI 記得手寫，見 `SKILL.md` Phase 2 step 6）。
**這份索引與 `conftest.py` / `test_*.py` / report 同屬必產物——只做 pytest 那套卻漏掉索引，等於漏了 R3 的承載結構（這是常見漏法，務必一併產出）。**
**預設用 markdown 表**（四欄如下）——**這份索引的讀者是「人」**（QA Agent 盤點、開發者查「這情境測了沒」），不是機器；md 表是人類掃得動、好維護、進 git 可 diff 的形式。
> **逃生門（窄）**：只有當專案已有「對人更好讀」的既有索引（如專案 wiki、既有覆蓋報表）才沿用之；**禁止用純機器格式（xml / json）當人類索引**——那等於沒給人看，違背本索引存在的目的。
> （對比：`conftest.py` / `test_*.py` / `report.xml` 讀者是機器、格式由 runner 決定；本索引讀者是人、故釘 md。**格式服從讀者**。）

最小四欄骨架（欄位語意中立、不綁專案值，但形式預設 md 表）：

| 欄位 | 內容 |
|------|------|
| 白話業務情境 | 人類可讀的「使用者會做什麼」（**非函式名**） |
| 對應測試函式 | 函式名，或 `—`（尚無對應測試） |
| 覆蓋狀態 | ✅完整（操作＋讀回） / ⚠️部分（附缺口原因，如「只測守門、正向待補」） / ❌未覆蓋 |
| 業務模組分類 | 所屬模組（可對到頁面 / API / 角色維度） |

> **`—` ＋ ❌未覆蓋 那一列，正是 R3「沿用還是新建」的答案來源**，也是 collect-only 結構上產不出的那一列。

**從第一條測試就建、不要等規模大了回溯補**：邊 codify 邊登記是「幾乎零增量成本」的累積；等到逾百函式平坦清單已退化成「憑印象掃」（正是 §1 與 §0 警告要避免的）才想回補，得回溯整理上百個既有測試的情境/覆蓋狀態，成本爆炸。延後 = 利滾利的技術債。

**防漂移紀律（不是 open question，就靠 codify 閉環同步）**：
- **新增覆蓋** → codify 一條測試後，於閉環末端回填該情境列（見 `SKILL.md` Phase 2 step 6）。
- **改/刪測試** → 同步更新或移除對應情境列的測試函式欄與覆蓋狀態（測試刪了該列退回 ❌未覆蓋）。
- 索引與 runner 同源於同一次 codify 動作，不另開維護時機——這就是「不漂移」的機制。

> **三層登記（2026-09-24 補註）**：索引改採「模組資料夾內手寫情境正本 `COVERAGE.md` ＋ 執行事實 `.runs/results.sqlite`
> ＋ 生成的 `CATALOG.md`」三層時，本節四欄的**欄位語意不變**，只是「手寫正本」下放到各模組資料夾、總表改為生成物。
> 三層分工、drift（孤兒／幽靈／佔位）判準見 `test-asset-hygiene.md` §1；實際檔名與指令以 plugin 工具實作為準。

## 1. 覆蓋矩陣（必做的**內部設計動作**，先於寫 TC；不寫進交付輸出）

讀完範圍內的程式碼後，**先**把所有「狀態維度」窮舉成一張表，每格至少對應一條 TC。
禁止憑印象直接跳到寫 TC。

> **這是設計時用來「防漏測」的內部工具，不是交付物**：窮舉完，每格對應的 TC 直接寫進
> `qa-engineer` 定義的單一 TC 輸出表；矩陣本身不出現在交給使用者的計畫裡（避免冗餘）。

需窮舉的維度（依本次功能取用）：

- **Status / 狀態**：相關狀態的每個值與轉移（A→B）
- **分支條件**：每個 if / switch / 條件渲染（含 happy + 失敗分支）
- **角色 / 權限**：每種有差異的使用者情境
- **視圖 / Tab 狀態**：每個 tab、每種列表狀態（空 / 單筆 / 多筆 / 跨視圖轉移）
- **資料邊界**：空 / 最小 / 最大 / 特殊字元 / null

> 取值來源（2026-09-24 補）：狀態維度**照後端的列舉定義逐值列**（不是照畫面上看得到的幾個）；
> 分支維度照後端處理器與前端衍生狀態（computed / 條件渲染）裡的每個 if / switch 列。
> 憑畫面印象列維度，漏掉的正是「畫面平常不會出現」的那幾個值。

| 維度 | 值 / 分支 | 對應 TC | 備註 |
|------|----------|---------|------|
| 狀態 | 待處理 | TC-003 | |
| 角色 | 一般使用者 | TC-010 | |

**任一格沒有對應 TC = 計畫不完整，不得交付。**

## 2. 可追溯性（必做）

- 每一條驗收條件 / 需求點，至少對應一條 TC。
- 本次 diff 改動到的每個分支、每個新增/修改的互動，至少對應一條 TC。
- 計畫末尾附「需求 ↔ TC 對照表」；不測的需求點明確標「不測 + 理由」。

## 3. 測試案例：每條 TC 要涵蓋的要素

> **交付輸出用 `qa-engineer` 定義的單一表格**（每列一條 TC：TC / 功能情境 / 操作步驟 / 證據 / 預期結果 / 需求）。
> 下面列的是**每條 TC 內容該包含的要素**（填進表格對應欄）——多步驟操作在表格「操作步驟」欄用 `→` 串接：

```
TC-{編號}
功能：{名稱}
前置條件：{完整進入路徑、必要的初始狀態}
操作步驟：
  1. {具體操作：點哪個元素 / 填什麼值 / 在哪個欄位} → 【證據】{這步要驗證什麼}
     預期結果：{可由其結構化證據獨立判定的結果}
  2. ...
需檢查項目：
  - [ ] 無執行期錯誤（console 無紅色錯誤）
  - [ ] 預期的狀態/資料變化發生
  - [ ] {其他特定檢查}
```

**關鍵規則：**
- 每個操作步驟標 **【證據】** 並說明驗證重點（對映一個 critical point + 一行 assert）。
- 每個步驟附**預期結果**，且寫成「看一個證據就能判定 pass/fail」的形式。
- 操作描述要具體，前置條件含完整進入路徑。

## 4. 必測 Checklist（設計時逐類涵蓋）

通用類別。實際檢查點依本次功能取用；技術棧專屬的「怎麼驗」放 `knowledge/`。

- **功能正確性**：主流程可完成、操作後狀態正確改變、改變後正確顯示、查詢/篩選回正確結果、成功/失敗訊息正確。
- **驗證邏輯**：必填留空觸發驗證訊息且禁止送出、格式錯誤正確提示。
- **UI 行為**：載入無執行期錯誤、loading 正確開關、文案/i18n 無顯示 key 名、互動元素 enabled/disabled 正確。
- **資料流程**：資料正確流向其來源（若有外部請求/持久化，驗其結果；細節見 `knowledge/`）、送出格式正確、回來的資料正確渲染。
- **多步驟 / 分頁 / wizard 表單**：每完成一步須以快照或讀回**確認該步資料已進入 state**，不可一次填到底才送出——否則中途某步未被收進 state 時，最終 payload 會缺漏該欄位且難定位是哪一步掉的。TC 須拆成逐步 state 確認，不寫成單一條「填完即送」。
- **錯誤路徑**：來源回錯誤時 UI 正確顯示、不白屏、不卡 loading；業務失敗不誤判成功；重複/並發操作不產生重複或互蓋；驗證失敗時在前端就擋下。
- **Edge case（預設必測，跳過寫理由）**：空狀態、重複操作、極長文字/特殊字元、邊界值。
- **權限（預設必測，跳過寫理由）**：有權限可執行、無權限元素不顯示、跨情境可見範圍正確。

> 若本次確無權限差異或 Edge case，須在計畫明寫「不適用 + 理由」，不得默默省略。

## 5. 測試資料建立規範（原則）

需建立測試資料時，**每個可填欄位都要填合理且真實的值**，不得偷懶留空。

**原則性原因**：留空的非必填欄位會在資料層沉澱「壞值」（空字串 / null / 型別預設值 / 邊界日期），
後續流程讀到壞值可能觸發例外、序列化錯誤或渲染異常，**讓真 bug 被遮蔽**，或讓二次操作神秘炸掉。

通用要求：日期填合理日期（不留空）、數值填業務合理值（非 0 或極值）、
格式欄位用合法格式、識別欄位用有語意的值、選項至少選一個、附件真的上傳。

**送出後要讀回檢查壞值**（2026-09-24 補）：建完資料後讀回那一筆（重查 API 或來源），確認**每個欄位都不是壞值**
（null / 型別最小日期 / 無意義的 0）。一發現壞值就停下修正測試步驟、重建資料，不要帶著壞值往下測——
否則後面每一步的失敗都無法分辨是產品問題還是前置資料問題。
信箱類欄位一律用**保證不會送達真人**的假網域（如 `@example.com`），見 `test-discipline.md` §5 副作用邊界。

> 各技術棧「壞值」的**具體後果與案例**（例如某型別的最小日期會讓某轉換拋例外）屬領域知識，見 `knowledge/`。

## 6. 大型功能：紅隊漏測複查（一次）

計畫（含覆蓋矩陣）完成後、交付執行**之前**，對「新互動＋新畫面」級別的功能，
由獨立視角只讀「矩陣 + diff + 驗收條件」（不執行），列出疑似漏測，QA Agent 依清單補 TC **一次**。
純樣式 / 文案 / 小改可略，但須註明「略過 + 理由」。

## 7. FAIL 前排除紀律（判 FAIL 之前必走，跨專案通用）

看到 FAIL **先別當成功能 bug**——多數「FAIL」其實是環境 / 探索 / 判讀問題。依序排除：

1. **服務存活先驗**：一次出現大量 FAIL，先確認前後端服務還在 listening（沒被中途關掉 / 沒崩）、
   測試環境前置（登入態 / test token / 必要資料）還在。環境塌了不是功能 bug。
   （2026-09-24 補）典型訊號是整批出現 `ERR_CONNECTION_REFUSED` / `net::ERR_*` / HTTP `000`；
   用 `netstat`（看 LISTEN）＋對每個服務 `curl` 一次首頁取狀態碼實測，**先驗環境、再驗碼**——
   dev server 長跑中途崩潰時所有測試都會紅，逐支去改測試碼是白工。
2. **「操作沒生效」五排除**（click 後沒有預期的 API / 狀態變化時，逐一排除再判 FAIL）：
   - selector 點到的不是真元素（背景同名元素 / portal 在別處 / 被遮擋）→ 用唯一鍵 / role 重新定位
   - 事件沒被框架認得（受控元件只改 DOM 沒觸發框架事件）→ 見 `knowledge/` 受控元件段
   - 時序：操作後狀態還沒更新就驗 → 操作 → 等 → 再驗
   - 真實值與記憶 / 計畫不符（後端欄位名 / 端點名 / 按鈕文案對不上）→ **先 grep 原始碼確認真實值**，別盲試
   - 真的沒接（路由未 wire / 功能未實作）→ 這才可能是 bug

   **UI 層五查**（2026-09-24 補；與上列互補——上列查「點對了沒」，這列查「點對了但畫面把它攔下了沒」）：
   - 按鈕是否 disabled / 游標為 not-allowed（讀 `disabled` 屬性或計算樣式）
   - 是否有**列內確認鈕**（子項新增後要再按一次該列的「加入 / 確認」才算數）或對話框內的二次確認
   - 是否彈出**確認對話框**等著按確定（對話框常渲染在 portal，不在原元件內）
   - 表單驗證是否**靜默攔截**（讀表單項的錯誤提示節點與 `[role="alert"]` 內容）
   - 富文本 / 受控元件的內容是否**真的同步進表單值**（看表單值，不是看編輯器 DOM；見 `knowledge/` F 段）

   兩組都查過、真的沒發出請求，才標 FAIL。
3. **業務語意三問（判「不給做」是 bug 還是 by design）**：當某操作「被擋下 / 不給送 / 看不到」時，
   先問：(a) 這是不是**刻意的卡控 / 權限設計**？(b) 後端回的是**業務碼（by design 擋）**還是真的炸（5xx）？
   (c) 換個合法前置 / 合法角色會不會就通？三問之後仍不通才登記 bug。
   （2026-09-24 補兩問）(d)「沒反應」是不是**多步驟流程**還沒走完？批次操作常是「加暫存 → 填原因 → 上傳附件 → 送出」，
   子項增刪常有列內確認，送出常有兩層確認。(e)「找不到入口」是不是**計畫寫的路由與實作不一致**？
   這種標「Partial / N.A.」回報計畫需更新，不要硬判 FAIL。
   by design 的典型：已結案 / 已退件 / 已下架的資料保留歷史不給刪；已核准的單不能再送審；簽核中送出鈕一定 disabled。

> 目的：避免把「環境塌 / 探索沒對準 / by-design 卡控」誤判成功能 FAIL，浪費往返並汙染報告可信度。

## 8. 探索式情境設計：TC 設計必過七類（2026-09-24 補入）

QA 不只補「已知 bug」的覆蓋——設計 TC 時要**主動發想「使用者會做、但測試沒模擬」的情境**，先於使用者踩到。
每次針對一個畫面 / 流程設計 TC，以下七類逐類問「這裡有沒有」，有就進 TC 表，確定沒有就在計畫註明「不適用 + 理由」：

1. **髒輸入**：前後空白、全形字、貼上（非逐字打）、超長、特殊字元、清空後再填
2. **亂序 / 中途變更**：非同步操作進行中改輸入（in-flight 競態）、填一半切走再回來、跳著填
3. **重複觸發**：連點按鈕、重複送出、對話框 / 抽屜重開後的殘留值
4. **狀態中斷 / 重入**：連結重開、暫存後重開、退件後重送、重新整理後續填
5. **導航路徑**：選單點擊 vs 直打 URL、跨頁帶參、瀏覽器返回鍵（見 `test-discipline.md` §1 導航鐵則）
6. **權限邊界**：「部分權限」的角色組合走真實入口（不要只用全權限帳號）
7. **資料邊界**：0 筆 / 1 筆 / 剛好滿一頁 / 跨頁、重複資料、資料已被他人異動

**理由**：實測一整輪由使用者手測抓到、自動化網漏接的缺陷（空白修剪後繞過卡控、非同步競態、選單路由接反、
殘留值……）**全部落在這七類**。「針對改動補 TC」只是下限，七類發想才是 QA 的本職。
與 §1 覆蓋矩陣的差別：§1 窮舉的是**程式碼裡已經存在的分支**；本節發想的是**使用者行為**——
程式碼沒寫到的處理（例如沒有做 trim），在 §1 的矩陣裡結構上不會出現。

## 9. 沒有合法輸入能觸發的失敗路徑：失敗注入（2026-09-24 補入）

外部系統回失敗、交易 commit 失敗這類分支，常常**查遍 schema 也找不到任何合法輸入能觸發**——
成功與否由外部系統決定、本機 mock 一律回成功。但這些分支往往正是重構的價值所在（rollback、失敗不留殘留），不測等於沒有回歸網。

- **不要「測試時改 mock 檔、測完改回」**：編譯型後端改原始碼對跑著的服務無效（已載入記憶體），
  要改檔 → 重編 → 重啟才生效；而「還原後沒真的重編」會讓下一支測試跑在帶注入邏輯的產物上——**而且它會通過**。
  這是「驗證器與施作器盲區同構」的典型，靜態檢查一律看不出來。
- **做法：新增一個只覆寫單一方法的注入器，其餘全部委派給原 mock，mock 檔零改動。**
  用「實作同一介面＋持有原 mock 並委派」，不要用繼承（原方法不可覆寫時，繼承會逼你回頭改 mock 檔）。
  注入條件用可辨識的輸入標記觸發（例如帶特定前綴的值才回失敗），其餘一律委派。
- **註冊只在本機環境且明確帶開關時生效**（專用環境變數）；測試端用同一個開關做收集期的具名 `skipif`——
  未開開關時 skip 而非 fail（常態回歸不該因沒開這個開關而變紅；這是 `critical-points.md` 硬規則 ④ 的 B 類）。
- **紅綠三段都要跑過才算驗完**（只跑綠的證明不了測試有效）：

  | 條件 | 應得結果 |
  |---|---|
  | 帶開關 + 打載入注入器的後端 | pass |
  | 不帶開關 | skip（不是 fail） |
  | **帶開關 + 打一般後端**（注入器沒載入） | **fail** |

  第三列是關鍵：證明測試真的依賴注入行為，不是恆綠的假測試。
- **注入的失敗值要對回真實約束**：例如用超長字串觸發截斷，長度必須實查該欄位的長度上限定義。
  憑感覺寫一個「看起來夠長」的值，欄位比你猜的長時注入不會發動，測試會因為別的原因通過，而你以為驗到了 rollback。
- 要在既有服務跑著的同時再起一個帶注入器的實例，見 `knowledge/pitfalls.md` N 段（預編輸出＋隔離 port）。
- **邊界**：注入器只用來觸發「外部系統回失敗」，不是用來造前置狀態——後者請走產品入口，判準見 `test-asset-hygiene.md` §6。

## 10. 缺陷責任歸屬：A/B 對照定位「前端沒送」還是「後端沒收」（2026-09-24 補入）

只驗「存進去是預設值」無法分辨責任——可能前端沒送、也可能後端沒接。同一支 API 打兩次做對照：

- **A 組**：payload 完全不帶該欄位（模擬有缺陷的前端）→ 讀回應為預設值
- **B 組**：payload 帶上游 API 實際回傳的真值 → 讀回應與送入值一致

B 組通過即證明**後端全鏈路無誤**，缺陷在前端；兩組都失敗才往後端查。
codify 時**兩組都留**：A 組是負向對照，修好前端後仍應維持綠燈（它驗的是「不帶欄位就會掉」這個契約）。
期望值一律從上游 API 實際回傳讀出，不可寫死。

追「值莫名變成預設值」這類缺陷時，**逐處確認變數在該作用域的實際來源與命名慣例**：
同一個變數名在兩處可能是不同形狀的資料（一處是 API 原始回應的 snake_case、一處是前端已轉 camelCase 的列資料），
同一句 `item.xxx` 一對一錯，grep 關鍵字分不出來。

## 11. 範圍展開四格與欄位級驗證（派工單的下限，每次都要）

**QA 只會測派工單上寫的東西——派工單漏掉的那一格，執行者結構上不會補。** 範圍完整性是指揮官的責任，
所以派工單（以及 QA 自己的計畫）必須逐格寫出下列內容；任一格填「無」要附一句理由，空白＝不合格。

1. **正向路徑**：本次改動的 happy path，逐步。
2. **反向／終止分支**：退件、拒絕、取消、軟刪、逾時、重送、權限不足——**逐條**列出適用哪幾條、怎麼觸發；
   不適用的逐條說為什麼。實際紀錄：退件重送是「整輪唯一沒被任何測試碰過的分支」，使用者一句話點破；
   另一輪「退件後資料帶回」九個模組有七個完全沒驗，先前的「機制上不會斷號」是讀碼推論。
3. **狀態序列**：至少一條多步操作（做 A → 做 B → 撤銷 A → 存檔 → 重開），驗最終狀態與各中間態一致。
   **單步操作測不出的鎖死型缺陷只有這格抓得到**——實例：「勾選 → 上傳 → 取消勾選 → 儲存」鎖死表單，
   而各自獨立的單步測試全綠；「新增第二列後第二列自己帶出日期」同樣只在多步序列出現。
4. **受影響的共用元件**：本次觸及的共用元件（上傳、表格、數字輸入、日期選擇、訊息框…）＋它們**其他使用點**
   是否要連帶回歸。改共用元件只驗本頁＝把影響面留給使用者（實例：修一個頁面的上傳名額，
   同一個上傳元件在另外十個檔案被用到，註冊、認證、預約流程全受影響）。

**欄位級驗證**（每次都要，不只寫入型）：

- 列出本次涉及的欄位共幾個，**逐欄**比對「畫面顯示值 ↔ API 回傳 ↔ DB（或資料來源）實值」。
  「畫面有顯示／API 回 200／寫入成功」都不算驗過。
- 寫入型：填入 → 暫存 → 重開 → 讀回 → 比對，逐欄**讀回 DB**；bool / int 一律用**非預設值**
  （預設值讀錯來源也會看起來對）；集合類驗多筆＋順序＋筆數。
- 純讀取頁同樣要拿畫面顯示值對 DB 實值——「有地方驗」永遠成立：沒有寫入，就驗顯示。
- 不驗的欄位**逐個列出＋理由**，不得寫「其餘略」。實際紀錄：某寫入端點 29 個欄位，唯一的測試只驗到 1 欄，
  端點層卻被算成「已覆蓋」。
