# 測試執行紀律（方法論）

QA Agent 執行測試（探索、首跑、回歸）時的行為紀律。**不綁任何技術棧、專案或外部系統**——
專案專屬的環境值（port、帳號、外部系統清單）放目標專案的 QA 知識層，不寫進這裡。

> 與其他檔的分工：`test-plan-design.md` 管「測什麼、怎麼設計」；`critical-points.md` 管「斷言怎麼寫」；
> 本檔管「執行時怎麼做人做事」；`test-asset-hygiene.md` 管「測試資產怎麼維護才不腐化」。
> 節號只增不改。

## 1. 核心鐵則

1. **走 UI 模擬使用者操作，包含導航路徑。** 進頁一律走側欄選單 / 頁內卡片等使用者實際會點的入口，
   **禁止只用「直打 URL」進頁**。直打 URL 測不到選單的顯示條件與路由接線，會假陰性——
   實測：兩個路由的元件交叉接反，所有直打 URL 的驗證全數通過，唯有選單點擊現形。
   直打 URL 可以當輔助（例如驗深連結），但至少要有一條測試走選單路徑。
2. **頁面載入的判定認頁面內容，不認 URL 或瀏覽器標題**：錨在頁標題元素（精確比對，見 `knowledge/pitfalls.md` J 段）
   或該頁獨有的資料特徵。URL 對了不代表渲染的是對的元件。
3. **優先級：正確性 > 精簡 > token。** 為了省 token 而縮減驗證範圍、跳過讀回，是用正確性換成本，不可接受。
4. **外部系統在本機已有 mock，就不准拿「需要真實外部系統」當 skip 或不測的理由。**
   凡是 mock 能打通的正向路徑（送審、回調、鎖定……）一律**實際觸發驗證**。
   真要 skip 只剩一種合法情形：該功能在本機**根本沒有對應的 mock、也無法構造觸發條件**，且必須具體寫出「缺哪個 mock」。
   （skip 分流的完整判準見 `critical-points.md` 硬規則 ④。）
5. **測試資料庫可破壞，不准拿「無法乾淨還原」當 skip 或繞路的理由**（前提：確認它是專用測試庫，不是共用或正式資料）。
   破壞性的正向路徑（建立、鎖定、寫多張子表、翻轉主檔狀態）**該觸發就觸發**，
   優先用當次新造、用後即棄的資料；能還原就順手還原，**還原不了也照跑**，
   絕不因「還原困難」而 skip，或改走後端直打繞過前端。
6. **造被測狀態、開通測試環境都走產品入口，不直接寫 DB。** 前提資料用產品的 API／UI 造出來；
   替測試帳號開權限、角色也走產品的管理頁或送審流程。可以破壞測試庫（第 5 條）不等於可以直寫它——
   前者是「放手觸發產品行為」，後者是「繞過產品自己拼資料」。例外判準見 `test-asset-hygiene.md` §6。

其餘通用鐵則已在他處，不重複：精確比對、不憑記憶猜 UI（`SKILL.md` 測試哲學）；
每個預期結果可由單一結構化證據驗證（`critical-points.md`）；FAIL 前的排除紀律（`test-plan-design.md` §7）。

## 2. 不打斷使用者（無人值守紀律）

測試是**無人值守任務**。除非真的卡到完全進不下去，否則**不問使用者**。

| 情境 | ❌ 不要 | ✅ 該做 |
|------|--------|--------|
| 瀏覽器行程被鎖 / 起不來 | 問使用者要怎麼辦 | 直接重試一次，再不行記 issue 繼續；**不得砍共用的瀏覽器行程**（別的 agent / MCP 可能正在用） |
| 某個案例卡住 | 問「要繼續還是停？」 | 換 3 種方法（換 ref / 換 selector / 換觸發方式）再不行才標 FAIL |
| 發現多個 FAIL | 問「要修嗎？」 | 全部記 issue、寫完報告，**最後**讓使用者決定 |
| context / token 看似吃緊 | 問「要不要簡化？」 | 照計畫跑完；需要時按 `knowledge/pitfalls.md` I 段分段落檔、交接續跑，不縮減驗證 |

**唯一可中斷**：環境壞到完全無法繼續（後端死掉、瀏覽器重試 3 次都起不來）。

⚠ FAIL 的案例若要修產品端程式碼（前端或後端），**先不要改，列出來即可**——測試者的職責是發現與舉證，
修不修、怎麼修由使用者決定。

## 3. 整輪結束才出報告

只在**全部案例跑完**才出報告，不是邊跑邊問。報告格式依 `SKILL.md`「測試報告格式」，另補兩點：

- 結果分類除 PASS / FAIL 外，要能表達「**Partial / N.A. / Env Limit**」（部分驗到、計畫與實作不一致、環境限制），
  並各附理由——不要把這三類硬塞進 PASS 或 FAIL。Env Limit 須寫明缺的是什麼（對照 §1 第 4 條，mock 已有者不得列 Env Limit）。
- 結論段明寫「FAIL 案例由使用者決定處理方式（不自動修）」。

## 4. 允許繞過 UI 直打的界線

正向的使用者操作（新增 / 編輯 / 上傳 / 送出 / 有畫面的查詢）**一律走前端流程**、攔 API 回應驗證。
只有下列情形允許 HTTP 直打，**且測試的說明文字（docstring）必須寫明是哪一種、為什麼**：

- 無 UI 入口的服務間呼叫（外部簽核系統的回調、webhook）
- 前端**路由根本沒接上**（本機沒有 UI 入口可走）
- 守門類：要構造非法值 / 邊界值，而 UI 本身擋住了無法輸入

資料準備、驗證讀回、清理可用 SQL 或 API（那是 housekeeping，不是「操作」；直接寫 DB 造狀態的界線見
`test-asset-hygiene.md` §6）。**API 不通時，正解是補 mock 資料讓 UI 流程跑得通，而不是繞過前端。**
理由：直打只驗了 API 與資料層，前端的組裝、驗證、按鈕鎖定全部沒驗到。

## 5. 副作用邊界總表：開跑前先確認「哪些外部效果是真的」

**任何測試開跑前，先盤一張表：本機環境下每個外部整合是 mock 還是真打。** 依**實際程式碼**查證
（服務註冊的條件分支、各整合的環境判斷），不是憑印象。

| 外部效果 | 本機行為（mock / 真打 / 依環境而定） | 防護 / 注意 |
|----------|--------------------------------------|------------|
| 外部簽核 / ERP 等交易系統 | 例：mock | 可放心真打 |
| 寄信 / 通知 | 例：**真寄**，只做了部分過濾 | 收件人清單須收斂為測試者本人；測試資料的信箱一律用不會送達真人的假網域 |
| 檔案 / 物件儲存 | 例：依啟動環境而定 | 未帶本機環境設定啟動時 mock 不生效、會真打雲端 |
| 組織 / 身分查詢 | 例：真連唯讀來源 | 無副作用，但連線目標要對 |
| 即時通訊通知 | 例：真發 | 無人值守測試的通知目標確認是自己的頻道 |
| 測試資料庫 | 可破壞 | 照 seed / cleanup 紀律 |

（上表「本機行為」欄是示意，每個專案要自己查、自己填。）

**防線靠本機未提交改動存在時，「版控顯示乾淨」是紅旗不是綠燈。** 收件人收斂、mock 切換這類防線常是
刻意不提交的本機改動——它本來就該長期顯示「已修改」。某天版控顯示該檔乾淨，代表防線已被還原掉，
而不是「沒事」。跑會觸發真實副作用的測試前，直接讀那段程式碼確認防線還在（能用 `pretest.side_effect_guards` 機械化就機械化）。

**新增外部整合時同步更新這張表。** 理由（實際事故）：某專案因為「簽核系統有 mock 所以都被隔離了」的錯誤推廣，
沒意識到寄信是真寄、而測試資料又用了公司真實網域的信箱，一輪 QA 對三位真人各寄了三、四十封信。
事故的根因不是寄信本身，是「哪些副作用是真的」**沒有清單、靠印象**。

## 6. 判斷與交付的證據要求（宣稱之前先有可重現的輸出）

以下每一條都是「讀碼推論看起來對、實跑才被推翻」的高發點；宣稱之前手上要有對應的原始輸出。

1. **想讓測試過的掩蓋手段一律停**：try/except 吞錯、加 sleep、寫死測資、放寬斷言、skip 測試——這些是「掩蓋」不是「修復」。
   外部系統有 mock、測試庫可破壞時，沒有合法理由 skip。
2. **每批測試前重驗三件事**（不是開頭驗一次就一路信到底——服務會被別的工作流中途換掉）：
   ① port 上 LISTEN 的是哪個 process（貼命令列全文，不是「port 正常」）；
   ② 它跑的是不是**本次要驗的碼**（改動處的字串出現在回應、產物時間戳晚於改動、或服務啟動時間晚於最後一次建置——
   建置了沒重啟，服務讀的仍是舊產物）；
   ③ 該端點回應的**目標欄位實際值**（不是 200）。環境變數設對不等於生效，另驗 `response.url`。
   環境檔裡的值要跟**這個 process 實際讀的那份設定**比（`pretest.alignment` 的 `equals_process_file`／`under_process_root`），
   不是跟原始碼裡的某一份比。
3. **修 bug 走 red → green → verify**：先寫會紅的測試錨定 bug → 看它紅 → 修到綠 → 回跑原始症狀確認消失，測試留在回歸網。
   貼**兩次執行的原始輸出**（含測試名與 pass/fail 那行），**紅的那次必須在修改前**。
   用突變／revert 驗紅時，確認真的重新建置了（產物或 dev server 沒更新會拿舊行為當證據）。
   找不到正確 seam 寫紅測試＝這本身就是發現，回報它。
4. **主張「某段防護是多餘的、可以刪」要做 ablation**：拔掉跑一次、裝回去跑一次，對照 DB／API 實際筆數。
   時序性防護（防連點、競態守門、轉場期間的鎖）**讀碼一定看不到那個窗口**——實例：判定某個送出鎖是空操作，
   拔掉後一次三連擊建出三張單。
5. **判「某欄位／情境有沒有被測過」不能只看 grep 計數**：先定位檔案，再開檔看是否參數化（parametrize），
   有就展開參數清單逐項看；判準是「這個欄位有沒有被當成條件送出／被斷言」，不是「字串有沒有出現」。
6. **掃描器回報乾淨≠沒問題**：引用任何自動化檢查的零缺口結論前，答出三件事——
   它**看得到什麼形狀**、看不到什麼；它的 0 是「掃過且沒有」還是「根本沒掃到」；有沒有**第二種判準**能交叉驗。
   同時附**一個反向樣本**（已知有問題的案例，證明這個工具抓得到）。衛生閘走 baseline，只擋新增，沉默不代表水位是 0。
7. **交付前自己跑一次衛生工具並貼輸出**：寫入當下的 hook 只看被改到的那個資料夾，而且提醒可能被忽略——
   驗收要有可重現的證據。交付前對本輪動到的每個資料夾跑 `hardcode_check`／`drift_check`／`skip_audit`（帶 `--baseline`），貼 exit code 與輸出。
8. **造了資料就證明清乾淨了**：回報「測試資料來源」時一併貼 teardown 之後的計數查詢輸出（自己造的那幾筆 = 0）。
