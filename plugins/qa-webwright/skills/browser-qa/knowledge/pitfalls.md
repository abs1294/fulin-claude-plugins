## A. 資料來源 / 後端驗證（專案有後端或外部 API 時）

- **能走 UI 就走 UI**：模擬使用者操作必須點畫面、填表、按鈕，
  **禁止直接打後端 API 繞過前端 validation / payload 組裝 / 按鈕鎖控**。UI 上跑通才算 PASS。
  - 例外：沒有 UI 入口的外部系統 callback（如簽核系統 / webhook）可用指令模擬；
    資料準備 / 驗證 / 清理可用 SQL 或 API（那是 housekeeping 與驗證，不是「操作」）。
- **業務錯誤碼 ≠ HTTP 2xx**：後端可能回 HTTP 200 但 body 帶業務失敗碼。
  斷言要看**業務碼**，不要看到 200 就當成功。
- **重複/並發**：送出中重複點擊、並發編輯，要驗不產生重複資料或互蓋。
- **允許直打的界線與登記方式**（2026-09-24）：除上面的外部回調外，前端路由根本沒接上、守門類要構造 UI 擋掉的非法值，
  也可直打；三者都要在測試說明寫明原因。完整界線見 `methodology/test-discipline.md` §4。
- **請求層共用 headers 寫死 `Content-Type: application/json`，會讓表單編碼請求靜默綁定失敗**（2026-09-24）
  - **現象**：同一組 headers 發的 JSON 請求一切正常、資料也真的寫入；緊接著發的表單編碼請求（`form=`）卻回「查無此資料」，
    而直接查 DB 明明查得到——於是往「查詢時序、連線快取、交易隔離、欄位型別補空白」一路查錯方向。
  - **原因**：body 是表單編碼、header 卻宣稱 JSON；後端依 Content-Type 決定解析方式，對不上時**靜默把欄位填成型別預設值**
    （字串變空字串），不拋例外、不回 4xx。問題在「送進去的欄位本來就是空的」，不在查詢端。
  - **正確做法**：context 層級的共用 headers 只放跨請求通用的欄位（如 `Authorization`、`Accept`），
    `Content-Type` 交給 HTTP 客戶端依 `data=`（JSON）或 `form=`（表單）自動決定；需要固定時逐次在呼叫處指定。
    懷疑綁定問題時，把「送出去的參數值」與後端 log 中「實際收到的請求內容」逐字比對，不一致就是綁定層的事。

## B. 日期 / 時區：跨 UI → 送出 → 來源 → 顯示 的一致性驗證

**何時必做**：PR 動到任何日期 / DateTime / Timestamp / Converter / DatePicker。

**原因（時區偏移）**：UI 的 DatePicker 選「2026-04-23」時，前端常用本地時區產生 ms：
`new Date(2026, 3, 23).getTime()` → 在 UTC+8 代表的瞬間是 `UTC 2026-04-22 16:00`。
同一個 ms，用哪個時區「取日期部分」會得到 04-23 或 04-22。後端 getter（UTC vs Local）、
序列化 Converter、前端再 `new Date(...)` 顯示——任一環算錯就 **-1 / +1 天 或 ±8 小時**。

**為什麼只用 curl 測 API 抓不到**：手寫 payload 幾乎都用「UTC 00:00」的 ms，
UTC 當天和本地當天同日，**踩不到偏移**。所以 curl 全綠 ≠ 真實 UI 沒事。

**四點驗證（同一筆日期從頭跟到尾，每點 log+assert；截圖至多留檔備查、不作判定）：**
1. **UI**：DatePicker 選一個好辨識的本地日期 → 斷言 input 顯示 `2026-04-23`
2. **送出 payload**：抓 request body，記下該欄位的 Unix ms
3. **來源實際值**（若有持久化）：查存進去的值，比對是本地 `2026-04-23 00:00` 還是合理 UTC（看約定）
4. **刷新後**：重新載入後 DatePicker 仍顯示 `2026-04-23`（沒變 04-22）

四者任一不一致即 FAIL。**禁止**：只用 curl 送 UTC 零點 ms 就宣稱已驗證；用 SQL 硬塞正確值繞過 pipeline；
送出後只看成功碼就 pass、不查來源 / 不刷新對照。

> 純前端無後端時：第 3 點（來源）省略，只驗 UI 選值 = 元件 state / 送出值 = 刷新後顯示。

**第 3 點的預期值要先分欄位型別**（2026-09-24）：「看約定」要落到具體——常見約定是一般日期時間欄位存 UTC
（本地 `2026-04-23 00:00` 在 UTC+8 存成 `2026-04-22 16:00`，顯示端再轉回本地），
但**純日期型別**欄位（資料庫 `date` 型別、無時間部分）存本地日期、不轉時區、恆為 00:00。
查驗前先確認該欄屬哪一種（看資料表定義 / ORM 欄位型別設定），再決定預期值；兩種混用同一套預期，必有一種會誤判。
任一點不一致時，順著鏈追：前端日期元件輸出 ms 的邏輯 → 後端 DTO 取 UTC 還是本地的 getter → 回應的序列化 converter。

## C. 測試資料「壞值」的具體後果

- **邊界日期**：留空的日期欄位若在資料層存成型別最小值（例 .NET `DateTime.MinValue` / `0001-01-01`），
  前端用 JS Date 對它做 UTC 換算會因歷史時區偏移產出**超界 Unix timestamp**，
  後端 `DateTimeOffset.FromUnixTimeMilliseconds` 會拋 `ArgumentOutOfRangeException`。
  → 所以即使非必填，日期也要填合理值。
- 空字串 / null 在後續「變更歷史 / 顯示 / 再送審」流程容易炸或渲染空白，遮蔽真 bug。

## D. Windows PowerShell 背景啟動 dev server

- `npm` / `npx` 在 Windows 是 `.cmd` / `.ps1` 包裝、**不是 `.exe`**。
  `Start-Process 'npm' ...` 走 Win32 CreateProcess 不認 PowerShell script → **silent fail**。
  - 正確：`Start-Process 'npm.cmd' ...` 或 `Start-Process 'cmd.exe' '/c','npm.cmd',...`；`dotnet.exe` 則正常。
- 啟動後用 `Get-NetTCPConnection -State Listen -LocalPort <port>` 確認真的 LISTEN，
  別只靠回傳的 PID 當作起來了。
- 某些 dev server 對 `npm run dev -- --port 5182` 的 `--` token 處理會吃掉 flag（PowerShell 5.1）→
  改用底層工具直接帶參數（如 `npx vite --port 5182`）繞過 npm script 包裝。

## D2. Windows 跑 pytest 的兩個雷（2026-07-02）

- **常無 `pytest` 可執行命令**：`pip install pytest-playwright` 裝了「模組」，但 Scripts 目錄常不在 PATH →
  `pytest ...` 報 command not found。
  - **現象**：AI 為了讓 `pytest` 跑得動，自己建 `/tmp/qa-shim/pytest` 轉發成 `python -m pytest`（多此一舉的擦屁股）。
  - **原因**：pytest 的 console script 未進 PATH，但模組本身可用。
  - **正確做法**：用 `python -m pytest`（模組形式）而非 `pytest`（命令形式）。`qa-flow.sh run` 已內建自動偵測
    （pytest / python -m pytest / python3 / py），手跑時記得改模組形式。
- **中文輸出 UnicodeEncodeError**：Windows Python 預設 stdout 編碼常非 UTF-8（cp950 等），測試輸出含中文的
  assert 訊息 / print 會拋 `UnicodeEncodeError`，看起來像測試炸掉但其實是編碼問題。
  - **正確做法**：`export PYTHONIOENCODING=utf-8`（`qa-flow.sh run` 已自動設）。

## E. 前端元件互動雷（依元件庫取用）

- **下拉選單常用 portal**：選項渲染在 body 末端的 portal，**不在 modal/trigger 的 DOM 內**
  （例：Naive UI 的 `.n-base-select-option`、多數 UI 庫的 popper）。
  → 找選項要 scope 在「最新顯示」的 menu，不要 scope 在 modal 內找不到。
- **巢狀 modal**：最上層 modal 通常是容器選擇器的「最後一個」（例：`.n-modal-container` 的 `.last`）。
  同頁多個同名 dropdown 時，精準 scope 最上層 modal，否則會誤觸背景元素破壞測試環境。
- **隱藏的 file input**：上傳元件的 `input[type=file]` 多半隱藏，用 `set_input_files` 直接設檔，
  不必點按鈕、不走 file chooser。
- **二次確認 dialog 可能在獨立節點**（例：`dialog.warning()` 產生的 `.n-dialog`，不在原 modal 內）→
  找確認鈕要全頁 scan 或精準 scope 該 dialog。
- **DatePicker / 日期輸入多為受控元件**：禁止只用「打字塞值」（如 `browser_type` / `fill`）——值常不同步進框架 model。
  → 正確做法是點開日曆 picker 選日期，或打字後**驗證輸入框確實回饋了該值**（input 顯示 + state 已更新）再往下。
  （此為「值怎麼正確輸入進去」的互動機制；「選進去後日期解析對不對」屬時區一致性，見 B 段四點驗證。兩者是不同失效面。）
- **互動觸發一律用 trusted click，禁 `evaluate` 內的 `element.click()`**（此條主探索/runner 皆適用，不限 webwright）：
  框架的 `v-on:click` 等需 **trusted event**；`evaluate` 內 `element.click()` 是 untrusted，handler **時跑時不跑** →
  不可重現的**假性 FAIL**。正確：用探索工具的 trusted click（MCP `browser_click` + ref / runner `locator.click()`）；
  ref/locator 失效時換 selector 重定位，`evaluate.click()` 只作最後手段並於報告註明。

## F. 受控元件 / 富文本 state 同步雷

- 富文本編輯器（例：基於 slate.js 的 WangEditor）內部是 immutable model，
  **直接設 `innerHTML` / Playwright `fill` 不會同步到框架 model**。
  → 正確做法是透過框架的 component state 設值（例 Vue dev mode 的 `__vueParentComponent.setupState.<ref>`），
  且只有 dev/非 production build 才有這些 debug hook。
- 通則：受控元件（值由框架 state 驅動）不能只改 DOM，要觸發框架認得的事件或直接改 state。
- **白箱注入：抓元件內部狀態繞開冗長前置表單**（2026-09-24；以 Vue 3 dev build 為例，其他框架找對應的 devtools 掛點）
  - **用途**：要驗某個驗證規則在「特定資料狀態」（例如「選了檔但上傳未完成」）的守門行為，而走到那一步得先填完十幾個必填欄位時，
    可直接在真實瀏覽器裡操作真實元件的內部狀態——仍是「真實程式碼、真實執行」，證據力不打折。
  - **三種手法**：
    1. **表單元件的公開 API**：DOM 元素的 `__vueParentComponent` 指向包住它的元件實例；表單驗證庫的表單元件常把
       `setFieldValue` / `validateField` / `getErrors` 等方法掛在 `component.exposed`，往上找到表單元件即可讀寫值、觸發驗證、讀錯誤集合。
    2. **`setupState`**：沒有公開 API 的元件，`component.setupState` 仍暴露內部 ref 與函式，且**已自動解包**——
       寫入要**直接賦值** `setupState.xxx = ...`，寫 `setupState.xxx.value = ...` 不會生效（那是在已解包的普通值上加屬性）。
       `__vueParentComponent` 鏈是「渲染它的祖先」不是「宣告它的元件」，子元件常要沿 `subTree` 遞迴走訪、比對元件名稱才找得到。
    3. **dev server 的原生 `import()`**：不掛在任何表單上的工廠函式（依參數動態產生驗證 schema），
       直接在瀏覽器 console `await import('/src/…/schemas.js')` 載入真實模組呼叫即可。
  - ⚠ **最重要的坑：直接呼叫元件內部的「送出」類函式，守門「放行」時會真的執行業務動作**。
    `validateField` 只到驗證為止、無副作用；但 `handleSubmit` 這類函式在守門正確放行時會照常往下——真的打 API、寫 DB、觸發外部簽核送審，
    跟真人按送出一樣（實例：驗「應放行」情境時直接呼叫，結果寫進三張表，只能事後清理）。
  - **正確做法**：「應該擋下」的情境可以直接呼叫（守門提早 return，碰不到 API）；「應該放行」的情境**不要呼叫到底**，
    改驗「擋下的情境必跳出特定錯誤提示、放行的情境不跳同一則」——同一組觀察的正反面，不是弱化的替代品。
  - 只有 dev / 非 production build 才有這些 debug 掛點。

## G. webwright 操作雷（僅在啟用 webwright 備用探索時適用）

> **適用範圍**：本段只在「真實外部站、無 a11y、長程未知路徑」才用 webwright 自主探索時適用。
> 有 a11y / 後端可攔的專案走 a11y `ref` + ApiRecorder + runner locator，**不走截圖、不走 Firefox contract**。

- **一次一個動作**：不要在一次 evaluate 內同時 click + verify（DOM 更新時序，verify 拿到舊狀態）→
  分兩步：操作 → 等 → 驗證。（此 DOM 時序雷正是 webwright 抓不到「連點 race」的根因——回歸期的時序斷言應交給
  runner 的 API count/事件斷言，不靠截圖。）
- **用 ref > CSS selector**：從 snapshot 取得的 ref 是 strict locator，精準；
  CSS 文字選擇器可能 match 到背景的同名舊元素而誤點。
- 探索瀏覽器設定：viewport 固定 `1280×1800`、headless local Firefox（webwright 探索 contract）。
  （留檔截圖若有，不用 `full_page=True`；但截圖僅備查，判定一律靠結構化證據，不是截圖。）

## H. 外部站 TLS/HTTP2 指紋封鎖（2026-06-26）

- **現象**：打真實外部站（Akamai / HTTP2-protected）時 Chromium 報 `ERR_HTTP2_PROTOCOL_ERROR`
  或連線被靜默拒，看起來像 flaky test。
- **原因**：站台以 TLS/H2 指紋封鎖 Playwright Chromium。
- **正確做法**：**先換 `playwright.firefox` 再排查，別當 flaky 重試。** 本機自家系統用 chromium 即可、踩不到此雷。

## I. 長流程 context 經濟：MCP 探索把 session 撐到反覆 compact（2026-07-06）

- **現象**：大批 TC（實測 31 條）全程在 MCP 逐步執行、每步全頁 snapshot（實測 138 次、每次 ≈17KB ≈ 5k tokens）、
  逐 TC 建 task —— 單一 session 自動 compact 30 次、高峰每 6 分鐘一次；每次 compact 後光基線（系統 prompt +
  重注入的 skill / task 清單 / MCP schema + 摘要）就吃掉 75–96k tokens，可工作視窗只剩 ~70k，摘要品質隨輪數漂移。
- **原因**：全頁 a11y snapshot 與逐 TC task 追蹤都是「每輪重複灌進 context 的大宗」；MCP 逐步執行的成本
  隨 TC 數線性成長，而 codify 後的 pytest 幾乎零 context 成本——晚沉澱 = 把便宜的事用最貴的方式做完。
- **正確做法**：
  1. **snapshot 節制**：全頁 `browser_snapshot` 只在「導航後首次 / DOM 結構變化後」拍；驗單一元素、讀值、
     判 disabled/class 一律 `browser_evaluate` 或既有 a11y `ref` 定向讀取；頁面沒變不重拍。
  2. **批次沉澱**：探索一批 CP（建議 ≤5）→ 立即落成 `test_*.py` assert → `qa-flow.sh run` 驗證 → 下一批。
     MCP 只負責「摸出 selector 與真實值」，重複執行交給 pytest。
  3. **進度落檔不落 task**：TC/CP 進度寫進 catalog 與報告檔（磁碟為 ground truth，compact 不掉）；
     task 清單維持本 skill 固定的 8 條，**不逐 TC 建 task**（每次 TaskUpdate 都會把整份清單重注入 context）。
  4. **compact 徵兆即分段**：session 已 compact 2–3 次仍有大量 TC 未跑 → 立即把進度落檔，交接新 session 續跑，
     別讓同一個 session 靠摘要撐完全程。

## J. 定位比對強度與多語系（2026-09-24）

- **頁標題錨點要精確比對**
  - **現象**：頁面還沒渲染就判「載入完成」，後續斷言拿到上一頁的東西。
  - **原因**：`text=` / `has_text` / `get_by_role(name=…)` 預設是**子字串比對**；頁標題與側欄選單項同名時，
    上一步剛點過的選單連結會被提前命中；頁內有第二個標題含同樣字樣時同理。
  - **正確做法**：頁載入錨點一律 `h1:text-is('…')` 或 `get_by_role("heading", name=…, exact=True)`。
    改頁標題文案屬行為類變更：必掃全部測試的錨點同步（用寬鬆 pattern 掃，帶字母後綴的案例編號曾漏網）。
- **選項名稱互為前綴時 `has_text` 會選錯**
  - **現象**：要指派「負責人」卻選中清單較前面的「採購負責人」；目標使用者本來就持有該角色，於是「變更」等於沒發生、
    送出鈕維持 disabled，測試以「無可指派的選項」收尾——訊息完全指錯方向。
  - **原因**：`.filter(has_text="負責人")` 是包含比對，`.first` 拿到誰取決於 DOM 順序。實例中 helper 的說明文字寫著「用精確比對避免子字串誤中」，
    實作卻是裸字串——**註解與程式碼不符，且註解那句才是對的**。
  - **正確做法**：`has_text=re.compile(rf"^{re.escape(label)}$")` 錨定完整字串。
    判準：**選項名稱集合裡，有沒有任何一個是另一個的前綴或子字串？** 角色名、部門名、類別名常有這個特性，一律錨定。
- **page object 手打的多語系對照字典會與產品譯文靜默分岔**
  - **現象**：一批既有測試在切成英文的頁面上全數逾時，症狀是「點了送出但沒觸發 API」；畫面上恰好有一則紅字提示，
    把人往「某區塊資料沒填」的方向帶。
  - **原因**：page object 用手打的 `{"zh-TW": …, "en-US": …}` 存按鈕與 placeholder 文字，其中幾個英文值與產品實際譯文不符
    （用字不同、只差一個大小寫）。中文那半剛好全對，所以在「該頁預設中文」的期間一直綠；產品一改成預設英文就全爆。
    那則紅字是頁面**常駐**的提示文字，被泛用的錯誤選擇器（`[class*=error]`）一起撈進來。
  - **正確做法**：顯示文字一律從產品 i18n 資源檔按 key 取，**不手打任何一種語言的字面值**；對照字典非用不可時，值也要從 i18n 取。
    判「送出沒反應」時先確認按鈕真的被點到（有沒有任何請求發出），再看畫面錯誤訊息。
    兩個 key 在中文下字串相同、英文下不同時，用錯 key 只會在英文輪顯形——取 key 前先開元件原始碼確認該欄位用的是哪一個。

## K. 等待時序與 API 攔截（2026-09-24）

- **非同步操作後用固定延遲讀 DOM，會讀到渲染前的假空狀態**
  - **現象**：查詢後讀表格列數為 0，一路懷疑到「外部資料源沒資料」、甚至準備回報元件庫渲染缺陷；
    攔截請求才看到 API 明明回了資料、元件內部狀態每一層也都有資料——最後看一眼畫面，資料好好地顯示著。
  - **原因**：點擊後只等了幾百毫秒就讀 DOM，請求根本還沒回來。
  - **正確做法**：觸發查詢後用 `wait_for_selector` 等目標列出現，或等該 API 的 response 事件再讀，不靠固定延遲猜時間。
    **DOM 查詢回 0 筆時，先看一眼畫面實況再往下推論**——「程式化查詢說沒有」不代表真的沒有。
    抓到新真因後，**逐條回頭檢查舊結論是否受同一坑影響**：受影響的作廢，同步執行、不涉及等待的結論維持有效——
    不要整批推翻，也不要整批保留。
- **等待條件只等「操作能繼續的必要條件」**
  - **現象**：等抽屜打開逾時，錯誤訊息像「抽屜沒開」，實際早就開了；而且**全套連跑必現、單獨跑不現**，最容易被當成隨機不穩定略過。
  - **原因**：等待條件寫成「抽屜內的富文本編輯器出現」，但該抽屜的編輯器是選填、不保證渲染。
  - **正確做法**：只等抽屜本體可見。判準：**這個等待條件是「操作能繼續的必要條件」，還是只是「畫面比較完整」？** 後者不該進 wait。
    連帶：全套連跑時前一支測試可能留下未關的抽屜 / 對話框遮罩，導致下一支等不到頁標題——進頁前先按 Escape 清遮罩、
    載入失敗重試一次，比放寬 timeout 有效。
- **進頁會自動打一次的 API，動作後用 `wait_for` 會抓到進頁那次**
  - **現象**：斷言驗到別人的資料，約三分之一機率紅；更糟的是切語系後查詢壞掉的測試仍然綠（抓到的是切換前那次）。
  - **原因**：API 攔截器的 `wait_for(url)` 回「已攔到的第一筆」；頁面在 mounted / 立即觸發的 watch 已經打過同一支 API。
  - **判準**（三件同時成立才算隱患）：該 URL 進頁會自動打（實讀元件的 mounted / immediate watch）＋測試在動作後 `wait_for` 同一 URL
    ＋有斷言吃那個回傳值。只當 barrier、回傳值丟掉的不算；進頁後沒有動作就 `wait_for` 是刻意抓進頁那次，正確。
  - **正確做法**：動作前 `before = api.count(url)`，動作後等到第 `before + 1` 筆；能綁請求就加綁定斷言（從**請求** payload 讀自己的 id——
    回應不含 id 時別從回應讀，會做出永遠不觸發的假護欄）。同條件重查兩次時 payload 相同，只能靠計數。護欄要用突變驗（把綁定值改壞要紅）。

## L. 斷言盲區：渲染層、排序結果、取值鍵、版面結構（2026-09-24）

- **「API 回成功」≠「畫面欄位有值」：渲染層缺陷要驗 DOM**
  - **現象**：改列表欄位 key 後，測試只斷言點排序的業務碼成功，全綠；但其中幾個欄位畫面整欄空白。
  - **原因**：缺陷在前端渲染層，斷言卻只看後端回應碼。表格元件對「沒有自訂 render 的欄」用 `row[column.key]` 取值，
    key 一改成後端命名就取不到（資料實際是另一種命名）。
  - **正確做法**：凡改動「列表欄位 key / 欄位資料對應 / render」，除了驗 API，**必須驗 DOM 儲存格真的有值**：
    從回應取某筆的欄位值，斷言它出現在表格 DOM（該欄資料本身為空時略過，避免誤判）。
    深層教訓：錯誤的心智模型（「改 key 不影響顯示」）會連帶選錯測試範圍。
- **排序要驗「結果真的排對」＋正倒序雙向＋先驗前提**
  - **現象**：只驗排序請求的業務碼成功，反向排序壞掉也綠；或拿降序資料去驗「應遞增」而假紅。
  - **原因**：成功碼只代表後端沒拒絕，不代表資料真的排對；點表頭的循環方向不一定從遞增開始。
  - **正確做法**：斷言回傳 items 真的照方向排序，且**兩個方向都驗**；方向**讀實際送出的排序參數**決定，不要假設第一次點就是遞增。
  - **分頁連帶**：伺服器端分頁時，遞減第一頁與遞增第一頁本來就是**不同子集**（頭尾兩端）；
    `set(desc_ids) == set(asc_ids)` 在資料少於一頁時會過、資料一多就壞——是潛伏的錯誤斷言。
    改驗「各方向內部有序」＋「兩方向結果不同」。驗「某類資料墊底」前先放大每頁筆數，否則墊底的那些根本不在回傳裡。
- **攔截到的是後端原始回應，欄位命名與前端不同**
  - **現象**：排序驗證一直 skip「資料不足 2 筆」，實際後端有幾百筆。
  - **原因**：攔截器讀的是原始 HTTP 回應（例如 snake_case），測試用前端轉換後的命名（camelCase）取值全拿到 `None`，
    被「資料不足」分支靜默 skip——測試碼在跑，但什麼都沒驗到。
  - **正確做法**：讀攔截回應一律用後端原始命名；「取不到值就 skip」的分支必加保險（`assert verified_count > 0` 之類），
    沒真的驗到東西要 FAIL（skip 紀律見 `methodology/critical-points.md` 硬規則 ④）。
- **版面像素斷言不要用嚴格比較**
  - **現象**：驗「元素完整可見 / 捲到底」偶發假紅。
  - **原因**：`bottom <= innerHeight` 這類嚴格比較會被分數高度的次像素捨入打破（實測差 0.24px）。
  - **正確做法**：用 hit-test（`elementFromPoint` 命中＝真可點）＋捲動到底判定（`scrollTop + clientHeight ≈ scrollHeight`，容差 1px）；
    「對齊」類斷言用 ≤1px 容差，不要求逐位元相等。
- **字串斷言對「版面壞掉」完全盲**
  - **現象**：一段說明文字改成 i18n key＋`v-html`＋sanitizer 後，標題與清單樣式全被剝掉、字全黏成一坨；lint、build、數十支 e2e 全綠。
  - **原因**：每支測試只問「字串有沒有出現」，而標題標籤被剝掉後那些字仍然出現；sanitizer 白名單不含標題標籤、且屬性白名單為空陣列（＝全禁）。
  - **正確做法**：驗**結構**——兩個標題去空白後不可相鄰黏連、元素數量（`locator("h3").count()`）、標題與內文的座標差、`display`。
    要在產品用 `v-html` 前，**先實跑一次 sanitizer 看輸出長度與標籤**，比讀白名單可靠。
    「跟既有先例一致」要看內容形狀：先例若只處理過純文字，語法一樣不代表白名單容得下帶結構的內容。
- **「英文版不該出現中文」斷言會把資料值誤判成漏翻**
  - **現象**：切英文後掃整頁 / 整封信的中文字，抓到一個中文公司名，判為漏翻。
  - **原因**：插值進來的資料值本來就可能是中文，那是正確行為。
  - **正確做法**：「切英文後中文必須消失」仍是唯一抓得到硬編的斷言（只驗英文有出現抓不到），但比對要去掉資料值：
    **同一段中文在中英兩版都出現 → 是資料值**（介面文字在英文版已被取代）。
    `leftover = [s for s in han.findall(en_text) if s not in zh_text]; assert not leftover`。
    連帶：帶具名插值的樣板不能整句比對，要用 `re.split(r"\{[a-zA-Z_]+\}", tmpl)` 拆出固定片段、只留長度 ≥2 的片段再比；
    中英譯文本來相同的（純代號）要跳過「中文須消失」，否則恆紅。

## M. 種子資料與共用狀態（2026-09-24）

- **改成自種自清後，會連鎖暴露「被舊種子預填值遮住的必填卡控」**
  - **現象**：種子改成全新建立後一次紅一整批，症狀都是「找不到某元素」或「API 沒發出、回應為 None」，而不是必填提示。
  - **原因**：舊種子多半預填好值，測試**從未走過真實的必填路徑**；全新資料欄位為空，某些欄位只在特定值時才渲染、某些必填欄位擋住送出。
    另外全新資料的首次送出可能走「新建」端點而非「更新」端點，斷言等錯端點會一直等不到（這是正確業務邏輯）。
  - **正確做法**：改種子後出現「找不到元素 / API 沒發出」，先比對**該欄位在新舊種子的值差異**，不要往 locator 或時序去猜；最快的驗法是開畫面看必填提示。
- **種子裡的外部鍵值不可自己編**
  - **現象**：所有用自種資料的送出測試一律回某個業務錯誤（例如「查無指定的簽核人員」），訊息指向下游流程。
  - **原因**：種子寫死的代碼與帳號**在資料庫根本不存在**；而且成立條件常是**配對**（代碼要存在、其對應的使用者也要存在，只有一邊有仍會失敗）。
  - **正確做法**：執行時從資料源動態取一組真的存在、且配對成立的值。判準：**種子資料裡的每個外部鍵值，是不是「我編的」？**
    編出來的值在測試庫重建後必然失效，而失敗訊息會指向下游而非種子本身。版號類同理：要「新版號須遞增」的測試，
    版號寫死一旦被其他測試推高就會被前端擋下、根本不打 API，表現成 `None` 取下標的 TypeError——動態取現行最大版號再 +1。
- **測試素材的成立條件是「不在某張產品維護的清單裡」時，不可寫死**
  - **現象**：兩支測試同時轉紅，斷言的原因代碼變了，看起來像後端判準寫錯。
  - **原因**：測試寫死某個網域當「會對到多筆資料」的樣本，而同一輪稍早把該網域家族補進了產品的「公用網域排除清單」——
    樣本從此被清單優先攔下，走不到那條分支。清單本身是產品功能、會隨維運增刪，測試卻把某一次的清單狀態寫死。
  - **正確做法**：**換一個樣本不是解法**（只是把地雷埋到下一次維運），要**執行時現查**符合條件的素材；
    查不到時優先走產品入口自造一份（`methodology/critical-points.md` 硬規則 ① ④），造不出來才依 skip 分流處理。
    同型的還有：字典值、黑白名單、權限碼綁定、排除清單。查詢要注意效能（對每一列跑子查詢可能逾時，可分兩段查、在程式側扣除）。
- **資料可不清時，全域斷言會被累積資料打爆**
  - **現象**：「近 N 天待處理件數 = 1」「某人名下加總 = 0」「第一頁第一列」「全表筆數相等」這類斷言在資料累積後全部失效。
  - **正確做法**：以自種標記為錨——差量（動作前先快照外來件數）、限縮到自己造的那幾筆 id、用篩選或翻頁定位本單、
    期望值的查詢條件對齊後端實際的 JOIN / 過濾條件。
- **fixture 切換身分後還原成寫死值，會讓後續整批假紅 / 假 skip**
  - **現象**：全套跑完後，所有以「執行中身分」為前提的測試整批失敗或被跳過。
  - **原因**：某 fixture 為了造資料切換身分（甚至重啟服務），teardown 還原成寫死的某個身分，而不是原本執行中的那一個。
  - **正確做法**：**讓資料遷就身分**（把資料種給目前執行中的身分），fixture 不去切換 / 重啟服務；判別目前服務實際身分要讀該 process 的啟動環境。
- **權限綁定走產品的權限流程**
  - 需要替測試帳號綁權限時，走產品的「修改 → 送審 → 核准回調」流程並做成冪等（已綁就不送審）。
  - ⚠ 若產品的權限版本鏈是全域單軌，送審會**連帶核准別人留在草稿上的未送審變更**；送審後要立刻用回調收尾，
    遇到殘留的 pending 先以退件解鎖。
  - 外部通知服務的可達性可能一天內反覆變：依賴「真的寄出」的斷言用具名的 B 類 `skipif`，只 skip 真依賴寄送成功的那幾支，件數 / 分組類照跑。
- **種子失敗路徑要能自清：拿不到 Id 就沒人清得掉**
  - **現象**：種子 INSERT 成功、但解析輸出取不到 Id 而 raise，資料已落地卻成孤兒——teardown 清單裡沒有它。
  - **原因**：執行 SQL 的 helper 只對非 0 回傳碼拋例外，「執行成功但輸出格式非預期」會正常回傳，資料已在庫裡。
  - **正確做法**：`raise` 之前先依**可辨識標記**兜底清一次（種子資料帶產品不會產生的前綴），不要依賴「解析成功拿到 Id」。
    驗證兜底有效：暫時讓解析永遠失敗，跑一次確認錯誤訊息出現、且事後查殘留為 0。
- **共用 fixture 的批內順序汙染**：寫入型測試共用同一筆資料時，正向操作後要還原、不依賴前一支的殘留狀態；
  殘留的「送審中」之類狀態會讓後續整批假失敗（屬 skip 分流的 D 類，應修 teardown 而非 skip）。

## N. 環境、多實例與 runner 執行（2026-09-24）

- **agent 顯示 idle ≠ 它的背景任務死了**
  - **現象**：看到某 QA agent idle 就自己前景重跑同一批測試，撞上它還在跑的任務，資料庫唯一鍵衝突。
  - **原因**：idle 只代表它當下那一輪沒動作，它以背景方式啟動的 process 可能還在跑。
  - **正確做法**：看實際 process 與其命令列（Windows：`Get-CimInstance Win32_Process -Filter "Name='python.exe'"`）。
    同一台機器上可能還有**第三方 session** 打同一個資料庫——看到權限 / 種子相關的偶發錯誤，先考慮併行干擾，不要當成產品缺陷。
- **驗「前端改動有沒有生效」：看 dev server 實際吐出的內容，數命中用 `grep -o | wc -l`**
  - 檔案 mtime、熱更新有沒有跳訊息都不算數，唯一算數的是 `curl` dev server 該原始檔路徑實際吐出什麼。
  - 協定要對：https 的服務用 http 打會回 `000`，看起來像服務沒起來——兩種協定各試一次再下結論。
  - `grep -c` 數的是「有命中的行數」，同一行出現三次只算一次；要「出現幾次」用 `grep -o … | wc -l`（實測曾用 `-c` 把「已還原」誤讀成「未還原」）。
  - 改動前後對照（二分法）時，兩端都要這樣驗過才開始跑，否則跑的是哪一版都不知道，整輪對照作廢。
- **開畫面測之前，先驗「本次改動的產物在不在那台後端上」**
  - **現象**：整輪測起來全過，但測到的是幾天前的程式碼。
  - **原因**：主線建置輸出目錄被別的 session 的 process 鎖住，於是本輪建置導到別處；前端指向的那台後端跑的仍是舊產物。**重啟解不掉**——重啟後載入的還是同一份舊產物。
  - **正確做法**（兩步都要）：① 查前端**實際**打哪台後端（看前端真正生效的環境設定檔與該後端 process 的命令列，
    不要看註解或別的設定檔）；② 對那台載入的產物直接 grep / `strings` 本次新增的類別名，命中 0 就是舊版。
    解法是用本輪的產出另起一個 port、前端另建一份環境設定指過去，**不要改共用的本機設定檔、不要殺別人的 process**；
    起完用瀏覽器網路紀錄實測畫面真的打到新 port。
- **port 歸屬以實測為準，不信註解**：環境腳本裡「某 port = 某服務」的註解會隨其他 session 起停而過期；
  跑之前用 `netstat -ano` ＋查 process 命令列確認歸屬——驗錯工作目錄的碼全程不會報錯。
- **單一 process 連跑全套會讓寫入型測試 flaky**：連跑數十支後 dev server 尾段降速，寫入型互動偶發逾時。
  **分兩批**：讀取型可並行（如 `-n3`），寫入型序列。上傳 / 送出型大量並行也可能撞後端並發限制，一律序列。
- **後端跑著時要再起一個實例：用預編輸出跑，不要重編共用輸出目錄**
  - 既有實例跑著時直接 `run`（會重編進共用輸出目錄）會撞檔案鎖；這不是程式錯誤，別去追編譯問題；也**不要砍別人的後端**。
  - 做法：先 build 到暫存輸出目錄（確認設定檔與 runtime 設定一併帶出），再從那裡直接執行、配隔離 port；測試端用環境變數指過去，兩個實例並存。
  - ⚠ 起背景服務**不要用 `nohup … &` 包在背景工具呼叫裡**——外層一退出子程序就跟著沒了（拿到 exit 0 但 port 上根本沒有 listener）。
  - 確認起來了要看 **listener ＋ log 裡的執行環境名稱**兩件事，不是只看 process 還在。
- **同一台後端上，兩個測試檔可能需要互斥的環境設定**
  - **現象**：補上某個環境變數後，另一個檔的幾支測試轉紅，差點回頭去翻不相干的產品碼。
  - **原因**：A 檔需要後端帶某個 mock 行為開關（讓特定輸入回退件形狀），B 檔斷言同一輸入要回核准形狀——兩者在同一台後端上不可能同時綠。
  - **正確做法**：跑全套前先確認每個目標檔需要哪一種；需要特殊開關的檔在說明中寫明，並起隔離的後端實例（另 port、另輸出目錄）跑。
- **module / session scope 的 fixture 內不可自己 `sync_playwright()`**
  - **現象**：`It looks like you are using Playwright Sync API inside the asyncio loop.`——**單獨跑那支完全正常，整包跑才炸**，
    錯誤訊息指向 asyncio，容易誤判成環境或 pytest 設定問題。
  - **原因**：同一執行緒已經有 pytest-playwright 開的 sync API 在跑，再開第二個就衝突；單跑時你開的剛好是第一個。
  - **正確做法**：把 pytest-playwright 的 `playwright` fixture（session scope，任何 scope 都收得到）收成參數，用它 `.chromium.launch()`，
    `finally` 裡關瀏覽器；原本 function-scoped fixture 會套的登入 / 路由改寫要自己再套一次。
    ⚠ 連帶：module-scoped fixture 跑在 function-scoped autouse fixture（例如授權）之外，要自己呼叫一次（冪等），
    否則頁面被路由守衛擋成無權限頁，整批斷言拿到的是錯誤頁的文字。
